## 双重检查锁（Double-Checked Locking）

```java
public class ConfigLoader {
      private static Map<String, Object> config;

      public static Map<String, Object> getConfig() {
          if (config == null) {
              config = 从文件读取YAML();  // 只读一次
          }
          return config;
      }
  }
```

单线程没问题。多线程呢？

  时间线 →
  线程A: if (config == null) → true → 开始读文件...
  线程B: if (config == null) → true → 也开始读文件...

  两个线程同时判断 config == null，都去读文件。结果：文件被读了两次，两个线程各拿到一个不同的 Map 对象，线程 A
  拿到的对象可能被线程 B 的覆盖掉。

---

**第一反应：加 synchronized**

```  java
public static synchronized Map<String, Object> getConfig() {
      if (config == null) {
          config = 从文件读取YAML();
      }
      return config;
  }
```

 安全了。但问题来了：99.9% 的调用 config 已经不是 null 了，只是从缓存取值而已，但 synchronized 强制所有线程排队。

  线程A 取缓存 → 等锁 → 拿到锁 → 返回 config → 释放锁
  线程B 取缓存 → 等锁 → 拿到锁 → 返回 config → 释放锁
  线程C 取缓存 → 等锁 → ...

  每次取缓存都要争抢同一把锁——白白浪费。

---

```java
public static Map<String, Object> getConfig() {
      if (config == null) {                    // ① 第一次检查（无锁）
          synchronized (ConfigLoader.class) {   // ② 加锁
              config = 从文件读取YAML();         // ③ 初始化
          }
      }
      return config;                            // ④ 返回
  }
```

 这里有个经典的竞态漏洞：

  时间线 →
  线程A: ① config == null → true → 进入 if
  线程B: ① config == null → true → 也进入 if（还没到 synchronized！）
  线程A: ② 拿到锁 → ③ 读文件 → config = 结果 → 释放锁
  线程B: ② 拿到锁 → ③ 又读了一遍文件！← 问题在这

  线程 B 在 ① 处判断时 config 是 null，但等它拿到锁时，线程 A 已经初始化完了。所以 synchronized 块内必须再检查一次。

---
  正解：synchronized 内再检查一次（「双重」的由来）

```java
  public static Map<String, Object> getConfig() {
      if (config != null) {                    // 第一次检查：快速路径
          return config;                       // 99.9% 走这里，不加锁
      }
      synchronized (ConfigLoader.class) {       // 加锁
          if (config == null) {                // 第二次检查：防止重复初始化
              config = 从文件读取YAML();
          }
      }
      return config;
  }
```

  两个线程同时撞到 null 的情况：

  线程A: 第一次检查 null → 等待锁
  线程B: 第一次检查 null → 等待锁
  线程A: 拿到锁 → 第二次检查 null → 读文件 → config=结果 → 释放锁
  线程B: 拿到锁 → 第二次检查 config≠null → 跳过 → 释放锁  ← 不会重复读文件了！

  还差一步：为什么需要 volatile？

  上面看起来完美了，**但 JVM 有个坑：指令重排序。**

  config = 从文件读取YAML();

  这行代码在 JVM 层面其实是三步：

  ① 分配内存空间
  ② 执行构造函数，填充 Map（耗时）
  ③ 把引用赋值给 config 变量   ← config 指向新对象

  **JVM 为了性能，可能把 ② 和 ③ 调换：**

  **① 分配内存空间**
  **③ 把引用赋值给 config ← 先指向了！（但对象还没初始化完）**
  **② 执行构造函数，填充 Map**

  如果 ③ 先执行了，另一个线程看到的情况是：

  线程A: ③ config = 0x1234（指向了一个还没填充完的半成品 Map）
  线程B: if (config != null) → true（看到了半成品的地址） → 直接返回！
         → 拿到一个没填充完的 Map → 💥

  volatile 禁止这种重排序：

  private static volatile Map<String, Object> config;

  volatile 保证：对 config 的写操作完成之前，任何线程都看不到它的新值。

```java
public class ConfigLoader {
  private static volatile Map<String, Object> config;  // ← volatile 防止指令重排
  public static Map<String, Object> getConfig() {
      Map<String, Object> result = config;  // 先读一次局部变量（比读 volatile 快）
      if (result != null) {
          return result;                    // 快速路径：99.9% 的情况
      }
      synchronized (ConfigLoader.class) {
          if (config == null) {             // 第二次检查（锁内）
              config = 从文件读取YAML();
          }
          return config;
      }
  }
```
