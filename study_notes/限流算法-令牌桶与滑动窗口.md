# 限流算法：令牌桶 + 滑动窗口

---

## 一、令牌桶（Token Bucket）

### 原理

一个桶，按固定速率往里放令牌，满了就丢弃。请求来了要拿令牌，拿到就放行，拿不到就拒绝。

```
          ┌─────────────────────────┐
          │                         │
 速率 r/s →  🎫🎫🎫🎫🎫🎫  ← 桶容量 b  │
          │       ↓                │
          └───────┬────────────────┘
                  │
             请求拿令牌
          ├─ 拿到 → 放行
          └─ 没拿 → 拒绝
```

---

### 为什么能支持突发流量

空闲时令牌攒着不丢。桶容量 200 = 最多攒 200 个。突然来一波流量，一口气全拿走——这就是「突发」。

```
正常：每秒 200 个请求，均匀到达 → 来一个拿一个，桶始终空的
  
空闲 1 秒：桶攒满 200 个令牌
       ↓
  突然 200 个请求同时到达 → 全拿了 → 200 个全放行
  
然后又回到正常：来一个拿一个
```

漏桶做不到这个——漏桶是固定速率出水，突发流量只能溢出丢弃。

---

### 惰性填充（不用后台线程）

不用定时线程放令牌，而是**每次请求时根据时间差计算该补多少**。参考 Guava RateLimiter 的做法。

```java
private void refill() {
    long now = System.currentTimeMillis();
    long elapsed = now - lastRefillTime;  // 距上次请求过了多久
    // 补充 = 经过的时间 × 每毫秒生成速率
    availableTokens = Math.min(capacity, availableTokens + elapsed * refillRatePerMs);
    lastRefillTime = now;
}
```

例子：速率 200/s = 0.2/ms，间隔 500ms 没请求 → 补 100 个令牌。睡了一万年没请求 → 补到 min(200, ...) 封顶。

---

### 完整代码（HeteroMesh 版）

```java
public class TokenBucketRateLimiter {
    private final long capacity;            // 桶容量
    private final double refillRatePerMs;   // 每毫秒生成令牌数
    private double availableTokens;         // 当前可用令牌
    private long lastRefillTime;            // 上次填充时间

    public TokenBucketRateLimiter(long permitsPerSecond) {
        this.capacity = permitsPerSecond;
        this.refillRatePerMs = (double) permitsPerSecond / 1000;
        this.availableTokens = capacity;     // 初始满桶
        this.lastRefillTime = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        refill();                            // 先补
        if (availableTokens < 1) return false;
        availableTokens--;                   // 拿走一个
        return true;
    }
}
```

---

### 跟 Guava RateLimiter 的区别

| | Guava（生产） | HeteroMesh（教学） |
|---|---|---|
| 并发控制 | synchronized + 双检锁 | synchronized |
| 预热 | 支持 warmup | 不支持 |
| 等待获取 | `acquire()` 阻塞直到拿到 | 只有 tryAcquire |
| 精度 | 微秒级 | 毫秒级 |

## 二、滑动窗口（Sliding Window）

### 为什么需要滑动窗口？

**固定窗口计数器**有临界突刺问题：

```
限制：每秒最多 100 个请求

固定窗口：
  [0─────────1s──────────][1──────────2s──────────]
   
  第 0.5s~1.0s：80 个请求 → 在窗口 1 内，不超过 100 ✅
  第 1.0s~1.5s：80 个请求 → 在窗口 2 内，不超过 100 ✅
  
  实际 0.5s~1.5s 这 1 秒内：80+80 = 160 个请求 ❌ 超了 60%！
```

**滑动窗口**把 1 秒切成 N 个小格，统计「最近 N 格的总和」。每过一小格，最老的数据自然滚出统计范围。

---

## 数据结构

两个数组，长度相同，下标一一对应：

```
windowCount = 10（切成 10 个格子）
windowLengthMs = 100ms（每格 100ms）
intervalMs = 1000ms（总共统计 1 秒）

counters[]   = [12, 8, 15, 10, 5, 3, 20, 7, 9, 11]  ← 每格的请求数
timestamps[] = [T0, T1, T2, T3, T4, T5, T6, T7, T8, T9] ← 每格的起始时间
```

`counters[i]` 和 `timestamps[i]` 描述同一个格子——这个格子里有多少请求，以及它的起始时间。

---

## 为什么是环形数组？

为了不频繁创建和销毁对象：

| | 不用环 | 用环 |
|---|---|---|
| 每过 100ms | new 新格子，GC 旧格子 | 找到过期格子，原地清零复用 |
| GC 压力 | 每秒 10 次对象分配 | **零对象分配** |

数组初始化一次，格子在原位循环复用，时间到了就清零。

Sentinel 的 `LeapArray` 就是这样实现的——用 `AtomicReferenceArray` + CAS 实现线程安全的环形复用。

## 核心代码解析（HeteroMesh 版）

```java
public synchronized boolean tryAcquire() {
    long now = System.currentTimeMillis();
    // 当前格子的起始时间（如 1100ms）
    long currentWindowStart = now - (now % windowLengthMs);

    // ① 统计所有有效格子的请求数
    int total = 0;
    for (int i = 0; i < windowCount; i++) {
        // 检查每个格子是否过期
        if (now - timestamps[i] > intervalMs) {
            counters[i] = 0;                    // 过期清零
            timestamps[i] = currentWindowStart; // 设置新的起始时间
        }
        total += counters[i];
    }

    // ② 判断是否超阈值
    if (total >= maxRequests) return false;

    // ③ 在当前格子里 +1
    int idx = (int) ((currentWindowStart / windowLengthMs) % windowCount);
    if (timestamps[idx] != currentWindowStart) {
        // 这个位置还是上一轮的数据 → 清零
        timestamps[idx] = currentWindowStart;
        counters[idx] = 0;
    }
    counters[idx]++;  // 原子地记数
    return true;
}
```

## 为什么叫「滑动」

```
固定窗口：
  [0s────────1s────────][1s────────2s────────]
  到了整秒才重置，刷新太慢

滑动窗口：
  ╔════════════ 1s 窗口 ════════════╗
  ║ [格][格][格][格][格][格][格][格][格][格] ║
  ╚══════════════════════════════════╝
       ↑                            ↑
   最老的格子                    最新的格子
   随时间流逝被滑出窗口            新数据不断填入
   
  每 100ms 就有一个老格子滚出去 → 窗口在连续「滑动」
```

## Sentinel 生产版 vs HeteroMesh 教学版

| | Sentinel（生产） | HeteroMesh（教学） |
|---|---|---|
| 并发控制 | LongAdder + CAS + ReentrantLock | synchronized |
| 数据结构 | AtomicReferenceArray<WindowWrap> | long[] + long[] |
| 锁粒度 | 仅在窗口轮转时加锁 | 每次 tryAcquire 都加锁 |
| 吞吐量 | 极高 | 够用 |
| 可读性 | 复杂 | 直观 |

---

## 一句话总结

| 算法 | 一句话 | 参考 |
|------|--------|------|
| 令牌桶 | 匀速放令牌，攒多了可以瞬间用掉（突发） | Guava RateLimiter |
| 滑动窗口 | 环形数组循环复用，过期自然滚出窗口 | Sentinel LeapArray |

---

## 两种算法对比

| | 令牌桶 | 滑动窗口 |
|---|---|---|
| 突发流量 | ✅ 支持，桶容量决定突发大小 | ⚠️ 有限，受窗口大小制约 |
| 平滑性 | 好（匀速补充） | 好（连续滑动） |
| 内存消耗 | 极小（几个字段） | 跟窗口精度成正比 |
| 实现难度 | 简单 | 中等 |
| 适用场景 | 允许瞬时突发、平均速率稳定的场景 | 需要精确控制某段时间内请求数的场景 |
