# HeteroMesh 后续课程总览：Agent Runtime 后端底座版

---

## 一、最终定位

HeteroMesh 的新定位：

```text
面向 AI / Agent 任务的分布式执行与调度 Runtime 后端底座
```

它不是一个 Agent 应用框架，不和 LangChain、CrewAI、AutoGen 直接竞争；它也不是 vLLM 这种推理引擎。HeteroMesh 要做的是 Agent 或 AI 任务运行时下面那层后端基础设施：

```text
任务提交
任务状态管理
Worker 发现与心跳
资源感知调度
远程执行
超时、取消、重试、故障转移
流式事件返回
指标、日志、trace
轻量 LLM / Tool 执行接入
```

一句话：

```text
Agent 负责决定“下一步做什么”。
HeteroMesh 负责把“下一步”稳定地调度到 Worker，执行、回收、观测和失败恢复。
```

---

## 二、为什么不直接改成 Agent 应用框架

当前项目的优势是 Java 后端底层能力：

```text
Netty
自定义协议
异步 RPC
Controller / Worker
任务状态机
负载均衡
重试、超时、熔断、限流
```

这些能力对 AI Agent 岗很有价值，但它们属于 Agent Infra / Agent Runtime，而不是 prompt 编排层。

因此后续路线必须避免两个极端：

```text
错误方向 A：完全不碰 AI / Agent，只做传统 RPC Demo
错误方向 B：丢掉后端底座，套 LangChain 做聊天 Agent
```

正确方向：

```text
后端底座是主线
Agent / AI 任务是应用场景
轻量接入 LLM / Tool / AgentStep
不做复杂多 Agent 角色扮演
```

## 三、当前已完成基础

截至当前阶段，HeteroMesh 已经具备 Agent Runtime 的底层雏形。

| 能力 | 当前状态 | 对 Agent Runtime 的意义 |
|------|----------|--------------------------|
| 自定义协议 | 已实现 | Worker 与 Controller 的底层通信格式 |
| Netty 长连接 | 已实现 | 支撑高并发远程执行和异步响应 |
| requestId + Future | 已实现 | 匹配一次远程调用的请求和响应 |
| Worker 注册与心跳 | 已实现 | Runtime 能知道哪些执行节点可用 |
| 负载均衡 | 已实现 | Runtime 可以选择合适 Worker |
| 熔断、限流组件 | 有基础实现 | 后续接入主链路后保护执行系统 |
| TaskRequest / TaskResult | 已实现 | AgentStep / ToolCall 可以复用任务抽象 |
| TaskStatus / TaskMetadata | 已实现 | 任务生命周期状态管理 |
| InMemoryTaskStore | 已实现 | Runtime 保存任务状态和结果 |
| TaskScheduler | 已实现基础版 | Controller 侧调度决策核心 |
| TaskExecutor | 已实现 demo 版 | Worker 侧执行入口 |
| TaskQueryService | 已实现 | 后续 HTTP API / Dashboard 的基础 |
| TaskTimeoutManager | 已实现雏形 | 任务级超时和终态保护基础 |
| 任务级重试 | 进行中 | 失败 Worker 转移到其他 Worker |

当前缺口：

```text
任务闭环还需要打磨
RPC 可靠性需要回炉
Worker 资源模型和背压还没有
HTTP / SSE API 还没有
AgentRun / AgentStep / ToolCall 还没有
LLM / Tool 执行器还没有
指标、压测、Docker 和最终展示还没有
```

## 四、总路线

后续课程按六个阶段推进：

```text
阶段一：任务调度闭环打磨
阶段二：RPC 与连接治理补强
阶段三：异构 Worker 与执行背压
阶段四：对外 API、流式事件和观测
阶段五：轻量 AI / Agent 执行场景
阶段六：工程化、压测和面试包装
```

核心原则：

```text
每一课都要有可运行闭环
每一课都要有测试
每一课都要能转化成面试讲点
不为了“像 Agent”而牺牲后端深度
```

## 五、阶段一：任务调度闭环打磨

目标：先把普通 AI 任务的生命周期做稳。

这一阶段完成后，系统应具备：

```text
提交任务 -> 创建任务 -> 选择 Worker -> 执行 -> 回传结果 -> 保存结果 -> 查询结果
失败 -> 判断能否重试 -> 换 Worker -> 最终成功或失败
超时 / 取消 / 后到结果 -> 不破坏终态
```

### 第21课：Controller 回收任务结果并写回 TaskStore

目标：

- Worker 返回 `TASK_RESULT`
- Controller 解析 `TaskResult`
- 写回 `TaskStore`
- 回传给原始提交方
- 后到结果不能覆盖终态

核心类：

```text
ServerHandler
TaskStore
TaskResult
TaskStatus
```

完成标准：

```text
Worker 执行成功后，Controller 能保存 SUCCEEDED 结果
Worker 执行失败后，Controller 能保存 FAILED 结果
Client 能收到最终结果
```

面试价值：

```text
能讲清楚 requestId 用于网络回包，taskId 用于任务生命周期，两者不是一回事。
```

### 第22课：任务查询与任务管理服务

目标：

- 按 `taskId` 查询任务详情
- 按状态过滤任务
- 列出所有任务
- 暴露任务耗时、Worker、失败原因

核心类：

```text
TaskQueryService
TaskDetailView
TaskSummaryView
```

完成标准：

```text
不用看日志，也能通过 Java API 查询任务状态和结果。
```

面试价值：

```text
Runtime 不是只会转发请求，而是能管理任务生命周期。
```

### 第23课：任务超时、取消与终态保护

目标：

- 区分 RPC 超时和任务超时
- 任务超时进入 `TIMEOUT`
- 支持取消未完成任务
- 终态任务不能被后到 Worker 结果覆盖

核心类：

```text
TaskTimeoutManager
TaskStore
TaskStateMachine
```

完成标准：

```text
TIMEOUT / CANCELED / SUCCEEDED / FAILED 都是终态
终态任务不能再次 complete
后到结果只能记录日志，不能改状态
```

面试价值：

```text
能讲清楚分布式系统中“晚到结果”和“状态幂等”的问题。
```

### 第24课：任务级重试与故障转移

目标：

- Worker 执行失败后换节点重试
- 使用 attemptedWorkers 排除失败节点
- 限制最大重试次数
- 区分可重试失败和不可重试失败

核心类：

```text
TaskRetryPolicy
TaskScheduler.retry
TaskMetadata.attemptedWorkers
```

完成标准：

```text
worker-A 返回 FAILED 后，Controller 可以把任务转发给 worker-B
超过最大重试次数后任务进入 FAILED
每次尝试都有记录
```

面试价值：

```text
这就是 Agent tool call / code execution 失败后的 failover 基础。
```

## 六、阶段二：RPC 与连接治理补强

目标：回头补强底层通信，避免后续所有高级能力被通信层拖垮。

### 第25课：RPC 全链路复盘与语义清理

目标：

- 梳理 `RpcProxy -> RpcClient -> Controller -> Worker -> RpcDispatcher -> RpcResponse`
- 画清楚 `requestId` 生命周期
- 清理注释中把 RPC 请求叫成任务请求的混乱语义
- 规划 `TASK_REQUEST / TASK_RESPONSE` 到 `RPC_REQUEST / RPC_RESPONSE` 的迁移

核心内容：

```text
requestId lifecycle
pendingRequests
pendingClients
RPC message boundary
Task message boundary
```

完成标准：

```text
不用看代码，也能讲清楚一次 RPC 调用从动态代理到响应返回的完整链路。
```

### 第26课：RPC 超时、pending 清理与错误语义

目标：

- RPC 超时后清理 pendingRequests
- Controller 转发超时后清理 pendingClients
- 补充错误码和异常类型
- 避免连接断开后请求无限挂起

核心类：

```text
RpcFuture
RpcClient
ServerHandler
RpcStatus / RpcErrorCode
```

完成标准：

```text
RPC 调用失败时有明确错误类型
pending map 不会泄漏
```

### 第27课：连接治理与断线重连

目标：

- 实现连接健康检查
- 实现断线重连策略
- 区分单连接多路复用和多连接池
- 连接关闭时处理未完成请求

核心类：

```text
ConnectionManager
ReconnectPolicy
ChannelHolder
```

完成标准：

```text
连接断开后不会无限等待
重连后可以继续发送任务或 RPC
```

面试价值：

```text
能讲清楚长连接生命周期，而不是只会用 Netty 发消息。
```

### 第28课：限流、熔断与重试接入主链路

目标：

- 把限流器接入 RPC 或任务提交入口
- 把熔断器接入 Worker 选择和失败记录
- 明确重试发生在 RPC 层还是任务层

核心类：

```text
CircuitBreakerManager
TokenBucketRateLimiter
SlidingWindowRateLimiter
TaskRetryPolicy
```

完成标准：

```text
限流、熔断、重试不是孤立类，而是真正影响请求链路。
```

## 七、阶段三：异构 Worker 与执行背压

目标：让 Worker 不再只是“能执行”，而是能表达资源、容量和负载。

### 第29课：Worker 资源模型与心跳上报

目标：

- 扩展 Worker 静态资源
- 支持 CPU、GPU 类型、显存、标签
- Worker 心跳上报动态负载
- Controller 更新资源快照

核心类：

```text
WorkerResource
WorkerLoadSnapshot
ServiceInstance
Heartbeat payload
```

完成标准：

```text
Controller 能看到每个 Worker 的资源和负载。
```

### 第30课：资源感知调度器

目标：

- TaskRequest 增加资源需求
- 根据 GPU 类型、显存、标签筛选 Worker
- 候选 Worker 中继续使用负载均衡策略

核心类：

```text
ResourceRequirement
WorkerResourceMatcher
ResourceAwareTaskScheduler
```

完成标准：

```text
需要特定资源的任务不会被调度到不匹配 Worker。
```

### 第31课：Worker 本地队列与背压

目标：

- Worker 不再无限接收任务
- 增加本地执行队列
- 支持最大并发数和队列长度
- 队列满时返回明确拒绝

核心类：

```text
WorkerTaskQueue
WorkerCapacity
BackpressurePolicy
RejectedTaskResult
```

完成标准：

```text
Worker 满载时会拒绝任务
Controller 能识别过载并调度其他 Worker
```

面试价值：

```text
这是大厂后端非常看重的容量治理能力。
```

### 第32课：节点下线与任务补偿

目标：

- Worker 下线时清理节点映射
- 处理下线 Worker 上的运行中任务
- 对可重试任务触发重新调度
- 对不可恢复任务标记失败

核心类：

```text
DeadNodeDetector
NodeChannelMap
TaskStore
TaskScheduler
```

完成标准：

```text
Worker 异常断开不会让任务永久卡在 RUNNING。
```

### 第33课：端到端集群集成测试

目标：

- 启动 1 个 Controller
- 启动多个 Worker
- 批量提交任务
- 模拟 Worker 失败、满载、恢复
- 验证重试和故障转移

核心内容：

```text
ClusterIntegrationTest
FailoverIntegrationTest
DemoLauncher
```

完成标准：

```text
一条命令能跑出完整调度演示。
```

## 八、阶段四：对外 API、流式事件和观测

目标：让系统从 Java 内部 demo 变成可被外部使用的 Runtime。

### 第34课：Controller HTTP API

目标：

- 提交任务
- 查询任务
- 查询 Worker
- 查询基础指标

建议接口：

```text
POST /api/tasks
GET  /api/tasks/{taskId}
GET  /api/tasks?status=RUNNING
GET  /api/workers
GET  /api/metrics
```

完成标准：

```text
不用 Java Client，也能通过 HTTP 使用 HeteroMesh。
```

### 第35课：SSE 流式事件

目标：

- 任务提交后可以订阅事件流
- 推送 DISPATCHING / RUNNING / SUCCEEDED / FAILED / TIMEOUT
- 后续 Agent step 可以复用同一套事件机制

建议接口：

```text
GET /api/tasks/{taskId}/events
```

完成标准：

```text
Client 能实时看到任务状态变化。
```

面试价值：

```text
Agent 执行通常需要流式输出，SSE 是非常自然的接口形态。
```

### 第36课：指标系统与 Trace

目标：

- 记录任务总数、成功数、失败数、超时数
- 记录平均耗时、P95、P99
- 记录每个 Worker 的任务数、失败数、队列长度
- 为每个任务保留执行 trace

核心类：

```text
MetricsRegistry
TaskMetrics
WorkerMetrics
TaskTrace
```

完成标准：

```text
能用指标证明系统稳定性，而不是只靠口头描述。
```

### 第37课：轻量 Dashboard

目标：

- 展示 Worker 列表
- 展示任务列表
- 展示任务状态统计
- 支持提交 demo 任务

完成标准：

```text
打开页面就能看到集群状态和任务流转。
```

说明：

```text
Dashboard 是展示工具，不是主线。不要在核心调度完成前过早投入太多。
```

## 九、阶段五：轻量 AI / Agent 执行场景

目标：只做足够证明项目和 Agent Runtime 有关的场景，不做复杂 Agent 框架。

### 第38课：AgentRun / AgentStep / ToolCall 模型

目标：

- 增加 AgentRun 表示一次 Agent 执行
- 增加 AgentStep 表示一次推理或工具调用步骤
- 增加 ToolCall / ToolResult 表示工具执行
- AgentStep 可以映射成 TaskRequest 调度到 Worker

核心类：

```text
AgentRun
AgentStep
ToolCall
ToolResult
AgentRunStore
```

完成标准：

```text
一个 AgentRun 可以包含多个 AgentStep
每个 AgentStep 都能复用现有任务调度链路
```

面试价值：

```text
能讲清楚 Agent Runtime 和普通任务调度系统的关系。
```

### 第39课：LLM_TASK 执行器

目标：

- Worker 支持一种 `LLM_TASK`
- 可选接入 Ollama 或 OpenAI API
- Controller 不关心具体模型调用细节，只调度任务

核心类：

```text
LlmTaskExecutor
LlmProvider
OllamaProvider
OpenAiProvider
```

完成标准：

```text
提交一个 prompt，Worker 调用模型并返回文本结果。
```

说明：

```text
LLM 接入只是应用场景，不要让它吞掉后端主线。
```

### 第40课：ToolRegistry 与 TOOL_TASK

目标：

- Worker 支持工具注册
- 支持执行 HTTP tool / file tool / simple shell tool
- 每个工具有超时和错误语义

核心类：

```text
ToolRegistry
ToolExecutor
ToolSpec
ToolTaskExecutor
```

完成标准：

```text
AgentStep 可以触发一次工具调用，并拿到 ToolResult。
```

### 第41课：执行权限与最小沙箱

目标：

- 限制 shell tool 的命令范围
- 限制工作目录
- 限制执行超时
- 记录执行日志

核心类：

```text
ExecutionPolicy
SandboxedCommandExecutor
ToolPermission
```

完成标准：

```text
工具执行不是裸奔，有最小权限控制和超时保护。
```

面试价值：

```text
Agent 能调用工具之后，权限和隔离会立刻变成核心问题。
```

### 第42课：最小 Agent Runtime Demo

目标：

- 创建一个 AgentRun
- 第一步调用 LLM_TASK 生成计划
- 第二步调用 TOOL_TASK 执行工具
- 第三步汇总结果
- SSE 返回每一步事件

完成标准：

```text
能演示一次简单 Agent 执行流，但核心卖点仍然是后端 Runtime。
```

## 十二、最终演示目标

最终项目应该能演示：

```text
1. 启动 Controller
2. 启动多个 Worker
3. Worker 自动注册并上报资源
4. 通过 HTTP 提交任务
5. Controller 根据资源和负载选择 Worker
6. Worker 执行任务并返回结果
7. SSE 实时推送任务状态
8. 查询任务详情和 Worker 状态
9. 模拟 Worker 失败，任务自动重试或故障转移
10. 模拟 Worker 满载，触发背压和重新调度
```
