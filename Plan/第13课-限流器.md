## 一、这节课解决什么问题？

### 1.1 当前问题

```
Controller 没有流量控制，Client 发多少就转发多少：

Client-1: 100 req/s
Client-2: 200 req/s
Client-3: 100 req/s
         ↓
     Controller ──400 req/s──→ Worker（只能处理 200 req/s）
                                  ↓
                              过载 → 超时 → 熔断 → 恢复 → 又过载

限流器就是在 Controller 上加一个阀门：超过 200 req/s 的请求直接拒绝，不让 Worker 过载。
```

### 1.2 这节课后的效果

```java
// Worker 注册时声明能力：「我能处理 200 QPS」
// Controller 为每个 Worker 创建一个限流器

// Client 请求到达 Controller → 先过限流器
if (rateLimiter.tryAcquire()) {
    // 放行 → 转发到 Worker
} else {
    // 拒绝 → 返回限流错误给 Client
    ctx.writeAndFlush(createErrorResponse("请求过于频繁，请稍后再试"));
}
```

### 1.3 两种算法

| 算法 | 原理 | 突发流量 | 实现复杂度 |
|------|------|---------|-----------|
| **令牌桶** | 按固定速率往桶里放令牌，请求拿到令牌才放行 | ✅ 支持 | 中 |
| **滑动窗口** | 把 1 秒切成 N 个小格，统计当前+过去格子的总量 | ⚠️ 有限支持 | 中 |

## 二、令牌桶算法

### 2.1 原理

```
  ┌──────────────────────────────────────┐
  │                                      │
  │   每秒放 200 个令牌                    │
  │       ↓                              │
  │  ┌─────────┐                         │
  │  │ 🎫🎫🎫🎫 │  ← 桶容量 200（满了丢弃） │
  │  └────┬────┘                         │
  │       │                              │
  │   请求来拿令牌                          │
  │   ├─ 桶里有 → 拿走，放行                │
  │   └─ 桶里没 → 拒绝                     │
  └──────────────────────────────────────┘
```

**突发流量**：如果一段时间没有请求，令牌攒满 200 个。突然来一波流量，可以瞬间消耗掉全部 200 个令牌——这就是「支持突发」。

### 2.2 实现（不用后台线程）

参考 Guava RateLimiter 的惰性填充思想——不是在后台线程里定时放令牌，而是**每次请求时计算「从上一次到现在过了多久，该放多少个令牌」**：

```java
public class TokenBucketRateLimiter {
    private final long capacity;                // 桶容量
    private final double refillRatePerMs;       // 每毫秒生成多少个令牌
    private double availableTokens;             // 当前可用令牌数
    private long lastRefillTime;               // 上次填充时间

    public synchronized boolean tryAcquire() {
        refill();                               // 先补令牌
        if (availableTokens < 1) return false;
        availableTokens--;
        return true;
    }

    private void refill() {
        long now = System.currentTimeMillis();
        long elapsed = now - lastRefillTime;
        availableTokens = Math.min(capacity, availableTokens + elapsed * refillRatePerMs);
        lastRefillTime = now;
    }
}
```

**例子**：容量 200，速率 200/s = 0.2/ms。100ms 没请求 → 补 20 个令牌。500ms 没请求 → 补 100 个。

## 三、滑动窗口算法

### 3.1 原理

把 1 秒的时间线切成 N 个小格（如 10 格，每格 100ms）。每个格子里记一个计数器。判断是否限流时，把最近 10 个格子的计数加起来。

```
1 秒窗口，10 个格子：
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│12│8 │15│10│5 │3 │20│7 │9 │11│  ← 每个格子 100ms 的通过请求数
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  ←─ t-1000ms ──── t-100ms ─→  t
            总和 = 100
    如果阈值 = 80 → 超过 → 拒绝
```

**优势**：避免固定窗口的「临界突刺」——固定窗口在 0.9s~1.1s 区间可能通过 2 倍流量，滑动窗口天然平滑。

### 3.2 实现（环形数组）

参考 Sentinel 的 `LeapArray` 设计——用环形数组避免频繁创建/销毁格子对象：

```java
public class SlidingWindowRateLimiter {
    private final int windowCount;          // 格子数量（如 10）
    private final long windowLengthMs;      // 每个格子的时长（如 100ms）
    private final long intervalMs;          // 总窗口时长 = windowCount * windowLengthMs
    private final long[] counters;          // 环形数组
    private final long[] timestamps;        // 每个格子对应的时间戳（窗口起始时间）
    private final long maxRequests;         // 阈值

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        long currentWindowStart = now - (now % windowLengthMs); // 当前格子的起始时间

        int total = 0;
        for (int i = 0; i < windowCount; i++) {
            // 过期格子重置
            if (now - timestamps[i] > intervalMs) {
                counters[i] = 0;
                timestamps[i] = currentWindowStart;
            }
            total += counters[i];
        }

        if (total >= maxRequests) return false;

        // 找到当前格子的位置并 +1
        int idx = (int) ((currentWindowStart / windowLengthMs) % windowCount);
        if (timestamps[idx] != currentWindowStart) {
            timestamps[idx] = currentWindowStart;
            counters[idx] = 0;
        }
        counters[idx]++;
        return true;
    }
}
```

注意：这只是一个说人话的教学版实现。Sentinel 生产版用了 `LongAdder` + CAS + ReentrantLock 做并发优化，这里用 `synchronized` 足够。

### 4.3 集成（选做，不做也 OK）

两种方式二选一：

**方式 A**：在 `tryForward` 开头加一个限流检查，超过阈值直接返回拒绝响应。

**方式 B**：把限流器实现为 `RpcInterceptor`，插入 Worker 的拦截器链——这是最优雅的做法，因为跟第 10 课的拦截器架构完美结合。

本课不用必须集成到 Controller——写出两个限流器类 + 跑通测试就算完成。下一课连接池会跟 Controller 有更紧密的集成。

## 六、常见错误预警

### 错误 1：令牌桶不用 volatile/synchronized

```java
// ❌ 多线程下 availableTokens 可能读到脏数据
private double availableTokens;
public boolean tryAcquire() { ... }

// ✅ 最简单的是 synchronized，单机限流够用
public synchronized boolean tryAcquire() { ... }
```

### 错误 2：滑动窗口格子数量太多或太少

```
❌ windowCount=2  → 格子太大，退化成固定窗口，有临界问题
❌ windowCount=100 → 格子太小，频繁创建/重置，性能差
✅ windowCount=10 → 100ms 一个格子，精度和性能平衡
```

### 错误 3：令牌桶容量小于速率

```java
// ❌ 速率 200/s 但桶容量 50 → 攒再多令牌也只能突 50 个
new TokenBucketRateLimiter(200/s, capacity=50);

// ✅ 容量 ≈ 速率，支持 1 秒的突发
new TokenBucketRateLimiter(200/s);  // capacity = 200
```
