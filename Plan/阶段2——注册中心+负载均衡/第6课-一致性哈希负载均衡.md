## 一、这节课解决什么问题？

### 当前状态 vs 目标

```
当前（第 5 课后）：
  Client ──TASK_REQUEST──→ Controller ──"成功收到消息"──→ Client
                                                           ↑
                                             Controller 自己回了，Worker 根本没参与

这节课后：
  Client ──TASK_REQUEST──→ Controller
                              │
                              │ ① 取 requestId，一致性哈希算出该分给谁
                              │ ② 从 NodeChannelMap 取出 Worker 的 Channel
                              │ ③ 把 TASK_REQUEST 转发过去
                              │
              Worker-A ←──────┘
                │
                │ 处理任务
                │
              Controller ←── TASK_RESPONSE ──→ Client
                             （原路返回）
```

### 为什么不能用简单的 `hash(nodeId) % n`？

```
假设 3 个 Worker：A、B、C
taskId = "img-001" → hash % 3 = 1 → Worker B ✓

现在 Worker B 宕机了，n 从 3 变成 2：
taskId = "img-001" → hash % 2 = 0 → Worker A ✗ （之前分给 B 的！）

→ 扩容/缩容时，几乎 100% 的映射关系都变了
→ 如果有状态任务（同一个 taskId 必须去同一个 Worker），缓存全部失效
```

一致性哈希解决的就是这个问题：**节点上下线时，只有少部分 key 的映射关系会变。**

## 二、一致性哈希原理

### 2.1 哈希环

把哈希值空间组织成一个环，范围 `[0, 2^31-1]`（Java int 的正数范围）：

```
                    0
                   / \
                  /   \
                 /     \
        2^31-1  /       \  哈希值从小到大顺时针排列
                \       /
                 \     /
                  \   /
                   \ /
                    ...
```

### 2.2 虚拟节点

物理节点 A 在环上只有 1 个位置 → 分布不均匀，A 可能只覆盖 5% 的 key。

解决办法：每个物理节点映射 150 个虚拟节点，均匀散布在环上。

```
物理节点 worker-gpu-01：
  虚拟节点 0："worker-gpu-01#0"   → hash → 环上位置 p0
  虚拟节点 1："worker-gpu-01#1"   → hash → 环上位置 p1
  ...
  虚拟节点 149："worker-gpu-01#149" → hash → 环上位置 p149
```

### 2.3 路由规则

```
给定 taskId：
  1. hash = hash(taskId)    // 算出 taskId 在环上的位置
  2. 顺时针找到第一个 ≥ hash 的虚拟节点
  3. 该虚拟节点对应的物理节点 = 目标 Worker
  4. 如果超过环的最大值（找不到）→ 取环上第一个节点（回到起点）
```

**为什么选 `TreeMap`？**
- `TreeMap.ceilingEntry(hash)` 天然支持「找 ≥ hash 的最小 key」— O(log n)
- `TreeMap.firstEntry()` 支持回环
- `HashMap` 没有顺序，做不到顺时针查找

### 2.4 节点增减的影响

```
新增 Worker-D：只在环上插入 150 个虚拟节点
  → 只影响紧挨着这 150 个位置的 key（理论上 150 / 总虚拟节点数 的比例）
  → 3 个节点 × 150 = 450 个虚拟节点，加一个节点影响约 150/600 = 25% 的 key

移除 Worker-B：从环上删除 150 个虚拟节点
  → 同样只影响约 25% 的 key
```

对比取模：3→4 节点扩容，`%3` 换 `%4`，**75%** 的映射关系会变。

### 3.1 LoadBalancer 接口（~15 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/loadbalancer/LoadBalancer.java`

```java
package com.heteromesh.loadbalancer;

import com.heteromesh.registry.ServiceInstance;

/**
 * 负载均衡器接口
 * 内部维护哈希环，节点上下线时调用 addNode/removeNode
 */
public interface LoadBalancer {

    /**
     * 节点上线时调用：把节点加入哈希环
     */
    void addNode(ServiceInstance instance);

    /**
     * 节点下线时调用：从哈希环移除节点的所有虚拟节点
     */
    void removeNode(String nodeId);

    /**
     * 根据 key（如 requestId）选择一个节点
     * @return 选中的 ServiceInstance，没有可用节点时返回 null
     */
    ServiceInstance select(String key);

    /**
     * 当前哈希环上有多少个物理节点
     */
    int size();
}
```

**为什么内部维护状态而不是每次 select 时重建？**

```java
// ❌ 无状态方案：每次 select 都重建 TreeMap
ServiceInstance select(List<ServiceInstance> nodes, String key) {
    TreeMap<Integer, ServiceInstance> ring = new TreeMap<>();
    for (ServiceInstance node : nodes) {
        for (int i = 0; i < 150; i++) {
            ring.put(hash(node.getNodeId() + "#" + i), node);
        }
    }
    // ... 查找
}
// → 每次 select 都 O(n × 150) 重建，高频调用时性能差

// ✅ 有状态方案：节点变化时增量更新
addNode(instance);    // 注册时插入 150 个虚拟节点
removeNode(nodeId);   // 下线时删除 150 个虚拟节点
select(key);          // 直接查 TreeMap，O(log n)
// → 增删低频，查找高频——各走各的复杂度
```

### 3.2 ConsistentHashLoadBalancer（核心，~80 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/loadbalancer/ConsistentHashLoadBalancer.java`

```java
package com.heteromesh.loadbalancer;

import com.heteromesh.registry.ServiceInstance;
import lombok.extern.slf4j.Slf4j;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.ConcurrentHashMap;

@Slf4j
public class ConsistentHashLoadBalancer implements LoadBalancer {

    // 每个物理节点对应的虚拟节点数
    private static final int VIRTUAL_NODES = 150;

    // 哈希环：hash值 → nodeId
    // TreeMap 保证 key 有序，支持 ceilingEntry（找 ≥ 给定值的最小 key）
    private final TreeMap<Integer, String> ring = new TreeMap<>();

    // nodeId → ServiceInstance（select 时根据 nodeId 拿到完整信息）
    private final Map<String, ServiceInstance> nodes = new ConcurrentHashMap<>();

    // ---------- 哈希函数 ----------

    /**
     * 用 MD5 对 key 取哈希，取低 32 位转为 int 正数
     * 为什么用 MD5 而不是 key.hashCode()？
     * - String.hashCode() 分布不够均匀，某些 pattern 会导致热点
     * - MD5 是密码学哈希，任意输入的分布都非常均匀
     */
    private int hash(String key) {
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            byte[] digest = md.digest(key.getBytes(StandardCharsets.UTF_8));
            // 取前 4 个字节，拼成 int，& 0x7FFFFFFF 确保是正数
            int h = ((digest[3] & 0xFF) << 24)
                  | ((digest[2] & 0xFF) << 16)
                  | ((digest[1] & 0xFF) << 8)
                  | ((digest[0] & 0xFF));
            return h & 0x7FFFFFFF;
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException("MD5 not available", e);
        }
    }

    // ---------- 节点管理 ----------

    @Override
    public void addNode(ServiceInstance instance) {
        String nodeId = instance.getNodeId();

        // ① 存储物理节点信息（后续 select 时拿完整对象）
        nodes.put(nodeId, instance);

        // ② 在环上插入 150 个虚拟节点
        for (int i = 0; i < VIRTUAL_NODES; i++) {
            String virtualKey = nodeId + "#" + i;
            int h = hash(virtualKey);
            ring.put(h, nodeId);
        }

        log.info("节点加入哈希环: nodeId={}, virtualNodes={}, ringSize={}",
                nodeId, VIRTUAL_NODES, ring.size());
    }

    @Override
    public void removeNode(String nodeId) {
        // ① 删除物理节点
        nodes.remove(nodeId);

        // ② 从环上删除该节点的所有虚拟节点
        //    注意：不能用 ring.values().removeIf(...)，因为要遍历 150 个 key
        //    直接遍历所有虚拟节点 key，逐个 remove
        for (int i = 0; i < VIRTUAL_NODES; i++) {
            String virtualKey = nodeId + "#" + i;
            int h = hash(virtualKey);
            ring.remove(h);
        }

        log.info("节点离开哈希环: nodeId={}, remainingRingSize={}",
                nodeId, ring.size());
    }

    @Override
    public ServiceInstance select(String key) {
        if (ring.isEmpty()) {
            return null;
        }

        int h = hash(key);

        // 顺时针找第一个 ≥ h 的虚拟节点
        Map.Entry<Integer, String> entry = ring.ceilingEntry(h);
        if (entry == null) {
            // 超过环上最大值 → 回到环起点（第一个节点）
            entry = ring.firstEntry();
        }

        String nodeId = entry.getValue();
        return nodes.get(nodeId);
    }

    @Override
    public int size() {
        return nodes.size();
    }
}
```

#### 关键代码解释

**① `ring.ceilingEntry(h)` 是什么？**

```java
// TreeMap 提供了两个关键方法：
// ceilingEntry(K key)：返回 key ≥ 给定值的、最小的那个条目。没有则返回 null。
// firstEntry()：返回 key 最小的条目。

// 例：环上有 [100, 300, 500] 三个位置
// ceilingEntry(150) → 300（顺时针第一个 ≥ 150 的）
// ceilingEntry(600) → null（超过了所有位置）→ firstEntry() → 100（回环）
```

**② 为什么用 MD5 而不是 `String.hashCode()`？**

```java
// String.hashCode() 的公式：s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]
// 对于相似字符串（如 "task-001", "task-002", "task-003"），hashCode 值可能很接近
// 导致任务集中在环上某一小段 → 某些 Worker 被打满

// MD5 是密码学哈希：输入改变 1 bit，输出变化约 50% 的 bit（雪崩效应）
// 保证 taskId 均匀分布在环上
```

**③ `& 0x7FFFFFFF` 是干什么？**

```java
// Java 的 int 是有符号的（-2^31 ~ 2^31-1）
// MD5 前 4 字节的最高位可能是 1 → int 变成负数
// TreeMap.ceilingEntry() 按自然顺序排列，负数在正数前面 → 环的逻辑混乱

// & 0x7FFFFFFF 去掉符号位 → 保证 hash 值在 [0, 2^31-1] 范围内
```

### 3.3 ServerHandler 改造：任务转发

位置：`heteromesh-controller/src/main/java/com/heteromesh/controller/ServerHandler.java`

改造点：
- 构造函数新增 `LoadBalancer` 参数
- `handleRegister` 中注册成功后调用 `loadBalancer.addNode()`
- `channelInactive` 中调用 `loadBalancer.removeNode()`
- `TASK_REQUEST` 不再自己 echo，改为一致性哈希选 Worker → 转发
- 新增 `TASK_RESPONSE`（从 Worker 回来的响应）→ 回传给原始客户端

```java
package com.heteromesh.controller;

import com.heteromesh.controller.node.NodeChannelMap;
import com.heteromesh.loadbalancer.LoadBalancer;
import com.heteromesh.protocol.Message;
import com.heteromesh.protocol.MessageType;
import com.heteromesh.registry.ServiceInstance;
import com.heteromesh.registry.ServiceRegistry;
import com.google.gson.Gson;
import io.netty.channel.Channel;
import io.netty.channel.ChannelHandlerContext;
import io.netty.channel.SimpleChannelInboundHandler;
import lombok.extern.slf4j.Slf4j;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Slf4j
public class ServerHandler extends SimpleChannelInboundHandler<Message> {

    private final ServiceRegistry registry;
    private final NodeChannelMap nodeChannelMap;
    private final LoadBalancer loadBalancer;

    // requestId → 原始客户端 Channel（用于 Worker 回复后回传）
    // 场景：Client 发 TASK_REQUEST 给 Controller，Controller 转发给 Worker
    //       Worker 回复 TASK_RESPONSE → 需要知道回传给哪个 Client
    private final Map<String, Channel> pendingClients = new ConcurrentHashMap<>();

    public ServerHandler(ServiceRegistry registry,
                         NodeChannelMap nodeChannelMap,
                         LoadBalancer loadBalancer) {
        this.registry = registry;
        this.nodeChannelMap = nodeChannelMap;
        this.loadBalancer = loadBalancer;
    }

    @Override
    protected void channelRead0(ChannelHandlerContext ctx, Message msg) {
        // 任何消息到达都更新心跳时间（来自第 5 课）
        updateHeartbeat(ctx);

        switch (msg.getType()) {
            case REGISTER      -> handleRegister(ctx, msg);
            case TASK_REQUEST  -> handleTaskRequest(ctx, msg);
            case TASK_RESPONSE -> handleTaskResponse(ctx, msg);
            default -> {} // PING/PONG 只更新心跳，不需要额外处理
        }
    }

    // ==================== 心跳 ====================

    private void updateHeartbeat(ChannelHandlerContext ctx) {
        String nodeId = nodeChannelMap.getNodeId(ctx.channel());
        if (nodeId != null) {
            ServiceInstance node = registry.lookup(nodeId);
            if (node != null) {
                node.setLastHeartbeat(System.currentTimeMillis());
            }
        }
    }

    // ==================== 注册 ====================

    private void handleRegister(ChannelHandlerContext ctx, Message msg) {
        ServiceInstance instance = new Gson().fromJson(msg.getBody(), ServiceInstance.class);

        // ① 存入注册中心
        registry.register(instance);
        log.info("节点注册成功: nodeId={}, gpuType={}, vramFree={}MB",
                instance.getNodeId(), instance.getGpuType(), instance.getVramFree());

        // ② 绑定 nodeId ↔ Channel
        nodeChannelMap.bind(instance.getNodeId(), ctx.channel());

        // ③ 加入一致性哈希环（新增！）
        loadBalancer.addNode(instance);

        // ④ 回复 ACK
        Message ack = Message.createAck(msg.getRequestId(), instance.getNodeId());
        ctx.writeAndFlush(ack);
    }

    // ==================== 任务转发（核心改动） ====================

    private void handleTaskRequest(ChannelHandlerContext ctx, Message msg) {
        String requestId = msg.getRequestId();

        // ① 一致性哈希：算出这个任务该分给哪个 Worker
        ServiceInstance target = loadBalancer.select(requestId);

        if (target == null) {
            // 没有可用 Worker
            log.warn("无可用节点处理任务: requestId={}", requestId);
            Message reply = Message.createTaskResponse(requestId, "无可用节点");
            ctx.writeAndFlush(reply);
            return;
        }

        // ② 从 NodeChannelMap 拿到目标 Worker 的 Channel
        Channel workerChannel = nodeChannelMap.getChannel(target.getNodeId());
        if (workerChannel == null || !workerChannel.isActive()) {
            log.warn("目标 Worker Channel 不可用: nodeId={}", target.getNodeId());
            Message reply = Message.createTaskResponse(requestId, "目标节点离线");
            ctx.writeAndFlush(reply);
            return;
        }

        // ③ 记录 requestId → 原始客户端 Channel（Worker 回复后要用）
        pendingClients.put(requestId, ctx.channel());

        // ④ 转发 TASK_REQUEST 到选中的 Worker
        workerChannel.writeAndFlush(msg);
        log.info("任务转发: requestId={} → Worker[{}]", requestId, target.getNodeId());
    }

    // ==================== Worker 回复回传 ====================

    private void handleTaskResponse(ChannelHandlerContext ctx, Message msg) {
        // Worker 处理完了任务，把 TASK_RESPONSE 发回了 Controller
        // Controller 需要把这个响应回传给最初发 TASK_REQUEST 的 Client

        String requestId = msg.getRequestId();
        Channel clientChannel = pendingClients.remove(requestId);

        if (clientChannel != null && clientChannel.isActive()) {
            clientChannel.writeAndFlush(msg);
            log.debug("响应回传: requestId={} → Client", requestId);
        } else {
            log.warn("找不到原始客户端或已断开: requestId={}", requestId);
        }
    }

    // ==================== 断连清理 ====================

    @Override
    public void channelInactive(ChannelHandlerContext ctx) {
        String nodeId = nodeChannelMap.getNodeId(ctx.channel());
        if (nodeId != null) {
            registry.unregister(nodeId);
            loadBalancer.removeNode(nodeId);  // ← 新增：从哈希环移除
            log.warn("节点断开连接: nodeId={}", nodeId);
        }
        nodeChannelMap.unbind(ctx.channel);

        // 清理该 Channel 关联的待回传请求
        pendingClients.values().removeIf(ch -> ch == ctx.channel());
    }
}
```

#### 为什么需要一个 `pendingClients` Map？

```
时序：
  1. Client-A 发 TASK_REQUEST(requestId="r1") → Controller
  2. Controller LB 选到 Worker-B，记录 pendingClients["r1"] = Client-A 的 Channel
  3. Controller 转发 TASK_REQUEST → Worker-B
  4. Worker-B 处理完，发 TASK_RESPONSE(requestId="r1") → Controller
  5. Controller 看到 TASK_RESPONSE，查 pendingClients["r1"] → 拿到 Client-A 的 Channel
  6. Controller 把响应发还给 Client-A

不记这个映射的话，第 5 步 Controller 收到 Worker 的响应时，
根本不知道最初是谁发起的请求——消息里只有 requestId，没有客户端标识。
```

`DeadNodeDetector` 构造函数和 `scan()` 方法的改动：

```java
// DeadNodeDetector.java 改动：

public class DeadNodeDetector {
    private final ServiceRegistry registry;
    private final NodeChannelMap nodeChannelMap;
    private final LoadBalancer loadBalancer;  // ← 新增
    private final long timeoutMs;
    // ...

    public DeadNodeDetector(ServiceRegistry registry,
                            NodeChannelMap nodeChannelMap,
                            LoadBalancer loadBalancer,  // ← 新增
                            long timeoutMs) {
        this.registry = registry;
        this.nodeChannelMap = nodeChannelMap;
        this.loadBalancer = loadBalancer;
        this.timeoutMs = timeoutMs;
    }

    private void scan() {
        List<ServiceInstance> instances = registry.getAllInstances();
        long now = System.currentTimeMillis();

        for (ServiceInstance node : instances) {
            if (!node.isAlive(timeoutMs)) {
                log.warn("节点心跳超时, 踢出: nodeId={}, lastHeartbeat={}ms ago",
                        node.getNodeId(), now - node.getLastHeartbeat());

                registry.unregister(node.getNodeId());
                loadBalancer.removeNode(node.getNodeId());  // ← 新增：从哈希环移除

                Channel channel = nodeChannelMap.getChannel(node.getNodeId());
                if (channel != null && channel.isActive()) {
                    channel.close();
                }
                nodeChannelMap.unbind(channel);
            }
        }
    }
}
```

## 六、常见错误预警

### 错误 1：哈希值包含负数

```java
// ❌ 直接用 MD5 前 4 字节拼成 int
int h = ((digest[3] & 0xFF) << 24) | ...;
return h;  // 最高位可能是 1 → 负数

// → TreeMap 自然顺序：负数 < 正数，环变两截：
// [-2^31, -1] 和 [0, 2^31-1]，选节点逻辑全乱

// ✅ 去掉符号位
return h & 0x7FFFFFFF;
```

### 错误 2：`removeNode` 忘了删虚拟节点

```java
// ❌ 只删了 nodes map
public void removeNode(String nodeId) {
    nodes.remove(nodeId);
    // ring 里还残留 150 个虚拟节点！
}
// → select 选中了这个已下线的节点 → 拿到 null → NPE

// ✅ 同时清理 ring
public void removeNode(String nodeId) {
    nodes.remove(nodeId);
    for (int i = 0; i < VIRTUAL_NODES; i++) {
        ring.remove(hash(nodeId + "#" + i));
    }
}
```

### 错误 3：`select` 返回 null 时没判断

```java
// ❌ 直接使用 select 的返回值
ServiceInstance target = loadBalancer.select(requestId);
Channel ch = nodeChannelMap.getChannel(target.getNodeId());
// → ring 空时 select 返回 null → NPE

// ✅ 先判空
ServiceInstance target = loadBalancer.select(requestId);
if (target == null) {
    // 返回错误给客户端
    return;
}
```

### 错误 4：忘记在 `handleRegister` 里调 `addNode`

```java
// 注册成功 → 存了 registry → 绑了 NodeChannelMap → 发了 ACK
// 但忘了 loadBalancer.addNode(instance)
// → 哈希环一直是空的 → select 永远返回 null → 所有任务都"无可用节点"
```

### 错误 5：PendingClients 内存泄漏

```java
// Client 发 TASK_REQUEST → pendingClients.put(requestId, channel)
// Worker 挂了没回 TASK_RESPONSE → pendingClients.remove(requestId) 永远不会被调用
// → requestId → channel 这条记录永远残留在 map 里

// 短期：测试场景不用管
// 长期：需要一个定时任务扫 pendingClients，清理超时请求（后续课会做）
```

### 错误 6：重复 `removeNode`

```java
// Worker 正常断连：
// ① channelInactive 触发 → loadBalancer.removeNode()
// ② DeadNodeDetector.scan() 还能看到这个节点（registry 还没清）
//    → isAlive(false) → 又调了一次 removeNode()
//
// → 问题不大（removeNode 是幂等的，ring.remove() 删不存在的 key 不报错）
// 但日志里会出现两次"节点离开哈希环"，看起来像 bug
//
// 解决方案：DeadNodeDetector 里先检查 ring 里是否还有该节点
```

## 七、复习问题

1. 为什么不能直接用 `taskId.hashCode() % workerCount` 来分配任务？一致性哈希解决了什么问题？
2. 虚拟节点是什么？为什么需要 150 个而不是 1 个？
3. `TreeMap.ceilingEntry()` 在一致性哈希中起什么作用？换成 `HashMap` 行不行？
4. 哈希函数为什么选 MD5 而不是 `String.hashCode()`？`& 0x7FFFFFFF` 是干什么的？
5. `LoadBalancer` 为什么设计成有状态的（内部维护 ring），而不是每次 select 都重建？
6. `pendingClients` Map 是干什么的？没有它会怎样？
7. 节点注册时哪些地方需要更新？（提示：4 个地方——registry、NodeChannelMap、LoadBalancer、ACK）
8. 节点下线时哪些地方需要清理？（提示：3 个地方——registry、NodeChannelMap、LoadBalancer）
9. 一致性哈希下，新增一个节点大约影响百分之多少的 key 映射？（算一下：n 个节点各 150 虚拟节点）
10. 如果 MD5 不可用（`NoSuchAlgorithmException`），会发生什么？有没有替代方案？

### 参考答案

**1. 取模 vs 一致性哈希？**

取模 `hash % n` 的问题在于 n 变了（节点上下线），几乎全部映射关系都变了。一致性哈希用环 + 顺时针查找，节点变化只影响相邻的一小段。打个比方：取模是「把扑克牌重新洗牌」，一致性哈希是「每个人按身高站成一圈，来了新人只影响他旁边那一段」。

**2. 虚拟节点为什么是 150 个？**

1 个物理节点 = 环上 1 个点。节点少时（比如 2 个），环被切成 2 段，长度不等的概率很大 → 负载不均。150 个虚拟节点把一个物理节点拆成 150 个点均匀散布在环上，大幅减少不均。150 不是硬性规定，Dubbo 默认 160，Nginx 默认 160。这个数字越大越均匀，但 addNode/removeNode 开销也越大。150 是个不错的平衡。

**3. `TreeMap.ceilingEntry()` vs `HashMap`？**

`ceilingEntry(h)` 返回 key ≥ h 的最小条目——这是「顺时针找下一个」的精确实现。HashMap 没有顺序，做不到。用 HashMap 的话只能遍历所有 key 手动比较，O(n) vs TreeMap O(log n)。

**4. MD5 vs hashCode？**

`String.hashCode()` 算法公开（`s[0]*31^(n-1) + ...`），相似字符串产生相似哈希值，任务会集中在环上某段。MD5 有雪崩效应（输入差 1 bit → 输出差约 50% bit），保证均匀分布。`& 0x7FFFFFFF` 去掉符号位，因为 Java int 有符号，负数扰乱环的顺序逻辑。

**5. 为什么有状态？**

节点上下线是低频事件（一分钟几次），任务路由是高频事件（每秒几万次）。把 TreeMap 维护在内存里，select 直接 O(log n) 查找。每次 select 都重建 TreeMap 的话 O(n × 150)，太浪费。

**6. pendingClients 的作用？**

Controller 是「中间人」：Client → Controller → Worker。Worker 回复 TASK_RESPONSE 时，Netty 只知道这个消息是 Worker 发来的，不知道最初哪个 Client 发的。pendingClients 用 requestId 做 key 记录了「这个请求最初来自哪个 Client Channel」，Controller 收到 Worker 响应后查表回传。这和 RpcClient 的 `pendingRequests` Map 是同一个原理。

**7. 注册时更新 4 个地方：**

| 操作 | 作用 |
|------|------|
| `registry.register(instance)` | Controller 知道有这个节点 |
| `nodeChannelMap.bind(nodeId, channel)` | 知道通过哪个 Channel 给这个节点发消息 |
| `loadBalancer.addNode(instance)` | 把节点加入哈希环（新增） |
| `ctx.writeAndFlush(ack)` | 告知 Worker 注册成功 |

**8. 下线时清理 3 个地方：**

| 操作 | 作用 |
|------|------|
| `registry.unregister(nodeId)` | 从注册中心移除 |
| `loadBalancer.removeNode(nodeId)` | 从哈希环移除（新增） |
| `nodeChannelMap.unbind(channel)` | 解除 Channel 绑定 |

**9. 新增节点影响多少 key？**

n 个节点，总虚拟节点 = n × 150。新增节点增加 150 个虚拟节点，大约 `150 / (n×150 + 150) = 1 / (n+1)` 的 key 会重新映射。3 个节点时 ≈ 25%，10 个节点时 ≈ 9%。

**10. MD5 不可用？**

MD5 是 JRE 标准库的一部分（`java.security.MessageDigest`），Java 规范要求必须提供 MD5，实际上不会不可用。如果实在担心，可以用 MurmurHash3（Guava 提供）替代，性能更好且分布同样均匀。

## 八、面试怎么聊

> "有了注册中心和心跳后，Controller 知道集群里有多少 Worker、各自什么状态。下一个问题是：任务来了该发给谁？我实现了一致性哈希负载均衡，核心是 TreeMap + 虚拟节点。"

> "每个 Worker 注册时，我在哈希环上给它创建 150 个虚拟节点——把 `nodeId + '#' + i` 用 MD5 取哈希，均匀散布在 0 到 2^31-1 的环上。任务到来时，用同样的哈希函数对 taskId 取哈希，顺时针找第一个 ≥ 它的虚拟节点，对应的物理节点就是目标 Worker。TreeMap 的 ceilingEntry 方法天然支持这个查找，O(log n)。"

> "为什么不用取模？因为分布式系统中节点上下线是常态——取模方案扩容时所有映射都乱掉，有状态任务的缓存全部失效。一致性哈希下，上下线一个节点只影响 1/(n+1) 比例的数据迁移。这跟 Redis Cluster 的哈希槽、Dubbo 的一致性哈希路由是同一个思想。"

> "虚拟节点解决的是负载不均问题——物理节点少的时候环上位置分布倾斜，某些节点分到更多 key（热点）。150 个虚拟节点把物理节点打散在环上，实际测试中 3 个节点就能达到 ±5% 以内的负载偏差。"
