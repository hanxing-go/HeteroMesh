# 第24课：任务级重试与故障转移

---

## 一、本课目标

第23课我们已经补上了任务级超时、取消和终态保护。

现在 Controller 侧已经能保证：

```text
TIMEOUT / CANCELED / SUCCEEDED / FAILED 这些终态不会被后到结果覆盖
```

但真实任务系统还有一个关键能力没有完成：

```text
Worker-A 执行失败后，任务能不能自动换到 Worker-B 再试一次？
```

本课要做的是任务级重试与故障转移。

完成后，系统应该具备：

```text
1. Worker 返回 FAILED 时，Controller 可以判断是否还允许重试
2. 重试时避开已经尝试过的 Worker
3. 成功选到新 Worker 后，Controller 重新转发 TASK_SUBMIT
4. 超过最大尝试次数后，任务进入 FAILED
5. 最终只给 Client 返回一次最终结果
```

这节课非常适合写进简历，因为它不只是“调用失败再调一次”，而是任务生命周期、负载均衡、状态机和网络转发共同协作。

---

## 二、先分清四个概念

### 2.1 RPC 重试

RPC 重试关注的是：

```text
一次远程调用失败了，要不要再发一次同样的 RPC？
```

它通常处理：

```text
网络抖动
连接断开
短暂超时
服务端临时不可用
```

### 2.2 任务重试

任务重试关注的是：

```text
一个业务任务在某个 Worker 上失败了，要不要换一个 Worker 重新执行？
```

它处理的是任务生命周期：

```text
task-001 第一次分配给 worker-a
worker-a 返回 FAILED
Controller 判断还能重试
task-001 第二次分配给 worker-b
worker-b 返回 SUCCEEDED
task-001 最终状态 SUCCEEDED
```

### 2.3 故障转移

故障转移关注的是：

```text
某个节点失败后，把任务迁移到其他可用节点。
```

在本项目里，本课先做最小版本：

```text
失败节点加入 attemptedWorkers
下一次调度时从候选节点中排除 attemptedWorkers
```

### 2.4 熔断

熔断关注的是：

```text
某个 Worker 连续失败很多次后，短时间内不再把请求发给它。
```

你现在代码里已经有 `CircuitBreakerManager`，但本课先不强行整合熔断器。

这节课先把任务级重试闭环打通，后面 RPC 回炉阶段再统一整理：

```text
任务重试
RPC 重试
熔断
限流
连接治理
```

面试时可以这样讲：

```text
任务级重试不是简单重复网络请求，而是基于 taskId 的生命周期重试。
每次尝试会记录 Worker，下一次调度会避开已经失败的节点，最终状态仍然由任务状态机保护。
```

## 三、本课边界

本课先不做这些：

```text
不做重试退避 backoff
不做延迟队列
不做持久化重试记录
不做并行抢占式执行
不做 Worker 主动取消旧任务
不把熔断器完整并入任务调度
```

我们先做同步的、最小可测试重试：

```text
Worker 返回 FAILED
Controller 立即选择另一个 Worker
Controller 重新转发 TASK_SUBMIT
```

## 五、关于 retryCount 的语义

现在 `TaskMetadata.retryCount` 的实现是：

```java
task.setRetryCount(task.getRetryCount() + 1);
```

它在第一次派发给 Worker 时也会加 1。

所以现阶段它更像：

```text
attemptCount
```

也就是“已经尝试过多少次”。

本课先不重命名字段，避免扩大改动面。你可以这样理解：

```text
retryCount = 已尝试次数
maxAttempts = 最大尝试次数
```

例如：

```text
maxAttempts = 3
```

表示：

```text
最多执行 3 次：
第 1 次 worker-a
第 2 次 worker-b
第 3 次 worker-c
```

如果第 3 次仍然失败，就进入最终 `FAILED`。

## 七、第一步：设计 TaskRetryPolicy

新建：

```text
heteromesh-controller/src/main/java/com/heteromesh/controller/scheduler/TaskRetryPolicy.java
```

它先负责两个判断：

```text
1. 这个失败结果是否可重试
2. 当前任务是否还没超过最大尝试次数
```

建议结构：

```java
package com.heteromesh.controller.scheduler;

import com.heteromesh.task.TaskMetadata;
import com.heteromesh.task.TaskResult;
import com.heteromesh.task.TaskStatus;

public class TaskRetryPolicy {
    private final int maxAttempts;

    public TaskRetryPolicy(int maxAttempts) {
        if (maxAttempts <= 0) {
            throw new IllegalArgumentException("maxAttempts must be positive");
        }
        this.maxAttempts = maxAttempts;
    }

    public int getMaxAttempts() {
        return maxAttempts;
    }

    public boolean canRetry(TaskMetadata task, TaskResult failedResult) {
        // TODO
    }

    public boolean isRetryable(TaskResult result) {
        // TODO
    }
}
```

### 7.1 isRetryable

本课先约定：

```text
只有 FAILED 结果可以触发重试
SUCCEEDED / TIMEOUT / CANCELED 都不触发重试
```

你可以先写：

```java
public boolean isRetryable(TaskResult result) {
    return result != null && result.getStatus() == TaskStatus.FAILED;
}
```

如果想多做一点，可以加一个简单的不可重试标记：

```text
errorMessage 以 "NON_RETRYABLE:" 开头时，不重试
```

比如：

```text
NON_RETRYABLE: invalid model name
```

这类错误换 Worker 也不会好，直接失败更合理。

### 7.2 canRetry

`canRetry` 需要同时判断：

```text
1. task 还不是终态
2. result 是可重试失败
3. task.retryCount < maxAttempts
```

注意这里用 `< maxAttempts`。

因为当前 `retryCount` 表示已经尝试过的次数。

例如：

```text
maxAttempts = 3
当前 retryCount = 1
说明已经试过 1 次，还可以再选第 2 次
```

## 八、第二步：扩展状态机

打开：

```text
heteromesh-common/src/main/java/com/heteromesh/task/TaskStateMachine.java
```

当前状态机大概是：

```text
SUBMITTED -> DISPATCHING
DISPATCHING -> RUNNING / FAILED / TIMEOUT / CANCELED
RUNNING -> SUCCEEDED / FAILED / TIMEOUT / CANCELED
```

重试需要一个新的合法流转：

```text
RUNNING -> DISPATCHING
```

原因是：

```text
任务在 worker-a 上 RUNNING
worker-a 返回 FAILED
Controller 决定不把任务最终 FAILED
而是重新进入 DISPATCHING，选择 worker-b
```

所以你要把 `RUNNING` 的允许目标改成：

```java
ALLOWED_TRANSITIONS.put(TaskStatus.RUNNING,
        EnumSet.of(TaskStatus.DISPATCHING,
                TaskStatus.SUCCEEDED,
                TaskStatus.FAILED,
                TaskStatus.TIMEOUT,
                TaskStatus.CANCELED));
```

这里有个设计点：

```text
FAILED 只有在“不再重试”时才是终态。
单次 Worker 失败只是一次 attempt 失败，不一定等于任务最终失败。
```

## 九、第三步：给 TaskScheduler 增加 retry 方法

打开：

```text
heteromesh-controller/src/main/java/com/heteromesh/controller/scheduler/TaskScheduler.java
```

当前 `schedule(request)` 做的是第一次调度：

```text
创建任务
进入 DISPATCHING
选择 Worker
assignWorker
recordAttempt
注册 timeout
```

本课要增加的是对已有任务重试：

```java
public ScheduleResult retry(String taskId) {
    // TODO
}
```

建议逻辑：

```text
1. taskStore.get(taskId)，不存在则返回 failure 或抛异常
2. 如果任务已经终态，不能 retry
3. 从 task.getAttemptedWorkers() 构造 excludedWorkers
4. 调用 loadBalancer.select(taskId, excludedWorkers)
5. 如果选不到 Worker，返回 failure
6. taskStore.updateStatus(taskId, DISPATCHING)
7. taskStore.assignWorker(taskId, worker.getNodeId())
8. taskStore.recordAttempt(taskId, worker.getNodeId())
9. 返回 ScheduleResult.success(task, worker)
```

这里不要重新注册任务级 timeout。

原因是：

```text
第23课的 timeout 是“整个任务生命周期”的 timeout。
重试不应该把 timeoutMs 重置成新的一轮，否则任务可能无限延长。
```

## 十、第四步：ServerHandler 处理 FAILED 结果

打开：

```text
heteromesh-controller/src/main/java/com/heteromesh/controller/ServerHandler.java
```

当前 `handleTaskResult` 基本是：

```java
TaskResult result = TaskPayloadCodec.decodeResult(message.getBody());
taskStore.complete(result.getTaskId(), result);
Channel clientChannel = pendingClients.remove(message.getRequestId());
clientChannel.writeAndFlush(message);
```

本课要改成：

```text
如果 Worker 返回 FAILED：
    先判断是否能 retry
    如果能 retry：
        选择新 Worker
        重新转发 TASK_SUBMIT
        不删除 pendingClients
        不回复 Client
        return
    如果不能 retry：
        complete 为最终 FAILED
        回复 Client

如果 Worker 返回 SUCCEEDED：
    complete 为最终 SUCCEEDED
    回复 Client
```

伪代码：

```java
private void handleTaskResult(ChannelHandlerContext ctx, Message message) {
    TaskResult result = TaskPayloadCodec.decodeResult(message.getBody());
    TaskMetadata task = taskStore.get(result.getTaskId()).orElse(null);

    if (task != null && task.getStatus() == TaskStatus.DISPATCHING) {
        taskStore.updateStatus(result.getTaskId(), TaskStatus.RUNNING);
    }

    if (task != null && retryPolicy.canRetry(task, result)) {
        ScheduleResult retry = taskScheduler.retry(result.getTaskId());
        if (retry.isSuccess()) {
            forwardTaskSubmitToWorker(message.getRequestId(), retry);
            return;
        }
    }

    completeAndReply(message, result);
}
```

你不一定要完全照这个拆方法，但建议把两个动作分清楚：

```text
retry 转发
最终完成并回复
```

否则 `handleTaskResult` 很快会变成一大坨。

## 十一、第五步：重试时如何重新构造 TASK_SUBMIT

重试时，Controller 需要把原始任务请求再发给新的 Worker。

你可以从 `TaskMetadata` 拿到原始请求：

```java
TaskRequest request = retry.getTask().getRequest();
String body = TaskPayloadCodec.encodeRequest(request);
```

重点是：

```text
重试转发要保留原来的 message.requestId
```

因为 `pendingClients` 是用 `requestId` 找到最初提交任务的 Client。

当前 `Message.createTaskSubmit(body)` 会生成新的 requestId，不适合重试转发。

你有两个选择：

### 选择 A：直接用构造器

```java
Message retrySubmit = new Message(
        MessageType.TASK_SUBMIT,
        originalRequestId,
        TaskPayloadCodec.encodeRequest(request)
);
```

### 选择 B：给 Message 增加重载工厂方法

```java
public static Message createTaskSubmit(String requestId, String body) {
    return new Message(MessageType.TASK_SUBMIT, requestId, body);
}
```

我更推荐选择 B。

原因是：

```text
Message 的创建规则集中在 Message 类里，ServerHandler 不需要到处 new Message。
```

## 十二、第六步：处理没有可用重试 Worker

如果 `taskScheduler.retry(taskId)` 返回失败，说明：

```text
1. 所有 Worker 都已经尝试过
2. 或者负载均衡器选不出新节点
3. 或者任务已经终态
```

这时 Controller 应该：

```text
把当前 Worker 返回的 FAILED 写成最终结果
回复 Client
```

也就是说：

```text
没有重试机会时，FAILED 才是最终 FAILED
```

## 十三、第七步：处理重试 Worker 连接不可用

本课你可以先写简单版本：

```text
retry 选到 worker-b 后，如果 worker-b channel 不可用，则最终失败
```

但更完整的版本是：

```text
worker-b channel 不可用
把 worker-b 也记录为 attempted
继续尝试 worker-c
```

这块容易写复杂。建议本课先实现：

```text
Worker 返回 FAILED 后，能成功切到另一个在线且有 Channel 的 Worker
```

等第26课连接治理时，再把“选到节点但连接不可用”的情况和重连、连接池、pending 清理一起补强。

## 十四、本课推荐实现顺序

你按这个顺序写：

```text
1. TaskRetryPolicy
2. TaskStateMachine 增加 RUNNING -> DISPATCHING
3. TaskScheduler 增加 retry(taskId)
4. Message 增加 createTaskSubmit(requestId, body) 重载
5. ServerHandler 构造器注入 TaskRetryPolicy
6. ServerHandler.handleTaskResult 先判断 retry，再 complete
7. HeteroMeshServer 创建 TaskRetryPolicy 并传给 ServerHandler
8. 手动跑一个 Worker-A 失败、Worker-B 成功的链路
9. 找我补测试和 review
```

写的时候记住一个核心原则：

```text
重试成功转发时，不要 remove pendingClients，也不要给 Client 返回失败。
```

Client 只应该收到最终结果。

## 十六、常见错误

### 错误 1：Worker 返回 FAILED 就立刻 complete

如果一看到 FAILED 就调用：

```java
taskStore.complete(taskId, failedResult);
```

任务会进入终态，后面就不能重试了。

正确顺序是：

```text
先判断能不能重试
不能重试时才 complete
```

### 错误 2：重试时生成新的 requestId

如果重试转发用了：

```java
Message.createTaskSubmit(body)
```

它会生成新的 requestId。

这样 Worker-B 返回结果时，Controller 可能找不到最初的 Client。

正确做法是保留原 requestId。

### 错误 3：重试时没有排除失败 Worker

如果 retry 还是调用：

```java
loadBalancer.select(taskId)
```

一致性哈希很可能又选回同一个 Worker。

重试必须使用：

```java
loadBalancer.select(taskId, attemptedWorkers)
```

### 错误 4：重试时重新注册任务 timeout

第23课的 timeout 是整个任务生命周期的 deadline。

重试不应该让任务超时时间不断刷新。

### 错误 5：重试转发后删除 pendingClients

如果重试时执行：

```java
pendingClients.remove(requestId)
```

最终结果回来时就找不到 Client。

只有最终完成并回复时，才删除 pendingClients。

## 十七、完成标准

本课完成后，你应该能做到：

```text
1. Worker-A 返回 FAILED 后，Controller 自动把任务转给 Worker-B
2. Worker-B 返回 SUCCEEDED 后，任务最终状态是 SUCCEEDED
3. attemptedWorkers 里能看到 worker-a 和 worker-b
4. retryCount 能反映尝试次数
5. 所有 Worker 都失败或达到 maxAttempts 后，任务最终 FAILED
6. Client 只收到一次最终 TASK_RESULT
7. 你能讲清楚任务重试和 RPC 重试的区别
```

## 十八、面试讲法

你可以这样讲：

```text
HeteroMesh 的任务重试是 Controller 侧的任务生命周期能力。
每个任务会记录 attemptedWorkers 和尝试次数。
当某个 Worker 返回 FAILED 时，Controller 不会立刻把任务标记为最终失败，而是先通过 TaskRetryPolicy 判断是否还能重试。
如果允许重试，TaskScheduler 会基于负载均衡器重新选择 Worker，并排除已经尝试过的节点。
重试转发时保留原始 requestId，这样最终结果仍然能回到最初的 Client。
只有达到最大尝试次数或没有可用候选节点时，任务才进入最终 FAILED。
```

这个回答里有几个面试官喜欢追问的点：

```text
为什么要保留 requestId？
为什么要记录 attemptedWorkers？
为什么任务失败不等于最终失败？
任务 timeout 是否会因为 retry 被重置？
RPC retry 和 task retry 的边界在哪里？
```

你把这些讲清楚，这节课就值了。
