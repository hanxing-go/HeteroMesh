## 一、这节课解决什么问题？

### 1.1 重试不是万能的

```
场景：Worker 负载过高，处理一个请求要 10 秒（远超 5 秒超时）

Client 请求 → Controller 转发 Worker-A → 5 秒超时 → 重试 Worker-B
Client 请求 → Controller 转发 Worker-A → 5 秒超时 → 重试 Worker-B
Client 请求 → Controller 转发 Worker-A → 5 秒超时 → 重试 Worker-B
...

每个请求都在 Worker-A 上浪费 5 秒，大量 Netty 线程被挂住，
系统整体响应越来越慢，最终雪崩。
```

**重试解决了「偶尔的失败」，熔断解决「持续的失败」。**

### 1.2 熔断器做什么

发现 Worker 连续失败超过阈值后，**暂时把它从候选节点中排除**，等一段冷却时间后再探测它恢复了没：

```
连续失败 5 次 →
  ┌──────────┐          ┌──────────┐     冷却 30 秒    ┌────────────┐
  │  CLOSED  │ ──────→ │   OPEN   │ ──────────────→ │ HALF_OPEN  │
  │ 正常放行  │  熔断！  │ 全部拒绝  │                  │ 放一个探测   │
  └──────────┘          └──────────┘                  └────────────┘
       ↑                                                   │
       │                       探测成功 ← 证明恢复了         │
       └───────────────────────────────────────────────────┘
                           探测失败 → 回到 OPEN（继续冷却）
```

### 1.3 这节课后的效果

```java
// ========== 改前 ==========
// 重试 3 次，每次都超时 5 秒 → 15 秒后返回失败
// 后续请求继续试，继续超时，继续浪费

// ========== 改后 ==========
// Worker-A 连续失败 5 次 → 熔断器打开，30 秒内跳过 Worker-A
// LoadBalancer.select() 自动排除已熔断的节点
// 30 秒后放一个探测请求 → 恢复了就关闭熔断，没恢复继续等
```

## 二、主流框架对比

### 2.1 Sentinel / Resilience4j

两个框架都是同一套设计，参考 Martin Fowler 的 Circuit Breaker 模式：

| 状态 | 行为 |
|------|------|
| **CLOSED** | 正常放行，统计失败次数 |
| **OPEN** | 全部拒绝，快速失败 |
| **HALF_OPEN** | 放一个探测请求，成功→CLOSED，失败→OPEN |

**Sentinel** 把熔断器放在责任链（Slot Chain）里，和流控、降级一起工作。
**Resilience4j** 提供独立的 `CircuitBreaker` 对象，用 `decorateSupplier` 包装调用。

### 2.2 HeteroMesh 的做法

熔断器作用在 **Controller 端**，按 Worker 粒度跟踪。每个 Worker 有一个独立的熔断状态——和上一课的 `Select(key, excludeNodes)` 机制自然结合：熔断的节点直接加入 `excludeNodes`。

## 三、设计

### 3.1 状态机

```
                     CLOSED 下 failureCount >= threshold
            ┌───────────────────────────────────────────┐
            │                                           ▼
     ┌──────────┐        ┌──────────┐  openDurationMs  ┌──────────────┐
     │  CLOSED  │        │   OPEN   │ ────────────────→│  HALF_OPEN   │
     │          │        │          │                   │              │
     └──────────┘        └──────────┘                   └──────────────┘
           ▲                                                 │
           │                     探测成功                     │
           └─────────────────────────────────────────────────┘
                                 探测失败 → 回到 OPEN
```

### 3.2 数据结构

每个 Worker 一个熔断器实例，用 `ConcurrentHashMap` 管理：

```
circuitBreakers: Map<nodeId, WorkerCircuitBreaker>

WorkerCircuitBreaker:
  state: CLOSED | OPEN | HALF_OPEN
  failureCount: int          // CLOSED 状态下的连续失败计数
  lastFailureTime: long      // 最后一次失败的时间戳
  openedAt: long             // 进入 OPEN 状态的时间戳（用于计算冷却时间）
  successCount: int          // HALF_OPEN 状态下连续成功的次数
```

### 3.3 配置

```java
public class CircuitBreakerConfig {
    int failureThreshold = 5;         // 连续失败几次触发熔断
    long openDurationMs = 30_000;     // OPEN 状态持续多久进入 HALF_OPEN
    int halfOpenSuccessThreshold = 2; // HALF_OPEN 下成功几次恢复 CLOSED
}
```

### 3.4 和现有代码的集成点

熔断器放在 `ServerHandler.tryForward()` 里——选择 Worker **之前**先检查该 Worker 是否熔断了：

```java
// tryForward 中
ServiceInstance target = loadBalancer.select(requestId, failedNodes);
// ↑ failedNodes 里包含「重试中失败的节点」和「已熔断的节点」
```

熔断的节点在调用 `select` 之前就会被加入 `failedNodes`，LoadBalancer 自动跳过。

**记录成功/失败**——在 `tryForward` 的超时回调和 `handleTaskResponse` 里：

```
Worker 正常响应 → handleTaskResponse → circuitBreaker.onSuccess(nodeId)
Worker 超时      → schedule 回调      → circuitBreaker.onFailure(nodeId)
```

### 4.2 CircuitBreaker（状态机逻辑，~80 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/CircuitBreaker.java`

```java
package com.heteromesh.rpc;

/**
 * 单个节点的熔断器。参考 Sentinel 三态状态机设计。
 *
 * 状态流转：
 *   CLOSED ──failureCount>=threshold──→ OPEN
 *   OPEN ──openDurationMs 过后───────→ HALF_OPEN
 *   HALF_OPEN ──探测成功─────────────→ CLOSED
 *   HALF_OPEN ──探测失败─────────────→ OPEN
 */
public class CircuitBreaker {

    enum State { CLOSED, OPEN, HALF_OPEN }

    private final String nodeId;
    private final CircuitBreakerConfig config;
    private State state = State.CLOSED;
    private int failureCount = 0;
    private long openedAt = 0;
    private int successCount = 0;

    public CircuitBreaker(String nodeId, CircuitBreakerConfig config) {
        this.nodeId = nodeId;
        this.config = config;
    }

    /** 检查请求是否被允许通过 */
    public boolean allowRequest() {
        switch (state) {
            case CLOSED: return true;
            case OPEN:
                if (System.currentTimeMillis() - openedAt >= config.getOpenDurationMs()) {
                    transitionTo(State.HALF_OPEN);
                    return true;  // 放一个探测请求
                }
                return false;
            case HALF_OPEN: return true;  // HALF_OPEN 下放行探测
            default: return false;
        }
    }

    /** 请求成功 */
    public void onSuccess() {
        switch (state) {
            case CLOSED: failureCount = 0; break;
            case HALF_OPEN:
                if (++successCount >= config.getHalfOpenSuccessThreshold()) {
                    transitionTo(State.CLOSED);
                }
                break;
            case OPEN: break;
        }
    }

    /** 请求失败 */
    public void onFailure() {
        switch (state) {
            case CLOSED:
                if (++failureCount >= config.getFailureThreshold()) {
                    transitionTo(State.OPEN);
                }
                break;
            case HALF_OPEN:
                transitionTo(State.OPEN);  // 探测失败，立即回到 OPEN
                break;
            case OPEN: openedAt = System.currentTimeMillis(); break;  // 重置冷却
        }
    }

    private void transitionTo(State newState) {
        this.state = newState;
        if (newState == State.OPEN) {
            this.openedAt = System.currentTimeMillis();
        } else if (newState == State.CLOSED) {
            this.failureCount = 0;
            this.successCount = 0;
        } else if (newState == State.HALF_OPEN) {
            this.successCount = 0;
        }
    }

    public boolean isOpen() { return state == State.OPEN; }
    public State getState() { return state; }
    public String getNodeId() { return nodeId; }
}
```

### 4.3 CircuitBreakerManager（管理所有节点的熔断器，~30 行）

位置：`heteromesh-controller/src/main/java/com/heteromesh/controller/CircuitBreakerManager.java`

```java
package com.heteromesh.controller;

import com.heteromesh.rpc.CircuitBreaker;
import com.heteromesh.rpc.CircuitBreakerConfig;

import java.util.Map;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.stream.Collectors;

/**
 * 管理所有 Worker 节点的熔断器。
 * 每个 Worker 一个独立的 CircuitBreaker 实例。
 */
public class CircuitBreakerManager {

    private final Map<String, CircuitBreaker> breakers = new ConcurrentHashMap<>();
    private final CircuitBreakerConfig config;

    public CircuitBreakerManager(CircuitBreakerConfig config) {
        this.config = config;
    }

    /** 获取或创建某个节点的熔断器 */
    private CircuitBreaker getOrCreate(String nodeId) {
        return breakers.computeIfAbsent(nodeId, id -> new CircuitBreaker(id, config));
    }

    /** 记录成功 */
    public void onSuccess(String nodeId) {
        getOrCreate(nodeId).onSuccess();
    }

    /** 记录失败 */
    public void onFailure(String nodeId) {
        getOrCreate(nodeId).onFailure();
    }

    /** 返回所有当前处于 OPEN 状态的节点（这些节点应该被排除） */
    public Set<String> getOpenNodes() {
        return breakers.entrySet().stream()
                .filter(e -> e.getValue().isOpen())
                .map(Map.Entry::getKey)
                .collect(Collectors.toSet());
    }

    /** 移除某个节点（节点下线时调用） */
    public void remove(String nodeId) {
        breakers.remove(nodeId);
    }

    public CircuitBreaker getBreaker(String nodeId) {
        return breakers.get(nodeId);
    }
}
```

### 4.4 ServerHandler 改造

在 `tryForward` 中集成熔断器：

```java
// ① 每次重试前，收集已熔断的节点
failedNodes.addAll(circuitBreakerManager.getOpenNodes());

// ② 选中 Worker 后，检查此 Worker 的熔断器是否放行
CircuitBreaker breaker = circuitBreakerManager.getBreaker(target.getNodeId());
// （allowRequest 已在 getOpenNodes 中隐式处理，这里不需要重复调）

// ③ 正常响应 → 记录成功
private void handleTaskResponse(ChannelHandlerContext ctx, Message msg) {
    Channel clientChannel = pendingClients.remove(requestId);
    if (clientChannel != null && clientChannel.isActive()) {
        clientChannel.writeAndFlush(msg);
        // 记录成功（如果是 Worker → Controller 的响应，需要从响应中知道是哪个 Worker）
    }
}

// ④ 超时 → 记录失败
// 在 tryForward 的 schedule 回调中：
circuitBreakerManager.onFailure(target.getNodeId());
```

**关键问题**：`handleTaskResponse` 中怎么知道响应来自哪个 Worker？当前 TASK_RESPONSE 的 body 是 RpcResponse JSON，不包含 Worker 信息。需要在转发时记录 `requestId → nodeId` 的映射。

```java
// 新增字段
private final Map<String, String> requestToNode = new ConcurrentHashMap<>();

// tryForward 中记录
requestToNode.put(requestId, target.getNodeId());

// handleTaskResponse 中获取
String nodeId = requestToNode.remove(requestId);
if (nodeId != null) {
    circuitBreakerManager.onSuccess(nodeId);
}
```

## 六、常见错误预警

### 错误 1：CLOSED 状态下成功不重置失败计数

```java
// ❌ 只有 HALF_OPEN 成功才处理，CLOSED 下成功啥也不做
public void onSuccess() {
    if (state == State.HALF_OPEN) { ... }
}

// ✅ CLOSED 下每次成功都应该重置 failureCount，防止累积
public void onSuccess() {
    if (state == State.CLOSED) {
        failureCount = 0;  // 只要有一次成功，说明 Worker 恢复了
    }
}
```

为什么 CLOSED 下要重置？因为「连续失败 5 次」是指**连续的**——中间穿插了一次成功说明 Worker 还活着，计数器应该归零。

### 错误 2：OPEN 状态下又失败了，不重置冷却时间

```java
// ❌ OPEN 状态下失败啥也不做
case OPEN: break;

// ✅ 应该重置 openedAt，重新计时
case OPEN: openedAt = System.currentTimeMillis(); break;
```

### 错误 3：getOpenNodes 和 allowRequest 重复判断

`getOpenNodes()` 返回的是 OPEN 状态的节点。HALF_OPEN 的节点不在里面——因为它们需要接收探测请求。所以 HALF_OPEN 的节点会正常被 LoadBalancer 选中，然后 `allowRequest()` 放行一个探测请求。

## 八、面试怎么聊

> "第 12 课我做了熔断器，参考 Sentinel 和 Resilience4j 的三态状态机。CLOSED 下统计连续失败次数，达到阈值切到 OPEN（快速失败），冷却时间到了切到 HALF_OPEN（放一个探测请求），探测成功回到 CLOSED，探测失败回到 OPEN。每个 Worker 一个独立的熔断器，在 Controller 端管理。"

> "熔断器和上一课的重试是互补的——重试解决偶发故障，熔断解决持续故障。重试失败时触发熔断器记录失败，熔断器 OPEN 后 LoadBalancer 自动排除该 Worker，避免大量请求在死节点上浪费超时时间。"

> "跟 Sentinel 对比：Sentinel 的熔断器放在 Slot Chain 里，支持慢调用比例和异常比例两种策略。HeteroMesh 用的是更基础的连续失败计数策略，解决的是同一个问题——阻止故障扩散。"
