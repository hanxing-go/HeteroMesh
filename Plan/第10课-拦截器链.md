## 一、这节课解决什么问题？

### 1.1 当前状态：横切逻辑没地方放

```java
// 现在如果你要在每次 RPC 调用前后打印日志，只能这样：
// Worker 端 —— 改 ClientHandler.handleTaskRequest()
Object result = dispatcher.dispatch(...);
log.info("RPC 调用完成: service={}, method={}, result={}", ...);  // ← 和业务逻辑挤在一起

// Client 端 —— 改 RpcProxy.invoke()
RpcResponse rpcResponse = rpcFuture.get();
log.info("RPC 响应: {}", rpcResponse.getStatus());  // ← 和代理逻辑挤在一起

// 想做鉴权？改代码。想做限流？改代码。想加 traceId？改代码。
// 每个需求都在同一个方法里堆 if-else，两个月后谁也看不懂。
```

**问题本质**：日志、鉴权、限流、traceId 这些逻辑是「横切关注点」——它们跟具体的 RPC 调用方法无关，但需要在每次调用前后执行。直接写在调用链路里会让代码膨胀、职责混乱。

### 1.2 这节课后的效果

```java
// ========== 改前 ==========
// 日志逻辑写在 ClientHandler.handleTaskRequest() 里
// 鉴权逻辑也写在同一个方法里
// 来一个新需求就往里加代码

// ========== 改后 ==========
// 1. 定义拦截器
public class LogInterceptor implements RpcInterceptor {
    @Override
    public Object intercept(RpcInvocation invocation, RpcInterceptorChain chain) throws Exception {
        log.info("→ 调用 {}.{}()", invocation.getServiceName(), invocation.getMethodName());
        long start = System.currentTimeMillis();
        try {
            Object result = chain.next(invocation);  // 交给下一个拦截器或最终处理者
            log.info("← 完成 {}.{}() 耗时 {}ms", invocation.getServiceName(),
                    invocation.getMethodName(), System.currentTimeMillis() - start);
            return result;
        } catch (Exception e) {
            log.error("← 失败 {}.{}()", invocation.getServiceName(), invocation.getMethodName(), e);
            throw e;
        }
    }
}

// 2. 组装拦截器链
RpcInterceptorChain chain = RpcInterceptorChain.newBuilder()
    .addInterceptor(new AuthInterceptor())
    .addInterceptor(new LogInterceptor())
    .addInterceptor(new RateLimitInterceptor())
    .handler(dispatcher)  // 最终处理者：真正执行反射调用
    .build();

// 3. 调用时，拦截器链自动执行
Object result = chain.next(invocation);
// → AuthInterceptor 先跑，通过后交给 LogInterceptor → RateLimitInterceptor → dispatcher
```

### 1.3 本质

```
方案：责任链模式（Chain of Responsibility）

  ClientHandler
      │
      ▼
  ┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌──────────────┐
  │ AuthInter.   │ ──► │ LogInter.   │ ──► │ RateLimit.   │ ──► │ RpcDispatcher│
  │ 鉴权          │     │ 日志          │     │ 限流          │     │ (最终处理者)   │
  └─────────────┘     └─────────────┘     └─────────────┘     └──────────────┘
       │                     │                    │                    │
       │ 失败→抛异常           │                    │ 超限→拒绝           │ 反射调用
       │ 成功→交给下一个        │ 计时→交给下一个       │ 通过→交给下一个
```

## 二、主流框架对比

### 2.1 Dubbo Filter

```java
public interface Filter {
    Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException;
}
```

- 基于 SPI 自动激活（`@Activate` 注解）
- Consumer 端和 Provider 端各有独立的 Filter 链
- 通过 `ProtocolFilterWrapper.buildInvokerChain()` 构建责任链
- 内置：AccessLogFilter、ExceptionFilter、TokenFilter、TpsLimitFilter 等 20+ 个

### 2.2 gRPC Interceptor

```java
public interface ServerInterceptor {
    <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
        ServerCall<ReqT, RespT> call, Metadata headers, ServerCallHandler<ReqT, RespT> next);
}
```

- Client 端和 Server 端各有独立的 Interceptor 接口
- 通过 `ServerInterceptors.intercept(service, interceptor1, ...)` 组装
- 拦截器按注册的逆序执行

### 2.3 HeteroMesh 的做法

HeteroMesh 作为教学项目，设计一个更简单的统一拦截器接口，同时覆盖 Client 端和 Worker 端：

```java
public interface RpcInterceptor {
    Object intercept(RpcInvocation invocation, RpcInterceptorChain chain) throws Exception;
}
```

跟 Dubbo 的 `Filter.invoke(invoker, invocation)` 和 gRPC 的 `interceptCall(call, headers, next)` 本质一模一样——**接收 invocation + 下一个节点，返回 result**。

## 三、设计

### 3.1 RpcInterceptorChain

```
RpcInterceptorChain 是一条链，链上的每个节点有两种角色之一：
  - RpcInterceptor：拦截器，可以在调用前后插入逻辑
  - handler：最终处理者，真正执行方法调用

链是单向的，调用 chain.next(invocation) 就往下走。
```

```java
RpcInterceptorChain chain = new RpcInterceptorChain(
    List.of(auth, log, rateLimit),  // 拦截器列表
    invocation -> dispatcher.dispatch(...)  // 最终 handler
);

// 执行：auth → log → rateLimit → handler
chain.next(invocation);
```

### 3.2 RpcInvocationContext（可选，本节课先不做）

后续可以加一个 `RpcInvocationContext` 在链上传递 traceId、userId、超时截止时间等元数据，不污染业务方法签名。第 10 课先把拦截器链本身跑通。

## 四、你要写的核心代码

### 4.1 RpcInterceptor（~10 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RpcInterceptor.java`

```java
package com.heteromesh.rpc;

/**
 * RPC 拦截器。参考 Dubbo Filter 和 gRPC Interceptor 设计。
 *
 * 实现类在 intercept() 中通过 chain.next(invocation) 将调用传递给下一个拦截器或最终处理者。
 * 可以在 chain.next() 前后插入横切逻辑（日志、鉴权、限流、指标等）。
 */
public interface RpcInterceptor {

    /**
     * 拦截一次 RPC 调用。
     *
     * @param invocation 本次调用的描述（serviceName + methodName + args）
     * @param chain      拦截器链，调用 chain.next(invocation) 将请求传给下一个节点
     * @return 最终处理者的返回值
     */
    Object intercept(RpcInvocation invocation, RpcInterceptorChain chain) throws Exception;
}
```

### 4.2 RpcInterceptorChain（~40 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RpcInterceptorChain.java`

```java
package com.heteromesh.rpc;

import java.util.ArrayList;
import java.util.List;

/**
 * RPC 拦截器链，责任链模式的实现。
 *
 * 链上依次排列拦截器，最后一个节点是最终处理者（handler）。
 * 调用 chain.next(invocation) 开始执行整条链。
 */
public class RpcInterceptorChain {

    private final List<RpcInterceptor> interceptors;
    private final RpcHandler handler;
    private int currentIndex = 0;  // 当前执行到第几个拦截器

    public RpcInterceptorChain(List<RpcInterceptor> interceptors, RpcHandler handler) {
        this.interceptors = interceptors;
        this.handler = handler;
    }

    /**
     * 将调用传递给链上的下一个节点。
     * 如果还有拦截器未执行 → 执行下一个拦截器
     * 如果所有拦截器都已执行 → 交给最终 handler
     */
    public Object next(RpcInvocation invocation) throws Exception {
        if (currentIndex < interceptors.size()) {
            // 逐个取拦截器，索引递增
            RpcInterceptor interceptor = interceptors.get(currentIndex++);
            return interceptor.intercept(invocation, this);
        } else {
            // 全部执行完毕，交给最终处理者
            return handler.handle(invocation);
        }
    }

    /**
     * 最终处理者：真正执行方法调用的逻辑。
     */
    @FunctionalInterface
    public interface RpcHandler {
        Object handle(RpcInvocation invocation) throws Exception;
    }

    // ===== Builder =====

    public static Builder newBuilder() {
        return new Builder();
    }

    public static class Builder {
        private final List<RpcInterceptor> interceptors = new ArrayList<>();
        private RpcHandler handler;

        public Builder addInterceptor(RpcInterceptor interceptor) {
            this.interceptors.add(interceptor);
            return this;
        }

        public Builder handler(RpcHandler handler) {
            this.handler = handler;
            return this;
        }

        public RpcInterceptorChain build() {
            return new RpcInterceptorChain(interceptors, handler);
        }
    }
}
```

### 4.3 一个内置拦截器示例：LogInterceptor（~30 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/LogInterceptor.java`

```java
package com.heteromesh.rpc;

import lombok.extern.slf4j.Slf4j;

/**
 * 日志拦截器：在每次 RPC 调用前后记录日志和耗时。
 */
@Slf4j
public class LogInterceptor implements RpcInterceptor {

    @Override
    public Object intercept(RpcInvocation invocation, RpcInterceptorChain chain) throws Exception {
        log.info("[RPC] → {}.{}() 参数个数={}",
                invocation.getServiceName(),
                invocation.getMethodName(),
                invocation.getArgs() != null ? invocation.getArgs().length : 0);

        long start = System.currentTimeMillis();
        try {
            Object result = chain.next(invocation);
            log.info("[RPC] ← {}.{}() 完成, 耗时={}ms",
                    invocation.getServiceName(),
                    invocation.getMethodName(),
                    System.currentTimeMillis() - start);
            return result;
        } catch (Exception e) {
            log.error("[RPC] ← {}.{}() 失败, 耗时={}ms",
                    invocation.getServiceName(),
                    invocation.getMethodName(),
                    System.currentTimeMillis() - start, e);
            throw e;
        }
    }
}
```

### 4.4 ClientHandler 改造

把 `handleTaskRequest` 中直接调 `dispatcher.dispatch()` 的部分，改为通过拦截器链执行。

// 在 ClientHandler 中：
public ClientHandler(RpcClient client, String nodeId, RpcDispatcher dispatcher) {

## 六、常见错误预警

### 错误 1：拦截器忘了调 chain.next()

```java
// ❌
public Object intercept(RpcInvocation inv, RpcInterceptorChain chain) {
    log.info("调用了");
    return "硬编码的返回值";  // 忘了交出去！后面的拦截器和 handler 都不执行
}

// ✅
public Object intercept(RpcInvocation inv, RpcInterceptorChain chain) throws Exception {
    log.info("前置处理");
    return chain.next(inv);  // 必须交出去！
}
```

### 错误 2：索引不重置

```java
// ❌ 用同一个 Chain 对象多次调用时，currentIndex 不会自动归零
chain.next(invocation1);  // currentIndex 走到末尾
chain.next(invocation2);  // currentIndex 还是末尾！跳过了所有拦截器

// ✅ 每次 next() 调用前重置，或者在每次调用时创建新的 Chain
```

**HeteroMesh 的做法**：每次 `ClientHandler.handleTaskRequest()` 调用时创建一个新的 `RpcInterceptorChain`，或者 `chain.next()` 内部处理重置。具体到实现：**Chain 实例不可重用，每个请求创建一个**。

### 错误 3：拦截器链顺序搞反

拦截器在 Builder 中 `addInterceptor` 的顺序就是执行顺序：
```java
chain.addInterceptor(A).addInterceptor(B).handler(H)
// 执行顺序：A → B → H
// 和 Dubbo 一样（Dubbo 用倒序遍历链表实现正序执行，但我们直接用索引递增更直观）
```

### 错误 4：拦截器里吞掉异常

```java
// ❌ catch 了异常但不抛，调用方以为成功了
try {
    return chain.next(inv);
} catch (Exception e) {
    return "null";  // 吞了！
}
```

## 八、面试怎么聊

> "第 10 课我做了拦截器链，和 Dubbo 的 Filter、gRPC 的 Interceptor 一样，本质是责任链模式。定义了一个 RpcInterceptor 接口（一个 intercept 方法），通过 RpcInterceptorChain 把多个拦截器串联起来，最后一个节点是真正的调用处理器。"

> "RpcInterceptorChain 内部维护了一个索引指针和一个 handler。chain.next(invocation) 被调用时，如果还有拦截器没执行就拿下一个执行，如果全部执行完了就交给 handler。每个请求创建一个新的 Chain 实例，避免 currentIndex 跨请求污染。"

> "和 Dubbo 对比：Dubbo 的 Filter 基于 SPI 和 @Activate 注解自动激活，用倒序遍历构建链表。HeteroMesh 的链更简单——顺序列表 + 索引递增，效果一样但更容易理解。Dubbo 有 20+ 内置 Filter，我们这节课先做一个 LogInterceptor 跑通链路。"

> "和 gRPC 对比：gRPC 的 Interceptor 分 Client/Server 两个接口，还有 forward 包装类做装饰器模式。我们用一个统一的 RpcInterceptor 覆盖两端，通过 Builder 组装。"
