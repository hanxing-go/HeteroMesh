
## 二、主流框架对比

### 2.1 Dubbo 的做法

Dubbo 默认 `FailoverCluster`，通过 `retries` 配置重试次数（不含首次调用）：

```xml
<dubbo:reference retries="2" />  <!-- 失败后重试2次，共3次 -->
```

**特点**：
- 每次重试会通过 LoadBalance 重新选一个 Provider（换一台机器试）
- `retries="0"` 表示不重试
- 6 种容错模式：Failover / Failfast / Failsafe / Failback / Forking / Broadcast

### 2.2 gRPC 的做法

gRPC 用 `retryPolicy` 配置，支持指数退避 + 抖动：

```json
{
  "retryPolicy": {
    "maxAttempts": 4,
    "initialBackoff": "0.1s",
    "maxBackoff": "1s",
    "backoffMultiplier": 2.0,
    "retryableStatusCodes": ["UNAVAILABLE"]
  }
}
```

**特点**：
- `maxAttempts` 包含首次调用（4 次 = 1 首次 + 3 重试）
- 指数退避：100ms → 200ms → 400ms → 800ms（有上限）
- ±20% 随机抖动，防止「惊群效应」
- 只对幂等操作重试

### 2.3 HeteroMesh 的做法

重试逻辑实现为一个 **RpcInterceptor**，放在第 10 课的拦截器链里。这正好验证了拦截器链的设计——新功能不用改业务代码，加一个拦截器即可。

## 三、设计

### 3.1 RetryConfig

```
一次重试策略的完整描述：
  maxRetries      重试次数（不含首次）
  initialBackoff  第一次重试前的等待时间（毫秒）
  backoffMultiplier 退避倍率（每次重试等待时间翻几倍）
  maxBackoff      最长等待时间上限（毫秒）
  retryableStatuses 哪些 RpcStatus 值应该触发重试
```

退避公式（参考 gRPC）：

```
delay(n) = min(initialBackoff × backoffMultiplierⁿ, maxBackoff)
         × (1 ± 0.2) 随机抖动

n=0: 100ms × (0.8~1.2) = 80~120ms
n=1: 200ms × (0.8~1.2) = 160~240ms
n=2: 400ms × (0.8~1.2) = 320~480ms
```

### 3.2 RetryInterceptor

实现 `RpcInterceptor` 接口，在 `intercept()` 里循环调用 `chain.next(invocation)`，失败时判断是否应该重试：

```java
for (int attempt = 0; attempt <= config.getMaxRetries(); attempt++) {
    try {
        return chain.next(invocation);  // 调下一个拦截器（最终到 handler）
    } catch (Exception e) {
        if (attempt == config.getMaxRetries() || !shouldRetry(e)) {
            throw e;  // 最后一次或不可重试，抛出去
        }
        Thread.sleep(computeBackoff(attempt));  // 退避等待
    }
}
```

### 3.3 放在拦截器链的哪个位置

```
链的顺序（重要！）：
  LogInterceptor → RetryInterceptor → handler

逻辑：
  ① LogInterceptor 记录「进入调用」
  ② RetryInterceptor 内部循环：
       chain.next() → handler.dispatch() → 失败
       → 等等 → chain.next() → handler.dispatch() → 成功
  ③ LogInterceptor 记录「调用完成」

RetryInterceptor 包裹 handler，每次重试 handler 都被重新执行。
LogInterceptor 在外面，只记录整体结果（不管中间重试了几次）。
```

如果 RetryInterceptor 放在 LogInterceptor 外面（第一个），Log 会打印每次重试的日志——两种放法各有用途。

### 4.2 RetryInterceptor（~60 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RetryInterceptor.java`

```java
package com.heteromesh.rpc;

import lombok.extern.slf4j.Slf4j;

/**
 * 重试拦截器。参考 Dubbo FailoverCluster + gRPC retryPolicy 设计。
 *
 * 用 for 循环包裹 chain.next()，失败时判断是否需要重试，需要就退避等待再试。
 * 实现为 RpcInterceptor，可以直接插入第 10 课的拦截器链。
 */
@Slf4j
public class RetryInterceptor implements RpcInterceptor {

    private final RetryConfig config;

    public RetryInterceptor(RetryConfig config) {
        this.config = config;
    }

    @Override
    public Object intercept(RpcInvocation invocation, RpcInterceptorChain chain) throws Exception {
        // 循环：最多 maxRetries + 1 次（含首次）
        // 每次调用 chain.next(invocation)
        // 成功 → return
        // 失败 → 判断是否可重试 → 可重试就 sleep(backoff) → 继续循环
        // 不可重试或次数到上限 → 抛异常
    }
}
```

需要你来完成的逻辑：
- for 循环 `attempt = 0` 到 `maxRetries`
- 每次 `chain.next(invocation)`
- catch 异常后判断：`Exception` 里是否包含 `RpcStatus` 信息（比如 `RuntimeException` 的消息中以 `FRAMEWORK_ERROR` 开头）？实际上这里有个设计问题——当前 handler（dispatcher）抛的是 `IllegalArgumentException` 等原始异常，不是 `RpcResponse`，RetryInterceptor 怎么知道这个异常对应哪个 `RpcStatus`？

**关键设计决策**：有两种方案——

**方案 A（简单）**：RetryInterceptor 不区分异常类型，所有 `Exception` 都重试。简单粗暴，够用。

**方案 B（更细）**：定义一个 `RpcException`，携带 `RpcStatus`，RetryInterceptor 根据 `RpcStatus` 判断是否重试。这是 Dubbo 的做法（`RpcException` 带各种错误码）。

第 11 课先用**方案 A**——所有异常都重试，后面再优化。

### 4.3 ClientHandler 改造

把 `RetryInterceptor` 加入拦截器链：

### 4.4 RpcProxy 改造（Client 端重试）

**当前我们只做了 Worker 端的重试。** Client 端（RpcProxy）的超时重试是另一个维度——仿照 Dubbo Failover，超时后换一个 Worker 重试。第 11 课先把 Worker 端的重试做透，Client 端重试放到后续课。

## 六、常见错误预警

### 错误 1：忘记录首次调用

```java
// ❌ 第一次也不用 chain.next()，直接跳过去重试
for (int i = 0; i < maxRetries; i++) {
    // ...
}

// ✅ 首次调用也算一次
for (int attempt = 0; attempt <= maxRetries; attempt++) {
    try {
        return chain.next(invocation);
    } catch (Exception e) {
        if (attempt == maxRetries) throw e;
    }
}
```

### 错误 2：退避时没处理中断

```java
// ❌ Thread.sleep 被中断后抛异常，整个重试终止
Thread.sleep(backoffMs);

// ✅ catch InterruptedException 恢复中断状态后继续重试或返回
try {
    Thread.sleep(backoffMs);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new RuntimeException("重试被中断", e);
}
```

### 错误 3：退避时间没加随机抖动

```java
// ❌ 100 个客户端同时超时 → 100 个同时睡 100ms → 同时醒来 → 同时重试 → 再次打挂
Thread.sleep(100);

// ✅ 加 ±20% 随机 → 有的睡 80ms，有的 120ms → 分散到达
Thread.sleep((long) (100 * (0.8 + Math.random() * 0.4)));
```

### 错误 4：在 RetryInterceptor 里调了 dispatcher.dispatch() 而不是 chain.next()

```java
// ❌ 绕过了拦截器链，后面的 LogInterceptor 不会执行
Object result = dispatcher.dispatch(invocation);

// ✅ 调 chain.next()，尊重链的完整性
Object result = chain.next(invocation);
```
