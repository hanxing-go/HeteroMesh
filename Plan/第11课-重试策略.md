## 一、这节课解决什么问题？

### 1.1 时间窗口问题

```
Worker 挂了，但心跳还没发现（需要 3 次心跳超时 ≈ 15 秒）

 ──Worker 挂──→──Client 发来 RPC──→──心跳最终发现──→
                    │
                    └─ LoadBalancer 选中这个挂掉的 Worker
                       ctx.writeAndFlush(TASK_REQUEST)
                       → 没有响应
                       → Client 超时，调用失败

  这 15 秒窗口内的请求全部失败了——尽管集群里还有其他活的 Worker！
```

**本质**：负载均衡选了一个「名义上活着、实际上已经死了」的节点。重试就是弥补这个时间窗口——**第一次失败，换一个再试。**

### 1.2 当前代码的问题

```java
// ServerHandler.handleTaskRequest() 当前逻辑：
ServiceInstance target = loadBalancer.select(requestId);
if (target == null) {
    // 没有可用节点 → 直接返回错误
    ctx.writeAndFlush(errorResponse);
    return;
}

Channel workerChannel = nodeChannelMap.getChannel(target.getNodeId());
if (workerChannel == null || !workerChannel.isActive()) {
    // Channel 不可用 → 直接返回错误
    ctx.writeAndFlush(errorResponse);
    return;
}

// 转发出去就不管了，没有超时等待
workerChannel.writeAndFlush(msg);
```

三个问题：
1. LoadBalancer 选到的 Worker 可能刚挂，Channel 不可用 → 直接报错
2. 转发后不等待响应，没有超时检测
3. 失败了不会换一个 Worker 重试

### 1.3 这节课后的效果

```java
// ========== 改前 ==========
// 选一个 Worker → 发 → 失败就报错

// ========== 改后 ==========
// 选一个 Worker → 发 → 等待响应
//   → 超时/失败 → 排除这个 Worker → 选下一个 → 重试
//   → 直到成功 或 没有可用的 Worker 了
```

参考 Dubbo FailoverCluster：失败自动切换，每次重试通过 LoadBalance 重新选择 Provider。

## 二、主流框架对比

### 2.1 Dubbo FailoverCluster

Dubbo 默认 Failover，通过 `retries` 配置：

```xml
<dubbo:reference retries="2" />  <!-- 失败后重试 2 次，共 3 次 -->
```

**核心机制**：每次重试会通过 LoadBalance **重新选一个 Provider**。第一次选 A 失败了，第二次选 B，第三次选 C。`retries=0` 就是不重试（Failfast）。

### 2.2 gRPC retryPolicy

gRPC 的 retry 在 Client 端做，支持指数退避 + 抖动：

```json
{
  "retryPolicy": {
    "maxAttempts": 4,
    "initialBackoff": "0.1s",
    "maxBackoff": "1s",
    "backoffMultiplier": 2.0,
    "retryableStatusCodes": ["UNAVAILABLE"]
  }
}
```

±20% 随机抖动防止「惊群效应」——所有客户端同时重试打挂服务器。

### 2.3 HeteroMesh 的做法

在 Controller 的 `ServerHandler` 里做 Failover 重试。每次重试从 LoadBalancer 换一个 Worker，利用集群里其他活着的节点。简单直接，不引入退避（目前阶段一个 Controller 不存在惊群问题）。

## 三、设计

### 3.1 重试流程

```
Client 发来 TASK_REQUEST
    │
    ▼
Controller: for (attempt = 0; attempt <= maxRetries; attempt++)
    │
    ├─ ① LoadBalancer.select(requestId) → 选 Worker-A
    │     └─ 没有 Worker 了？→ 返回错误给 Client
    │
    ├─ ② nodeChannelMap.getChannel(workerA_id) → Channel
    │     └─ Channel 不可用？→ 排除 Worker-A → continue（选下一个）
    │
    ├─ ③ 转发 TASK_REQUEST 到 Worker-A
    │     ├─ pendingClients 记录 clientChannel
    │     └─ 等 Worker 回复 TASK_RESPONSE（通过 pending 机制）
    │
    ├─ ④ Worker 回复了 TASK_RESPONSE
    │     └─ → 回传给 Client → 成功！return
    │
    └─ ⑤ 没等到回复（超时）→ 从 pendingClients 清理
          → 排除 Worker-A → continue（重试选 Worker-B）
```

### 3.2 需要新增的机制

**当前 Controller 转发是「发了不管」的**，没有等 Worker 回复的逻辑。需要加一个超时等待机制。

但注意：**handleTaskRequest 运行在 Netty EventLoop 线程上，不能阻塞！** 需要用 Netty 的 `EventLoop.schedule()` 做超时定时器：

```java
// 转发到 Worker
workerChannel.writeAndFlush(msg);

// 设置一个超时定时器
ctx.executor().schedule(() -> {
    // 超时了：检查 pendingClients 里这个 requestId 还在不在
    // 在的话说明 Worker 没回复 → 从 pendingClients 移除 → 重试下一个
}, timeoutMs, TimeUnit.MILLISECONDS);
```

这就是 Dubbo 的 `DefaultFuture` 超时机制——等价于第 9 课写的 `RpcFuture`，只不过从 Client 端搬到了 Controller 端。

### 3.3 排除已失败的 Worker

重试时不能每次都选到同一个挂掉的 Worker，需要在重试期间临时排除：

```java
Set<String> failedNodes = new HashSet<>();
for (int attempt = 0; attempt <= maxRetries; attempt++) {
    ServiceInstance target = loadBalancer.select(requestId, failedNodes);  // 排除失败的
    if (target == null) break;  // 没有活的了
    // ... 尝试转发 ...
    // 超时 → failedNodes.add(target.getNodeId());
}
```

## 四、你要写的核心代码

### 4.1 参考 Dubbo 的设计

Dubbo FailoverCluster 源码里的做法（`FailoverClusterInvoker.doInvoke()`）：

```java
// 重试前重新获取最新的 Provider 列表
copyinvokers = list(invocation);

// select 方法接受「已失败的节点列表」做排除
Invoker<T> invoker = select(loadbalance, invocation, copyinvokers, selected);
//  ↑ selected 是已调用过且失败的节点列表
```

`reselect()` 核心逻辑：`invokers - selected` 的差集上重新走 LoadBalance，所以不会重复选失败的。

### 4.2 HeteroMesh 的实现：tryForward

```java
// ① LoadBalancer 需要新增一个重载方法
ServiceInstance select(String key, Set<String> excludeNodeIds);

// ② ServerHandler 改造
private void handleTaskRequest(ChannelHandlerContext ctx, Message msg) {
    tryForward(ctx, msg, new HashSet<>(), 0);
}

private void tryForward(ChannelHandlerContext ctx, Message msg,
                        Set<String> failedNodes, int attempt) {
    String requestId = msg.getRequestId();

    if (attempt > DEFAULT_MAX_RETRIES) {
        ctx.writeAndFlush(Message.createTaskResponse(requestId,
                "重试" + DEFAULT_MAX_RETRIES + "次后仍失败"));
        return;
    }

    // ① 从剩余节点中选择（排除已失败的）
    ServiceInstance target = loadBalancer.select(requestId, failedNodes);
    if (target == null) {
        ctx.writeAndFlush(Message.createTaskResponse(requestId, "无可用节点"));
        return;
    }

    // ② Channel 不可用 → 排除当前节点 + 重试
    Channel workerChannel = nodeChannelMap.getChannel(target.getNodeId());
    if (workerChannel == null || !workerChannel.isActive()) {
        failedNodes.add(target.getNodeId());
        tryForward(ctx, msg, failedNodes, attempt);
        return;
    }

    // ③ 转发 + 记录
    pendingClients.put(requestId, ctx.channel());
    workerChannel.writeAndFlush(msg);

    // ④ 超时定时器
    ctx.executor().schedule(() -> {
        Channel client = pendingClients.remove(requestId);
        if (client != null) {
            // 还没回 → 超时，排除当前节点，重试
            failedNodes.add(target.getNodeId());
            tryForward(ctx, msg, failedNodes, attempt + 1);
        }
    }, FORWARD_TIMEOUT_MS, TimeUnit.MILLISECONDS);
}
```

**逻辑**：
- 每次重试前通过 `select(key, excludeNodes)` 排除已失败的节点
- 超时/不可用 → 把当前节点记入 `failedNodes` → 递归重试
- 正常响应 → `handleTaskResponse` 拿走 → 超时定时器发现 `remove` 返回 null → 不重试
- 跟 Dubbo 一样：**同一个 LoadBalancer，只是在越来越小的候选集上选**

## 六、常见错误预警

### 错误 1：在 EventLoop 线程里 sleep

```java
// ❌ EventLoop 是 Netty 的 I/O 线程，sleep 会卡死整个 EventLoop
Thread.sleep(5000);

// ✅ 用 schedule 异步定时器
ctx.executor().schedule(() -> { ... }, 5000, TimeUnit.MILLISECONDS);
```

### 错误 2：pendingClients 没清理导致重试和正常响应冲突

```java
// ❌ 重试前忘了从 pendingClients 移除旧的
tryForward(ctx, msg, requestId, attempt + 1);
// 旧的 pendingClients[requestId] 还在！

// ✅ 超时回调里先 remove，再重试
Channel client = pendingClients.remove(requestId);
if (client != null) {
    tryForward(ctx, msg, requestId, attempt + 1);
}
```

### 错误 3：正常响应和超时重试的竞态

```
场景：Worker-A 只是负载高（不是死了），5 秒内没处理完。Controller 超时后
      重试发给 Worker-B。但 Worker-A 在第 6 秒也处理完了，响应又回来了。

  ① 超时定时器触发 → pendingClients.remove(requestId) → 拿到 client
  ② 触发重试 tryForward → pendingClients.put(requestId, ctx.channel())
  ③ 同时 Worker-A 的 TASK_RESPONSE 也到了 → handleTaskResponse()
     → pendingClients.remove(requestId) → 拿到重试后的新 record
     → 把 Worker-A 的响应回传给 Client

  结果：Client 收到的是 Worker-A 的迟到的响应，而不是 Worker-B 的。
        但如果 Worker-A 也返回成功，结果其实是一样的（幂等操作）。
        如果不是幂等的——比如累加计数——就会出现数据不一致。
```

**什么时候会发生**：超时时间设太短 + Worker 只是慢不是死。

**怎么解决**：每次重试用不同的 requestId（如 `requestId + "#" + attempt`），让新旧响应走不同的 key，互不干扰。

**第 11 课先不处理这个**——单次 5 秒超时足够宽裕，Worker 要么很快返回，要么大概率真死了。后续课在 Client 端统一做 requestId 版本号。

### 错误 4：递归深度

```java
// 最多递归 3 层（maxRetries=2），完全可以接受
tryForward(0) → tryForward(1) → tryForward(2) → 返回错误
```

## 八、面试怎么聊

> "第 11 课我在 Controller 端做了 Failover 重试，参考 Dubbo 的 FailoverCluster。当 Controller 转发请求到 Worker 超时或失败时，自动选另一个 Worker 重试，利用集群冗余来消化心跳检测时间窗口内的请求失败。"

> "关键设计是用 Netty 的 schedule 定时器做异步超时检测，不在 EventLoop 线程里阻塞。超时后通过递归 tryForward 选下一个 Worker，pendingClients 的 remove 返回值区分「正常响应已到」和「超时需要重试」两种状态。"

> "和 Dubbo 对比：Dubbo 的 Failover 是在 Consumer 端通过 Cluster 层透明完成的，每次重试 LoadBalance 重新选 Provider。HeteroMesh 在 Controller 端做，因为 Controller 是唯一知道所有 Worker 状态的中枢节点。"
