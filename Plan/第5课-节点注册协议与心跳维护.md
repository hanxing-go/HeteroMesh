## 一、这节课解决什么问题？

### 当前状态 vs 目标

```
当前（阶段 0 状态）：
  Worker ──连接──→ Controller ──回消息──→ Worker  ← 纯粹的消息收发
  Controller 完全不知道 Worker 是谁

这节课后：
  Worker ──连接──→ Controller
    │                  │
    └──发送 REGISTER──→│  "我叫 worker-gpu-01，RTX 5090，显存 24GB"
                       │
                       ├─ 存入 ServiceRegistry
                       ├─ 回复 REGISTER_ACK "注册成功"
                       ├─ 启动心跳检测
                       └─ 30 秒无心跳 → 踢出

  变成真正的「管理者」
```

### 为什么不直接在 `channelActive` 里注册？

已经有 `ConnectionManager.add(channel)` 在 `channelActive` 时调用。但问题是：
- key 是 `channel.id()`（Netty 断连重连就变），不是 Worker 的逻辑 ID
- 没有节点元数据（GPU 型号、显存、负载）
- 没有注册确认机制（Worker 不知道 Controller 是否接受了自己）

**这节课就是把"连接"升级为"注册"。**

## 二、注册流程设计

### 2.1 时序图

```
 Worker                               Controller
   │                                      │
   │──── TCP 握手 ───────────────────────→│
   │                                      │
   │──── REGISTER {nodeId, gpu, ...} ────→│  ① Worker 自报家门
   │                                      │
   │                             ② 存入 ServiceRegistry
   │                             ③ 关联 Channel → nodeId
   │                             ④ 记录 lastHeartbeat = now
   │                                      │
   │←─── REGISTER_ACK {nodeId} ──────────│  ⑤ 确认注册成功
   │                                      │
   │─── PING ────────────────────────────→│  ⑥ 开始心跳（已有的 HeartbeatHandler）
   │←── PONG ────────────────────────────│
   │   ...每 5 秒重复...                   │
   │                                      │
   │                        ⑦ 后台定时检查 lastHeartbeat
   │                           超过 15 秒没心跳 → unregister
```

### 2.2 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 注册消息用什么序列化？ | JSON | 一次性操作，可读性 > 性能 |
| 谁发起注册？ | Worker（主动） | Worker 知道自己的信息，穿透 NAT |
| nodeId 从哪来？ | Worker 本地配置 | `worker-gpu-01`、`worker-cpu-02` 等 |
| Controller 怎么知道 Channel 对应哪个 nodeId？ | 新建 NodeChannelMap | ConnectionManager + ServiceRegistry 统一 |

### 3.2 ServiceInstance 增强

当前 `ServiceInstance` 只有基本字段，这课要加上 Worker 的硬件信息：

```java
package com.heteromesh.registry;

import lombok.AllArgsConstructor;
import lombok.Data;

@Data
@AllArgsConstructor
public class ServiceInstance {
    private String nodeId;        // Worker 逻辑标识 "worker-gpu-01"
    private String host;          // Worker IP
    private int port;             // Worker 端口
    private String gpuType;       // GPU 型号，如 "RTX 5090" / "RTX 3080" / "CPU Only"
    private long vramFree;        // 空闲显存（MB），CPU 节点填 0
    private int load;             // 当前负载（排队的任务数）
    private long registerTime;    // 注册时间戳
    private long lastHeartbeat;   // 最后心跳时间戳

    // 判活：超过 timeoutMs 没心跳 = 已死亡
    public boolean isAlive(long timeoutMs) {
        return System.currentTimeMillis() - lastHeartbeat < timeoutMs;
    }
}
```

**改完记得更新现有构造调用处**（InMemoryServiceRegistryTest 等），因为构造函数参数变了。

### 3.3 NodeChannelMap（~25 行）

这个类解决一个问题：Controller 知道 nodeId 时，怎么找到对应的 Netty Channel 发消息？

```java
package com.heteromesh.controller.node;

import io.netty.channel.Channel;

import java.util.concurrent.ConcurrentHashMap;

/**
 * nodeId ↔ Channel 的双向映射
 * 替代原来 ConnectionManager 的 channel.id() 做 key 的方式
 */
public class NodeChannelMap {

    // nodeId → Channel
    private final ConcurrentHashMap<String, Channel> nodeToChannel = new ConcurrentHashMap<>();
    // Channel → nodeId
    private final ConcurrentHashMap<String, String> channelToNode = new ConcurrentHashMap<>();

    public void bind(String nodeId, Channel channel) {
        nodeToChannel.put(nodeId, channel);
        channelToNode.put(channel.id().asShortText(), nodeId);
    }

    public void unbind(Channel channel) {
        String nodeId = channelToNode.remove(channel.id().asShortText());
        if (nodeId != null) {
            nodeToChannel.remove(nodeId);
        }
    }

    public Channel getChannel(String nodeId) {
        return nodeToChannel.get(nodeId);
    }

    public String getNodeId(Channel channel) {
        return channelToNode.get(channel.id().asShortText());
    }

    public int size() {
        return nodeToChannel.size();
    }
}
```

### 3.5 Controller 端：ServerHandler 改造

```java
// ServerHandler.java 改造：

public class ServerHandler extends SimpleChannelInboundHandler<Message> {

    private final ServiceRegistry registry;
    private final NodeChannelMap nodeChannelMap;

    public ServerHandler(ServiceRegistry registry, NodeChannelMap nodeChannelMap) {
        this.registry = registry;
        this.nodeChannelMap = nodeChannelMap;
    }

    @Override
    protected void channelRead0(ChannelHandlerContext ctx, Message msg) {
        switch (msg.getType()) {
            case REGISTER -> handleRegister(ctx, msg);
            case TASK_REQUEST -> handleTaskRequest(ctx, msg);
            default -> log.debug("收到消息: type={}", msg.getType());
        }
    }

    private void handleRegister(ChannelHandlerContext ctx, Message msg) {
        // ① 反序列化 ServiceInstance
        ServiceInstance instance = new Gson().fromJson(msg.getBody(), ServiceInstance.class);

        // ② 存入注册中心
        registry.register(instance);
        log.info("节点注册成功: nodeId={}, gpuType={}, vramFree={}MB",
                instance.getNodeId(), instance.getGpuType(), instance.getVramFree());

        // ③ 绑定 nodeId ↔ Channel
        nodeChannelMap.bind(instance.getNodeId(), ctx.channel());

        // ④ 回复 ACK
        Message ack = Message.createAck(msg.getRequestId(), instance.getNodeId());
        ctx.writeAndFlush(ack);
        log.info("发送注册确认: nodeId={}", instance.getNodeId());
    }

    private void handleTaskRequest(ChannelHandlerContext ctx, Message msg) {
        // 暂时保留原有逻辑
        Message reply = Message.createTaskResponse(msg.getRequestId(), "成功收到消息");
        ctx.writeAndFlush(reply);
    }

    @Override
    public void channelInactive(ChannelHandlerContext ctx) {
        // 连接断开 → 清理
        String nodeId = nodeChannelMap.getNodeId(ctx.channel());
        if (nodeId != null) {
            registry.unregister(nodeId);
            log.warn("节点断开连接: nodeId={}", nodeId);
        }
        nodeChannelMap.unbind(ctx.channel());
    }
}
```

需要给 Message 加一个工厂方法：

```java
// Message.java 新增
public static Message createAck(String requestId, String nodeId) {
    Message msg = new Message();
    msg.setType(MessageType.REGISTER_ACK);
    msg.setBody("{\"nodeId\":\"" + nodeId + "\",\"status\":\"ok\"}");
    msg.setRequestId(requestId);
    return msg;
}
```

### 3.7 心跳超时检测：DeadNodeDetector（~45 行）

HeartbeatHandler 负责"发心跳"，但 Controller 还需要一个**独立的后台线程**来"检查谁没心跳了"。

```java
package com.heteromesh.controller.node;

import com.heteromesh.registry.ServiceInstance;
import com.heteromesh.registry.ServiceRegistry;
import io.netty.channel.Channel;
import lombok.extern.slf4j.Slf4j;

import java.util.List;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

/**
 * 定期扫描注册中心，踢出心跳超时的节点
 */
@Slf4j
public class DeadNodeDetector {

    private final ServiceRegistry registry;
    private final NodeChannelMap nodeChannelMap;
    private final long timeoutMs;
    private final ScheduledExecutorService scheduler =
            Executors.newSingleThreadScheduledExecutor(r -> {
                Thread t = new Thread(r, "dead-node-detector");
                t.setDaemon(true);  // 守护线程，JVM 退出时自动关闭
                return t;
            });

    public DeadNodeDetector(ServiceRegistry registry,
                            NodeChannelMap nodeChannelMap,
                            long timeoutMs) {
        this.registry = registry;
        this.nodeChannelMap = nodeChannelMap;
        this.timeoutMs = timeoutMs;
    }

    public void start() {
        scheduler.scheduleAtFixedRate(this::scan, 5, 5, TimeUnit.SECONDS);
        log.info("DeadNodeDetector 启动, timeout={}ms", timeoutMs);
    }

    private void scan() {
        List<ServiceInstance> instances = registry.getAllInstances();
        long now = System.currentTimeMillis();

        for (ServiceInstance node : instances) {
            if (!node.isAlive(timeoutMs)) {
                log.warn("节点心跳超时, 踢出: nodeId={}, lastHeartbeat={}ms ago",
                        node.getNodeId(), now - node.getLastHeartbeat());

                // ① 从注册中心移除
                registry.unregister(node.getNodeId());

                // ② 关闭对应的 Channel
                Channel channel = nodeChannelMap.getChannel(node.getNodeId());
                if (channel != null && channel.isActive()) {
                    channel.close();
                }
                nodeChannelMap.unbind(channel);
            }
        }
    }

    public void stop() {
        scheduler.shutdown();
    }
}
```

### 3.8 更新 heartbeat 时间戳

心跳消息到 Controller 后，要更新对应节点的 `lastHeartbeat`。这在上层 Handler 做：

```java
// 在 ServerHandler 或一个新的 HeartbeatUpdateHandler 中：
// 每次收到消息都更新 lastHeartbeat（不只是 PING/PONG）

@Override
protected void channelRead0(ChannelHandlerContext ctx, Message msg) {
    // 更新心跳时间（任何消息到达都算存活）
    String nodeId = nodeChannelMap.getNodeId(ctx.channel());
    if (nodeId != null) {
        ServiceInstance node = registry.lookup(nodeId);
        if (node != null) {
            node.setLastHeartbeat(System.currentTimeMillis());
        }
    }
    // ... 继续分发
}
```

> 这样设计的原因是：即使 PING/PONG 被 HeartbeatHandler 拦截了（不传到上层），只要 Worker 有发任何消息（包括 PING），channelRead 就会被触发，lastHeartbeat 就被更新。

**等等，PING/PONG 被 HeartbeatHandler 拦截了，不会到达 ServerHandler！** 所以更好的做法是：让 HeartbeatHandler 也在读到 PING/PONG 时更新心跳时间，或者让 ServerHandler 除了 HeartbeatHandler 之外再有一个专门的心跳更新逻辑。

最简单的方案：在 Controller 端的 HeartbeatHandler 中，收到 PING 时更新 `lastHeartbeat`：

```java
// Controller 端 HeartbeatHandler 修改
// 原来：收到 PING → 回 PONG → beatCnt 重置
// 新加：收到 PING → 更新 ServiceRegistry 里的 lastHeartbeat

// 但 HeartbeatHandler 在 heteromesh-common 模块，它不应该依赖 ServiceRegistry（那是 Controller 的事）

// 解决方案：HeartbeatHandler 增加一个回调接口
public interface HeartbeatCallback {
    void onHeartbeatReceived(ChannelHandlerContext ctx);
}
```

**或者更简单**：HeartbeatHandler 的 `channelRead` 已经把 PING/PONG 吃掉了，我们改成让它吃掉之前先更新心跳。怎么做？

**最简单方案**：不要在 HeartbeatHandler 里更新，而是让 HeartbeatHandler 把心跳事件"透传"到下一个 Handler。具体做法：HeartbeatHandler 处理完 PING/PONG 后，用 `ctx.fireChannelRead(msg)` 把消息继续传给 ServerHandler。

```java
// HeartbeatHandler.channelRead 修改：
@Override
public void channelRead(ChannelHandlerContext ctx, Object o) {
    Message msg = (Message) o;
    if (msg.getType() == MessageType.PING) {
        ctx.writeAndFlush(Message.createPong());
        beatCnt.set(0);
        // ✅ 关键改动：把 PING 透传给下一个 Handler（让它更新 lastHeartbeat）
        ctx.fireChannelRead(msg);  // ← 新增这一行
    } else if (msg.getType() == MessageType.PONG) {
        beatCnt.set(0);
        ctx.fireChannelRead(msg);  // ← 新增这一行
    } else {
        ctx.fireChannelRead(msg);  // 原本就有，透传非心跳消息
    }
}
```

这样 ServerHandler 就能收到 PING/PONG 并更新 `lastHeartbeat` 了。

## 四、Pipeline 顺序

Controller 端 Netty Pipeline 的 Handler 顺序非常重要：

```
Inbound 方向（接收消息）：
  1. LengthFieldBasedFrameDecoder  ← 粘包处理（最外层）
  2. MessageDecoder                ← 字节 → Message 对象
  3. HeartbeatHandler              ← 处理 PING/PONG，透传给下一个
  4. ServerHandler                 ← 处理 REGISTER、TASK（更新心跳时间）
  5. ExceptionHandler              ← 异常捕获（最内层）

Worker 端：
  1. LengthFieldBasedFrameDecoder
  2. MessageDecoder
  3. HeartbeatHandler              ← 处理 PONG 回复
  4. ClientHandler                 ← 处理 REGISTER_ACK、TASK_RESPONSE
  5. ExceptionHandler
```

## 六、常见错误预警

### 错误 1：Pipeline 顺序错误

```java
// ❌ HeartbeatHandler 在 ServerHandler 之后
// → PING/PONG 被 HeartbeatHandler 拦截前，ServerHandler 先收到
// → ServerHandler 不认识 PING，可能出错

// ✅ HeartbeatHandler 必须在 ServerHandler 之前！
ch.pipeline()
    .addLast(new MessageDecoder())
    .addLast(new HeartbeatHandler())  // ← 先处理心跳
    .addLast(new ServerHandler(...))  // ← 再处理业务
```

### 错误 2：ServiceInstance 字段变更后测试未更新

```java
// ServiceInstance 加了 3 个新字段（gpuType, vramFree, load）
// 旧的测试里 new ServiceInstance("id", "host", 9090, t1, t2) 会编译失败
// → 记得更新所有调用处
```

### 错误 3：channelInactive 时忘记清理

```java
// Worker 正常关闭 → channelInactive 触发 → 没有 unregister + unbind
// → ServiceRegistry 里残留死节点 → DeadNodeDetector 也要等超时才能踢
// → 测试时两个节点用同一个 nodeId，第二个注册失败

```

### 错误 4：DeadNodeDetector 线程不是 daemon

```java

// → JVM 不会退出（因为还有非守护线程在跑）
// → 测试跑完卡住不结束

// ✅ 守护线程

```

### 错误 5：忘记在 application.yml 里配路由规则

```yaml

# 记得在 YAML 里加路由规则（第 4 课的内容）：

  REGISTER: json
```

## 八、面试怎么聊

> "通信引擎跑通后，第一件事是让 Controller 能管理 Worker 节点。我设计了一个注册协议：Worker 在 TCP 连接建立后，第一条消息就是 REGISTER，以 JSON 格式携带自己的 nodeId、GPU 型号、显存等信息。Controller 收到后存入 ServiceRegistry 并回复 ACK。这样 Controller 就有了全集群的拓扑视图。"

> "节点健康检测分两层：第一层是 Netty 的 IdleStateHandler + HeartbeatHandler，负责发送和响应心跳包；第二层是 DeadNodeDetector，一个独立的守护线程每 5 秒扫描所有节点，超过 15 秒没心跳就踢出——关闭 Channel + 从注册中心移除。这其实参考了 Eureka 的自保模式和 Dubbo 的心跳机制。channelInactive 也会触发清理，覆盖正常断连场景。"
