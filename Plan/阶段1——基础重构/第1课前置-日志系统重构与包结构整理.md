## 二、Java 日志体系全景

Java 的日志生态很混乱，历史原因导致有一堆框架。你只需要理解这张图：

```
┌─────────────────────────────────────────────────────┐
│                   你的代码                            │
│         import org.slf4j.Logger;                     │
│         log.info("xxx");                            │
└─────────────────────┬───────────────────────────────┘
                      │ 调用
┌─────────────────────▼───────────────────────────────┐
│              SLF4J (门面接口)                         │
│     只定义了 Logger 接口，不干活                       │
│     类比：Java 的 JDBC 接口                          │
└─────────────────────┬───────────────────────────────┘
                      │ 绑定（classpath 上谁在就用谁）
         ┌────────────┼────────────┐
         ▼            ▼            ▼
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │ Logback │  │ Log4j2  │  │ JUL桥接 │   ← 实现层（只需要一个）
    │ (推荐)  │  │         │  │         │
    └─────────┘  └─────────┘  └─────────┘
```

**为什么用 SLF4J 而不是直接用 Logback？**

和你学过的"面向接口编程"一个道理：
- 你的代码只依赖 `slf4j-api`（接口）
- 底层实现可以随时换（Logback → Log4j2），不改一行业务代码
- Spring Boot、Netty、Dubbo 全都用 SLF4J

**类比**：
- SLF4J = USB 接口标准
- Logback = 某品牌的 U 盘
- 你的代码只认 USB 口，不关心插的是什么牌子

## 三、SLF4J 核心 API

整个 SLF4J 你只需要会 3 样东西：

### 3.1 获取 Logger

```java
// 方式一：手动获取（标准写法）
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class ExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(ExceptionHandler.class);
}

// 方式二：Lombok @Slf4j（等价于方式一，编译时自动生成上面那行）
import lombok.extern.slf4j.Slf4j;

@Slf4j
public class ExceptionHandler {
    // 编译后自动有 private static final Logger log = ...
}
```

你的项目已经有 Lombok 依赖，所以直接用 `@Slf4j` 就行。

### 3.2 日志级别（从低到高）

```
TRACE  →  DEBUG  →  INFO  →  WARN  →  ERROR
 最细       调试     正常     警告     错误
```

**什么时候用哪个级别？**

| 级别 | 用途 | 你的项目中的例子 |
|------|------|-----------------|
| TRACE | 极其详细的追踪，几乎不用 | 每个字节的编解码过程 |
| DEBUG | 开发调试信息，生产关闭 | 收到 PING/PONG、RPC 响应内容 |
| INFO | 正常业务流程的关键节点 | 服务器启动、节点注册、任务完成 |
| WARN | 不影响运行但需要注意 | 连接断开（IOException）、未知 requestId |
| ERROR | 出错了，需要人工介入 | 未预期的异常、编解码失败 |

**经验法则**：
- 如果这条日志在正常运行时每秒会打几十次 → DEBUG
- 如果这条日志只在启动/关闭/重要事件时打 → INFO
- 如果这条日志意味着"有东西不对但还能跑" → WARN
- 如果这条日志意味着"出 bug 了" → ERROR

### 3.3 占位符 `{}`

```java
// ❌ 错误：字符串拼接（每次都执行，即使日志级别不够不输出）
log.debug("收到消息: type=" + msg.getType() + ", body=" + msg.getBody());

// ✅ 正确：占位符（只在实际输出时才拼接字符串）
log.debug("收到消息: type={}, body={}", msg.getType(), msg.getBody());
```

**为什么占位符更好？**

假设你设置了 `level=INFO`，那 `log.debug(...)` 不会输出。
- 拼接写法：即使不输出，`msg.getType() + msg.getBody()` 的字符串拼接已经执行了，浪费 CPU
- 占位符写法：SLF4J 先检查级别，不够就直接 return，`{}` 里的参数根本不会被拼接

**异常堆栈的特殊写法**：

```java
// 最后一个参数如果是 Throwable，SLF4J 自动打印完整堆栈
log.error("处理消息时发生异常: channel={}", ctx.channel().id().asShortText(), cause);
//                                                                          ↑
//                                                          这个 cause 会自动打印堆栈
```

这比 `cause.printStackTrace()` 好在哪？
- 堆栈信息和日志在同一个输出流里，不会交错
- 带时间戳和线程名，能定位是哪个连接出的问题
- 可以输出到文件，不会丢失

## 四、Logback 配置详解

你的项目在 `src/main/resources/logback.xml` 里配置 Logback。

### 4.1 最小配置（你现在用的）

```xml
<configuration>
    <!-- Appender = 日志输出到哪里 -->
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 你的代码包：DEBUG 级别以上都输出 -->
    <logger name="com.heteromesh" level="DEBUG"/>
    
    <!-- Netty 框架：只输出 INFO 以上（避免刷屏） -->
    <logger name="io.netty" level="INFO"/>

    <!-- 全局默认：INFO -->
    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
```

### 4.2 Pattern 格式解读

`%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n`

| 占位符 | 含义 | 输出示例 |
|--------|------|----------|
| `%d{HH:mm:ss.SSS}` | 时间（时:分:秒.毫秒） | `14:23:15.123` |
| `%thread` | 线程名 | `nioEventLoopGroup-3-1` |
| `%-5level` | 级别，左对齐占 5 字符 | `INFO ` / `ERROR` |
| `%logger{36}` | 类名，最长 36 字符 | `c.h.transport.ExceptionHandler` |
| `%msg` | 你写的日志内容 | `连接断开: channel=abc123` |
| `%n` | 换行 | |

实际输出效果：
```
14:23:15.123 [nioEventLoopGroup-3-1] ERROR c.h.transport.ExceptionHandler - 连接断开: channel=abc123
```

### 4.3 文件输出 + 滚动（生产环境用）

```xml
<configuration>
    <!-- 控制台输出 -->
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 文件输出：按天滚动，保留 7 天 -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/heteromesh.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>logs/heteromesh.%d{yyyy-MM-dd}.log</fileNamePattern>
            <maxHistory>7</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{50} - %msg%n</pattern>
        </encoder>
    </appender>

    <logger name="com.heteromesh" level="DEBUG"/>
    <logger name="io.netty" level="INFO"/>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
        <appender-ref ref="FILE"/>
    </root>
</configuration>
```

这节课你只用控制台输出就够了，文件输出是给你看看生产环境怎么配的。

## 五、Logger 层级机制

Logback 的 Logger 是有层级的，和 Java 包结构一一对应：

```
root                          level=INFO    ← 全局默认
└── com
    └── heteromesh            level=DEBUG   ← 你配的
        ├── protocol          继承 DEBUG
        ├── transport         继承 DEBUG
        └── controller        继承 DEBUG
```

**规则**：子 Logger 没有显式设置 level 时，继承父 Logger 的 level。

所以你只需要设 `com.heteromesh` 为 DEBUG，下面所有子包自动都是 DEBUG。

如果某个包太吵（比如心跳每 5 秒打一次），可以单独压制：
```xml
<logger name="com.heteromesh.transport.HeartbeatHandler" level="INFO"/>
```

## 六、包结构整理的设计思路

当前你的包结构：

```
com.heteromesh/
├── protocol/     Message, MessageType, MessageSerializer,
│                 MessageEncoder, MessageDecoder, MessageCodec
└── transport/    ExceptionHandler, HeartbeatHandler,
                  ConnectionManager, RpcClient
```

问题：`protocol/` 里混了"协议定义"和"序列化实现"，`transport/` 里混了"传输层"和"RPC 逻辑"。

这节课我们先不大动，只做一件事：**确认现有代码能跑，加上日志**。包结构的大调整放到第 2 课（抽取 Serializer 接口时自然会拆包）。

但你需要理解目标结构的设计原则：

| 包名 | 职责 | 类比 |
|------|------|------|
| `protocol/` | 协议定义（消息格式、类型枚举、编解码） | HTTP 协议规范 |
| `serializer/` | 序列化实现（JSON、Binary、Kryo） | 内容编码（gzip、deflate） |
| `transport/` | 传输层（心跳、异常、连接管理） | TCP 连接管理 |
| `rpc/` | RPC 逻辑（请求匹配、超时、代理） | HTTP Client |
| `registry/` | 注册中心（节点注册、发现） | DNS |
| `loadbalance/` | 负载均衡（选哪个节点） | Nginx upstream |
| `faulttolerance/` | 容错（重试、熔断、限流） | Hystrix |

**单一职责原则**：每个包只做一件事。当你说"这个类放哪个包"犹豫时，问自己：它的核心职责是什么？

## 七、Lombok @Slf4j 的工作原理

你可能好奇：`@Slf4j` 注解是怎么变成 `log` 变量的？

```java
// 你写的源码
@Slf4j
public class ExceptionHandler extends ChannelInboundHandlerAdapter {
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
        log.error("异常: {}", cause.getMessage(), cause);
    }
}

// Lombok 在编译时（javac 阶段）自动插入的代码
public class ExceptionHandler extends ChannelInboundHandlerAdapter {
    private static final org.slf4j.Logger log =
        org.slf4j.LoggerFactory.getLogger(ExceptionHandler.class);
    
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
        log.error("异常: {}", cause.getMessage(), cause);
    }
}
```

**关键点**：
- `log` 是 `private static final` — 类级别共享，不是每个对象一份
- `getLogger(ExceptionHandler.class)` — Logger 名字就是类的全限定名，日志里能看到是哪个类打的
- 编译时处理 — 运行时没有任何性能开销，和手写完全一样

## 九、常见错误

### 错误 1：忘记加 Lombok 依赖

你的项目已经有了，不用担心。但如果报 `log cannot be resolved`，检查 IDE 是否安装了 Lombok 插件。

### 错误 2：异常堆栈丢失

```java
// ❌ 错误：cause 被当成普通参数，堆栈丢失
log.error("异常: {}", cause);

// ✅ 正确：cause 作为最后一个 Throwable 参数，堆栈自动打印
log.error("异常: {}", cause.getMessage(), cause);
```

规则：如果最后一个参数是 `Throwable` 类型，SLF4J 会自动打印它的堆栈。但如果你把它放在 `{}` 对应的位置，它就只会调用 `toString()`。

### 错误 3：在循环里打 INFO

```java
// ❌ 1000 条消息每条都打 INFO，日志刷屏
for (Message msg : messages) {
    log.info("处理消息: {}", msg.getId());
}

// ✅ 循环内用 DEBUG，循环外用 INFO 汇总
log.info("开始处理 {} 条消息", messages.size());
for (Message msg : messages) {
    log.debug("处理消息: {}", msg.getId());
}
log.info("处理完成");
```
