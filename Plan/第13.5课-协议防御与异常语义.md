## 一、这节课解决什么问题？

### 1.1 当前问题

现在 `MessageDecoder` 的核心逻辑大概是这样：

```java
frame.readInt();       // 魔数，但没有校验
frame.readByte();      // 版本，但没有校验
byte serializerCode = frame.readByte();
frame.readByte();      // type，但没有校验
int length = frame.readInt();
byte[] bytes = new byte[length];
frame.readBytes(bytes);
```

这段代码能跑，但它有一个工程问题：

> 它默认网络上的每个包都是好人。

真实网络入口不能这样写。客户端可能发错协议、旧版本协议、恶意超大 length、非法消息类型。Decoder 是第一道门，应该尽早拒绝非法包，不要把脏数据交给业务层。

### 1.2 本课改造后的效果

```java
int magic = frame.readInt();
if (magic != MessageEncoder.MAGIC_NUMBER) {
    throw new CorruptedFrameException("Invalid magic number: " + Integer.toHexString(magic));
}

byte version = frame.readByte();
if (version != MessageEncoder.VERSION) {
    throw new CorruptedFrameException("Unsupported protocol version: " + version);
}

byte serializerCode = frame.readByte();
Serializer serializer = SerializerRouter.getByCode(serializerCode);

byte typeCode = frame.readByte();
MessageType.fromCode(typeCode); // 只为校验是否合法

int length = frame.readInt();
if (length < 0 || length > MessageEncoder.MAX_FRAME_LENGTH - MessageEncoder.HEADER_LENGTH) {
    throw new CorruptedFrameException("Invalid body length: " + length);
}

byte[] bytes = new byte[length];
frame.readBytes(bytes);
return serializer.deserialize(bytes);
```

你最终手敲出来的代码不一定要和上面一模一样，但判断逻辑要等价。

## 二、参考主流项目怎么做

### 2.1 Dubbo：协议头先校验

Dubbo 的自定义协议里也有 magic、flag、status、requestId、body length。它不会一上来就把 body 丢给业务处理，而是先判断：

- 是不是 Dubbo 协议
- 序列化方式是否合法
- body 长度是否超过限制
- 请求/响应标识是否正确

HeteroMesh 这一课学的是同一个思想：

> 网络入口处先做协议合法性校验，非法包不进入业务 Handler。

### 2.2 Netty：Decoder 是协议边界

Netty 的 Pipeline 通常是：

```text
ByteBuf -> FrameDecoder -> MessageDecoder -> BusinessHandler
```

`LengthFieldBasedFrameDecoder` 只负责把 TCP 字节流切成一帧一帧：

```text
解决的是：这个包完整了吗？
不解决：这个包是我的协议吗？版本对吗？类型合法吗？
```

所以本课要在 `MessageDecoder` 里补第二层判断。

### 2.3 Kafka / Redis / HTTP2 的共同点

这些系统虽然协议不同，但入口设计都类似：

| 项目 | 入口校验 |
|------|----------|
| Kafka | 先解析 request header，根据 apiKey/apiVersion 分发 |
| Redis RESP | 先检查 `*`、`$`、`+` 等协议前缀和长度 |
| HTTP2 | 校验 frame type、flags、stream id、payload length |

结论：

> 自定义协议不是只把字段写进去，还要能拒绝不属于你的字段组合。

## 三、先统一协议常量

### 3.1 为什么要统一？

现在 `MessageEncoder` 里有：

```java
private static final int MAGIC_NUMBER = 0xCAFEBABE;
private static final byte VERSION = 0X01;
public static final int HEADER_LENGTH = 11;
```

问题是：

- `MAGIC_NUMBER` 和 `VERSION` 是 private，Decoder 不能复用
- Decoder 里 `super(1024 * 1024, 7, 4, 0, 0)` 写死了最大帧长度
- 如果 Encoder 和 Decoder 常量不一致，协议会变得很危险

### 3.2 你要改成这样

位置：`heteromesh-common/src/main/java/com/heteromesh/protocol/MessageEncoder.java`

```java
public class MessageEncoder extends MessageToByteEncoder<Message> {
    public static final int MAGIC_NUMBER = 0xCAFEBABE;
    public static final byte VERSION = 0x01;
    public static final int HEADER_LENGTH = 11;
    public static final int MAX_FRAME_LENGTH = 1024 * 1024;

    @Override
    protected void encode(ChannelHandlerContext ctx, Message msg, ByteBuf out) {
        byte[] bytes = SerializerRouter.select(msg).serialize(msg);

        out.writeInt(MAGIC_NUMBER);
        out.writeByte(VERSION);
        out.writeByte(SerializerRouter.getCode(msg));
        out.writeByte(msg.getType().getCode());
        out.writeInt(bytes.length);
        out.writeBytes(bytes);
    }
}
```

注意：

这里没有让你新增 `ProtocolConstants`，因为本课目标是小步改造。等协议字段越来越多，再抽常量类。

## 四、改造 MessageDecoder

### 4.1 原来的 Decoder

位置：`heteromesh-common/src/main/java/com/heteromesh/protocol/MessageDecoder.java`

当前代码大致是：

```java
public class MessageDecoder extends LengthFieldBasedFrameDecoder {
    public MessageDecoder() {
        super(1024 * 1024, 7, 4, 0, 0);
    }

    @Override
    protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
        ByteBuf frame = (ByteBuf) super.decode(ctx, in);
        if (frame == null) {
            return null;
        }

        frame.readInt();
        frame.readByte();
        byte serializerCode = frame.readByte();
        frame.readByte();
        int length = frame.readInt();

        byte[] bytes = new byte[length];
        frame.readBytes(bytes);

        Serializer s = SerializerRouter.getByCode(serializerCode);
        return s.deserialize(bytes);
    }
}
```

### 4.2 你要手敲的新结构

你可以照这个结构写，但每个 `if` 里的判断和异常信息你要自己手敲一遍，别复制粘贴。

```java
package com.heteromesh.protocol;

import com.heteromesh.serializer.Serializer;
import com.heteromesh.serializer.SerializerRouter;
import io.netty.buffer.ByteBuf;
import io.netty.channel.ChannelHandlerContext;
import io.netty.handler.codec.CorruptedFrameException;
import io.netty.handler.codec.LengthFieldBasedFrameDecoder;

public class MessageDecoder extends LengthFieldBasedFrameDecoder {

    public MessageDecoder() {
        super(MessageEncoder.MAX_FRAME_LENGTH, 7, 4, 0, 0);
    }

    @Override
    protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
        ByteBuf frame = (ByteBuf) super.decode(ctx, in);
        if (frame == null) {
            return null;
        }

        int magic = frame.readInt();
        // TODO 1: 校验 magic，不等于 MessageEncoder.MAGIC_NUMBER 时抛 CorruptedFrameException

        byte version = frame.readByte();
        // TODO 2: 校验 version，不等于 MessageEncoder.VERSION 时抛 CorruptedFrameException

        byte serializerCode = frame.readByte();
        Serializer serializer = SerializerRouter.getByCode(serializerCode);

        byte typeCode = frame.readByte();
        // TODO 3: 调用 MessageType.fromCode(typeCode)，只为校验 typeCode 是否合法

        int length = frame.readInt();
        // TODO 4: 校验 length：不能小于 0，不能超过 MAX_FRAME_LENGTH - HEADER_LENGTH
        // TODO 5: 校验 frame.readableBytes() 是否足够读取 length 个字节

        byte[] bytes = new byte[length];
        frame.readBytes(bytes);

        return serializer.deserialize(bytes);
    }
}
```

### 4.3 每个 TODO 的写法示例

#### TODO 1：magic 校验

```java
if (magic != MessageEncoder.MAGIC_NUMBER) {
    throw new CorruptedFrameException(
            "Invalid magic number: " + Integer.toHexString(magic));
}
```

为什么用 `Integer.toHexString`？

因为 magic 通常用十六进制表达。看到 `cafebabe` 比看到 `-889275714` 更直观。

#### TODO 2：version 校验

```java
if (version != MessageEncoder.VERSION) {
    throw new CorruptedFrameException(
            "Unsupported protocol version: " + version);
}
```

这个字段现在看起来只有一个值，但未来协议升级会用到。

#### TODO 3：type 校验

```java
MessageType.fromCode(typeCode);
```

为什么不接返回值？

因为 body 里的 `Message` 反序列化后也带 type。这里的目的是让协议头里的 typeCode 不要是非法值。

如果你想写得更清楚，也可以这样：

```java
MessageType headerType = MessageType.fromCode(typeCode);
```

即使暂时不用 `headerType`，代码可读性会更好。

#### TODO 4：length 范围校验

```java
int maxBodyLength = MessageEncoder.MAX_FRAME_LENGTH - MessageEncoder.HEADER_LENGTH;
if (length < 0 || length > maxBodyLength) {
    throw new CorruptedFrameException("Invalid body length: " + length);
}
```

注意：

`MAX_FRAME_LENGTH` 表示整帧最大长度，body 最大长度应该减掉 header。

#### TODO 5：readableBytes 校验

```java
if (frame.readableBytes() < length) {
    throw new CorruptedFrameException(
            "Frame body is incomplete, expected " + length
                    + " bytes, actual " + frame.readableBytes());
}
```

理论上 `LengthFieldBasedFrameDecoder` 已经保证完整帧了，但这里保留校验有两个价值：

1. 代码语义更完整
2. 如果未来调整 lengthFieldOffset 或 header 格式，这里能更快暴露问题

## 五、完整参考版本

下面是完整参考版本。你可以对照理解，但建议你不要复制，自己打开文件手敲。

```java
public class MessageDecoder extends LengthFieldBasedFrameDecoder {
    public MessageDecoder() {
        super(MessageEncoder.MAX_FRAME_LENGTH, 7, 4, 0, 0);
    }

    @Override
    protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
        ByteBuf frame = (ByteBuf) super.decode(ctx, in);
        if (frame == null) {
            return null;
        }

        int magic = frame.readInt();
        if (magic != MessageEncoder.MAGIC_NUMBER) {
            throw new CorruptedFrameException(
                    "Invalid magic number: " + Integer.toHexString(magic));
        }

        byte version = frame.readByte();
        if (version != MessageEncoder.VERSION) {
            throw new CorruptedFrameException(
                    "Unsupported protocol version: " + version);
        }

        byte serializerCode = frame.readByte();
        Serializer serializer = SerializerRouter.getByCode(serializerCode);

        byte typeCode = frame.readByte();
        MessageType.fromCode(typeCode);

        int length = frame.readInt();
        int maxBodyLength = MessageEncoder.MAX_FRAME_LENGTH - MessageEncoder.HEADER_LENGTH;
        if (length < 0 || length > maxBodyLength) {
            throw new CorruptedFrameException("Invalid body length: " + length);
        }

        if (frame.readableBytes() < length) {
            throw new CorruptedFrameException(
                    "Frame body is incomplete, expected " + length
                            + " bytes, actual " + frame.readableBytes());
        }

        byte[] bytes = new byte[length];
        frame.readBytes(bytes);

        return serializer.deserialize(bytes);
    }
}
```

## 六、常见错误预警

### 错误 1：HEADER_LENGTH 又写错成 10

```text
Magic(4) + Version(1) + SerializerCode(1) + Type(1) + Length(4) = 11
```

这里很容易算漏 `SerializerCode`。

### 错误 2：校验 type 时写成 readInt

```java
// 错误
int typeCode = frame.readInt();

// 正确
byte typeCode = frame.readByte();
```

协议头里的 Type 是 1 个字节，不是 4 个字节。

### 错误 3：先读 body 再校验 length

```java
// 错误顺序
byte[] bytes = new byte[length];
frame.readBytes(bytes);
if (length < 0) { ... }
```

如果 length 是负数或异常大，创建数组时就已经出问题了。必须先校验，再申请数组。

### 错误 4：把非法协议交给 ServerHandler

不要这么做。`ServerHandler` 处理的是合法 `Message` 的业务语义，非法二进制帧应该在 Decoder 阶段就被拒绝。

## 八、面试怎么讲

可以这样讲：

> HeteroMesh 的协议头是 11 字节，包含 magic、version、serializerCode、messageType 和 body length。早期只依赖 LengthFieldBasedFrameDecoder 切出完整帧，但它只能保证字节流被切完整，不能保证这是合法的 HeteroMesh 协议。所以我在 MessageDecoder 里补了协议防御：校验 magic 防止非本协议流量进入，校验 version 支持协议演进，校验 type 和 serializerCode 防止非法消息进入业务层，校验 length 防止异常长度导致内存风险。

如果面试官问：

> 为什么不用 HTTP/gRPC？

可以回答：

> 生产环境当然可以用成熟协议，但这个项目目标是学习 RPC 框架底层。我手写协议是为了掌握粘包拆包、协议头设计、序列化路由和 requestId 匹配。为了避免它只是 demo，我也补了协议入口防御和测试。
