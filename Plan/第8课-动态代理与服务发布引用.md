## 一、这节课解决什么问题？

### 当前状态 vs 目标

```
当前（第 7 课后）——想调一个远程方法：

  ① 构造 Message
     Message req = Message.createTaskRequest("你好");
  
  ② 通过 RpcClient 发送
     CompletableFuture<Message> future = rpcClient.call("你好");
  
  ③ 等待响应
     future.thenAccept(response -> {
         String result = response.getBody();  ← 拿到的还是原始字符串
         // 自己解析、自己转型……
     });

  → 每一步都是「网络编程」，不是「RPC 编程」
  → 调用方必须知道 Message、MessageType、requestId、序列化格式


这节课后——同样调一个远程方法：

  // ① 引用远程服务（拿到一个本地代理）
  TaskService service = RpcProxy.reference(TaskService.class, rpcClient);

  // ② 像调本地方法一样调用
  String result = service.processImage("img.jpg");
  //           ↑ 完全不知道底层有网络、序列化、负载均衡


Worker 端也一样简洁：

  // ① 发布服务
  RpcServiceRegistry registry = new RpcServiceRegistry();
  registry.publish(TaskService.class, new TaskServiceImpl());

  // ② 收到请求时自动反射调用 → 不需要手写 if-else 分发
```

### 为什么这才是「真正的 RPC 味」？

RPC（Remote Procedure Call）的核心思想是 **「让远程调用看起来像本地调用」**。这个「看起来像」靠的就是**动态代理**——调用方拿到的不是真实的实现类，而是一个 JVM 在运行时生成的代理对象。代理对象拦截你的方法调用，把「方法名 + 参数」打包发到网络对面，等对面执行完再把结果传回来。

```
你写的代码：                         实际发生的事：
                                    
service.processImage("img.jpg")     proxy.invoke()
     ↓                                  ↓
  [代理对象] ──序列化──→ 网络 ──→ [真实实现]
     ↑                                  ↓
     └──────── 网络 ←──反序列化 ←──── processImage("img.jpg")
                                          ↓
                                     return "处理完成"
```

Dubbo 的 `@DubboReference` 和 `@DubboService`、gRPC 的 stub、Spring Cloud OpenFeign——全是这个原理。这节课就是把 HeteroMesh 从「网络消息框架」升级为「RPC 框架」的关键一步。

## 二、动态代理原理（JDK Proxy）

### 2.1 什么是动态代理？

Java 提供了 `java.lang.reflect.Proxy`，可以在**运行时**凭空生成一个实现了指定接口的类，这个类会把所有方法调用转发给你指定的 `InvocationHandler`：

```java
// 你不用写 TaskServiceProxy 这个类，JVM 帮你生成
TaskService proxy = (TaskService) Proxy.newProxyInstance(
    TaskService.class.getClassLoader(),       // 类加载器
    new Class[]{ TaskService.class },          // 要实现的接口
    new InvocationHandler() {                  // 方法调用拦截器
        @Override
        public Object invoke(Object proxy, Method method, Object[] args) {
            // 每次调 proxy 的任何方法，都会进这里！
            System.out.println("有人调了: " + method.getName());
            return "假的返回值";
        }
    }
);

proxy.processImage("test.jpg");
// 输出：有人调了: processImage
// 但根本没执行真正的 processImage——被 InvocationHandler 拦截了
```

### 2.2 RPC 框架怎么利用这个？

```
InvocationHandler.invoke() 里做的事：

  ① 获取方法名、参数类型、参数值
       ↓
  ② 打包成 RpcInvocation 对象（可序列化）
       ↓
  ③ 序列化成 JSON，通过 Netty 发到远程
       ↓
  ④ 等待响应（CompletableFuture）
       ↓
  ⑤ 拿到响应 → 反序列化 → return 给调用方
  
  调用方全程以为自己在调本地方法。
```

### 2.3 对比：为什么不用静态代理？

```java
// ❌ 静态代理：每加一个接口，你就要手写一个代理类
public class TaskServiceProxy implements TaskService {
    private RpcClient client;
    
    @Override
    public String processImage(String path) {
        // 打包、发送、等回复、解包……
        // 100 个方法 → 手写 100 遍
    }
}

// ✅ 动态代理：加 100 个接口，0 行额外代理代码
TaskService ts = RpcProxy.reference(TaskService.class, rpcClient);
UserService us = RpcProxy.reference(UserService.class, rpcClient);
OrderService os = RpcProxy.reference(OrderService.class, rpcClient);
// 三个接口，同一套逻辑，没有重复代码
```

## 三、核心数据结构：RpcInvocation

### 3.1 要跨网络传输一个方法调用，需要哪些信息？

```
在本地调用：
  service.processImage("img.jpg", 300, true)

要把它变成一个「可以在任意 JVM 里重放」的数据结构，需要 4 样东西：
  ① 接口名      "com.heteromesh.demo.TaskService"    ← 知道找哪个服务
  ② 方法名      "processImage"                        ← 知道调哪个方法
  ③ 参数类型列表 ["java.lang.String", "int", "boolean"] ← 处理方法重载
  ④ 参数值列表   ["img.jpg", 300, true]                ← 传给方法的实际参数
```

**为什么需要「参数类型列表」？**

```java
// Java 允许方法重载：
public interface TaskService {
    String processImage(String path);          // 方法 1
    String processImage(byte[] imageData);     // 方法 2：同名，参数类型不同
}

// 如果没有参数类型，收到 "processImage" + ["img.jpg"] 时，
// 你无法确定该调方法 1 还是方法 2（"img.jpg" 既是 String 也是 byte[] 的合法内容）

// 有了参数类型列表：["java.lang.String"] → 明确了，调方法 1
```

### 3.2 RpcInvocation 设计

```java
// 这 6 个字段 = 一次方法调用的完整自描述
String serviceName;       // 接口全限定名，如 "com.heteromesh.demo.TaskService"
String methodName;        // 方法名，如 "processImage"
String[] parameterTypes;  // 参数类型全限定名，如 ["java.lang.String", "int"]
Object[] args;            // 参数值，如 ["img.jpg", 300]
String requestId;         // 请求 ID（复用 Message 的 requestId，用于匹配响应）
boolean oneWay;           // 是否单向调用（发了不管结果，适合日志、通知类方法）
```

序列化后变成 JSON，放在 TASK_REQUEST 的 body 里：

```json
{
  "serviceName": "com.heteromesh.demo.TaskService",
  "methodName": "processImage",
  "parameterTypes": ["java.lang.String"],
  "args": ["/path/to/image.jpg"],
  "requestId": "a1b2c3d4-...",
  "oneWay": false
}
```

## 四、调用链路全景图

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Client（服务消费者）                           │
│                                                                      │
│  String result = service.processImage("img.jpg");                    │
│       ↓                                                              │
│  ┌──────────────────────────────────────────┐                        │
│  │ RpcProxy (InvocationHandler)              │                        │
│  │  ① 构造 RpcInvocation                     │                        │
│  │  ② 序列化为 JSON                          │                        │
│  │  ③ rpcClient.call(invocationJson)         │                        │
│  │  ④ future.get() 等结果                    │                        │
│  │  ⑤ 反序列化 result → 返回给调用方          │                        │
│  └──────────────────────────────────────────┘                        │
│       ↓ (通过已有的 Netty Channel)                                    │
└───────┼──────────────────────────────────────────────────────────────┘
        │
        │  TASK_REQUEST { body: RpcInvocation JSON }
        ↓
┌───────────────────────────────────────────────────────────────────────┐
│                      Controller（路由器）                              │
│   ServerHandler.handleTaskRequest()                                   │
│     → loadBalancer.select(requestId)   ← 选一个 Worker                │
│     → 转发 TASK_REQUEST 到 Worker                                     │
└───────┼───────────────────────────────────────────────────────────────┘
        │
        │  TASK_REQUEST { body: RpcInvocation JSON }
        ↓
┌───────────────────────────────────────────────────────────────────────┐
│                       Worker（服务提供者）                             │
│                                                                        │
│  ClientHandler.handleTaskRequest()                                     │
│     → RpcDispatcher.dispatch(invocation)                               │
│       ① 反序列化 body → RpcInvocation                                  │
│       ② registry.lookup(invocation.serviceName) → 找到实现对象         │
│       ③ method.invoke(instance, invocation.args)  ← 反射调用！         │
│       ④ 拿到 return 值                                                 │
│     → 构造 TASK_RESPONSE { body: result JSON }                         │
│     → ctx.writeAndFlush(response)                                     │
└───────┼───────────────────────────────────────────────────────────────┘
        │
        │  TASK_RESPONSE { body: "\"处理完成\"" }
        ↓
      原路返回 → Controller → Client → RpcProxy → future.complete()
                                                         ↓
                                            service.processImage() 返回 "处理完成"
```

**要点**：Controller 不用改任何代码——它只是透明转发 TASK_REQUEST / TASK_RESPONSE。真正的变化发生在两端：Client 端多了代理层，Worker 端多了反射分发层。

## 五、你要写的代码

### 5.1 RpcInvocation（~40 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RpcInvocation.java`

**为什么需要这个类？**
- 之前 TASK_REQUEST 的 body 是裸字符串（如 `"你好"`），调用方和实现方约定好「你发什么我回什么」
- 现在需要一个**结构化的方法调用描述**，让 Worker 知道自己该调哪个类的哪个方法、传什么参数
- **和原来的区别**：TASK_REQUEST 的 body 从自由格式字符串变成 RpcInvocation 的 JSON 序列化

```java
package com.heteromesh.rpc;

import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

/**
 * RPC 调用描述符，序列化后放在 TASK_REQUEST 的 body 里。
 * 包含了「在远程 JVM 重放一次方法调用」所需的全部信息。
 */
@Data
@NoArgsConstructor
@AllArgsConstructor
public class RpcInvocation {

    /** 接口全限定名，如 "com.heteromesh.demo.TaskService" */
    private String serviceName;

    /** 方法名，如 "processImage" */
    private String methodName;

    /** 参数类型全限定名数组，用于解决重载方法的路由 */
    private String[] parameterTypes;

    /** 参数值数组（JSON 序列化后的原始值） */
    private Object[] args;

    /** 请求 ID，用于匹配响应 */
    private String requestId;

    /** 单向调用：true = 发了不管结果，适合日志/通知类场景 */
    private boolean oneWay;
}
```

**为什么用 `Object[]` 存参数而不是 `String[]`？**

因为参数可能是数字、布尔值等非字符串类型。Gson 反序列化 JSON 时会自动还原类型：
- `"img.jpg"` → String
- `300` → 会被 Gson 解析为 `Double`（Gson 的默认行为，需要特殊处理）
- `true` → Boolean

**Gson 数字类型陷阱**：Gson 默认把所有数字解析成 `Double`，这意味着如果你的方法参数是 `int`，反射调用时会报 `IllegalArgumentException: argument type mismatch`。我们会在 RpcDispatcher 里处理这个转换。

### 5.2 RpcProxy（~65 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RpcProxy.java`

**为什么需要这个类？**
- 封装 JDK 动态代理的创建逻辑，让调用方一行代码拿到代理
- 封装「方法调用 → RpcInvocation → 发消息 → 等响应 → 解包」的完整逻辑
- **和原来的区别**：原来调用方需要手动调 `rpcClient.call()` 并处理 `CompletableFuture<Message>`，现在一行 `RpcProxy.reference()` 搞定

```java
package com.heteromesh.rpc;

import com.google.gson.Gson;
import com.heteromesh.protocol.Message;
import com.heteromesh.transport.RpcClient;
import lombok.extern.slf4j.Slf4j;

import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

@Slf4j
public class RpcProxy {

    private static final Gson GSON = new Gson();
    private static final long DEFAULT_TIMEOUT_MS = 30_000;

    /**
     * 引用一个远程服务，返回动态代理对象。
     *
     * @param interfaceClass 服务接口的 Class 对象
     * @param rpcClient      底层 RPC 客户端（封装了 Netty Channel + pendingRequests）
     * @return 代理对象，可以强转为 interfaceClass 类型
     */
    @SuppressWarnings("unchecked")
    public static <T> T reference(Class<T> interfaceClass, RpcClient rpcClient) {
        return (T) Proxy.newProxyInstance(
                interfaceClass.getClassLoader(),
                new Class<?>[]{interfaceClass},
                new RpcInvocationHandler(rpcClient, interfaceClass)
        );
    }

    /**
     * 拦截所有代理对象的方法调用，转为 RPC 请求。
     */
    private record RpcInvocationHandler(RpcClient rpcClient,
                                         Class<?> interfaceClass) implements InvocationHandler {

        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            // ① Object 的方法（toString / equals / hashCode）不走远程
            if (method.getDeclaringClass() == Object.class) {
                return method.invoke(this, args);
            }

            // ② 构造 RpcInvocation
            RpcInvocation invocation = new RpcInvocation();
            invocation.setServiceName(interfaceClass.getName());
            invocation.setMethodName(method.getName());
            invocation.setParameterTypes(getParameterTypeNames(method));
            invocation.setArgs(args != null ? args : new Object[0]);

            // ③ 发送 RPC 请求
            String body = GSON.toJson(invocation);
            CompletableFuture<Message> future = rpcClient.call(body);

            // ④ 处理返回值
            if (method.getReturnType() == void.class || method.getReturnType() == Void.class) {
                // void 方法：不等结果，直接返回 null
                return null;
            }

            if (method.getReturnType() == CompletableFuture.class) {
                // 异步方法：把 CompletableFuture<Message> 转成 CompletableFuture<实际类型>
                return future.thenApply(msg -> {
                    // 这里只能拿到 Message，实际类型需要调用方自己转换
                    // 简化处理：返回 body 原始字符串
                    return msg.getBody();
                });
            }

            // ⑤ 同步方法：阻塞等待，直到拿到响应
            Message response = future.get(DEFAULT_TIMEOUT_MS, TimeUnit.MILLISECONDS);
            String responseBody = response.getBody();
            if (responseBody == null || responseBody.isEmpty()) {
                return null;
            }

            // ⑥ 反序列化返回值
            return GSON.fromJson(responseBody, method.getReturnType());
        }

        private String[] getParameterTypeNames(Method method) {
            Class<?>[] types = method.getParameterTypes();
            String[] names = new String[types.length];
            for (int i = 0; i < types.length; i++) {
                names[i] = types[i].getName();
            }
            return names;
        }
    }
}
```

**关键设计决策①：为什么用 `record` 而不是普通内部类？**

`RpcInvocationHandler` 的数据就是 `(rpcClient, interfaceClass)` 这个二元组，天然适合用 record——自动生成构造函数、equals、hashCode、toString。Java 21 的 record 特性。

**关键设计决策②：Object 的方法为什么走本地？**

```java
if (method.getDeclaringClass() == Object.class) {
    return method.invoke(this, args);
}
```

`toString()`、`equals()`、`hashCode()` 这三个方法定义在 `Object` 类里，代理对象也有它们。如果把它们也发到远程去执行，完全是浪费——而且远程根本没有这个代理对象，会出错。

**关键设计决策③：同步 vs 异步**

```
接口方法返回值          →   代理行为
────────────────────────────────────────────
void                   →   发了不管，立刻返回 null
CompletableFuture<T>   →   立刻返回 future，调用方自己等
String / int / 对象     →   阻塞等待，拿到结果后返回
```

**关键设计决策④：为什么参数类型要用全限定名字符串，而不是直接传 Class 对象？**

因为 `RpcInvocation` 要序列化成 JSON 跨网络传输。`Class` 对象不能直接 JSON 序列化，而且不同 JVM 里的 `Class` 对象不是同一个。用字符串 `"java.lang.String"` 就够了——Worker 端可以用 `Class.forName()` 加载。

### 5.3 RpcServiceRegistry（~30 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RpcServiceRegistry.java`

**为什么需要这个类？**
- Worker 可以有多个服务（TaskService、UserService、OrderService……），需要一个地方统一管理
- 收到 RpcInvocation 后，用 `serviceName` 快速查到这个服务的实现对象
- **对标的功能**：Dubbo 的 `ServiceRepository`、Spring 的 `ApplicationContext`

```java
package com.heteromesh.rpc;

import lombok.extern.slf4j.Slf4j;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * 本地服务注册表：管理当前 Worker 暴露了哪些服务。
 * 一个 Worker 可以暴露多个服务（如 TaskService、UserService）。
 */
@Slf4j
public class RpcServiceRegistry {

    // serviceName → 实现对象
    private final Map<String, Object> services = new ConcurrentHashMap<>();

    /**
     * 发布一个服务。
     *
     * @param interfaceClass 服务接口（用于获取 serviceName）
     * @param implementation 实现对象
     */
    public <T> void publish(Class<T> interfaceClass, T implementation) {
        String serviceName = interfaceClass.getName();
        Object old = services.put(serviceName, implementation);
        if (old != null) {
            log.warn("服务重复发布, 覆盖旧实现: serviceName={}", serviceName);
        } else {
            log.info("服务发布成功: serviceName={}", serviceName);
        }
    }

    /**
     * 查找服务实现。
     * @return 实现对象，未找到时返回 null
     */
    public Object lookup(String serviceName) {
        return services.get(serviceName);
    }

    /**
     * 取消发布。
     */
    public void unpublish(Class<?> interfaceClass) {
        services.remove(interfaceClass.getName());
    }

    public int size() {
        return services.size();
    }
}
```

**为什么用 `ConcurrentHashMap`？**

虽然当前场景是启动时注册、运行时不变化（写一次读多次），但 ConcurrentHashMap 保证了「注册」和「查找」之间的可见性——发布服务后立刻就能被查找到，没有竞态。HashMap 不保证跨线程可见性。

### 5.4 RpcDispatcher（~50 行）

位置：`heteromesh-common/src/main/java/com/heteromesh/rpc/RpcDispatcher.java`

**为什么需要这个类？**
- 收到 TASK_REQUEST 后，需要把 RpcInvocation 转成真正的反射调用
- 封装「查服务 → 匹配方法 → 转换参数类型 → 反射调用 → 返回结果」的完整流程
- **和原来的区别**：原来 `ClientHandler.handleTaskRequest` 是直接拼字符串 echo，现在是真正的反射分发

```java
package com.heteromesh.rpc;

import com.google.gson.Gson;
import lombok.extern.slf4j.Slf4j;

import java.lang.reflect.Method;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * RPC 调用分发器：根据 RpcInvocation 找到服务实现并反射调用。
 */
@Slf4j
public class RpcDispatcher {

    private static final Gson GSON = new Gson();

    private final RpcServiceRegistry registry;

    // 缓存 Method 对象，避免每次调用都做反射查找
    // key = "serviceName#methodName#paramType1,paramType2,..."
    private final Map<String, Method> methodCache = new ConcurrentHashMap<>();

    public RpcDispatcher(RpcServiceRegistry registry) {
        this.registry = registry;
    }

    /**
     * 分发一个 RPC 调用：查服务 → 匹配方法 → 反射调用 → 返回结果。
     *
     * @param invocationJson TASK_REQUEST body（RpcInvocation 的 JSON）
     * @return 方法返回值（可能为 null），序列化后放入 TASK_RESPONSE
     */
    public Object dispatch(String invocationJson) throws Exception {
        RpcInvocation invocation = GSON.fromJson(invocationJson, RpcInvocation.class);

        // ① 查找服务实现
        Object service = registry.lookup(invocation.getServiceName());
        if (service == null) {
            throw new IllegalStateException(
                    "服务未找到: " + invocation.getServiceName());
        }

        // ② 获取 Method（优先从缓存取）
        Method method = getMethod(service.getClass(), invocation);

        // ③ 转换参数类型（Gson 数字类型处理）
        Object[] convertedArgs = convertArgs(invocation.getArgs(), method.getParameterTypes());

        // ④ 反射调用
        log.debug("RPC 调用: {}.{}(), requestId={}",
                invocation.getServiceName(), invocation.getMethodName(), invocation.getRequestId());
        return method.invoke(service, convertedArgs);
    }

    /**
     * 根据方法名 + 参数类型列表匹配 Method 对象。
     */
    private Method getMethod(Class<?> serviceClass, RpcInvocation invocation)
            throws NoSuchMethodException, ClassNotFoundException {

        String cacheKey = buildCacheKey(invocation);
        Method cached = methodCache.get(cacheKey);
        if (cached != null) {
            return cached;
        }

        String[] typeNames = invocation.getParameterTypes();
        Class<?>[] paramTypes = new Class<?>[typeNames.length];
        for (int i = 0; i < typeNames.length; i++) {
            paramTypes[i] = toClass(typeNames[i]);
        }

        Method method = serviceClass.getMethod(invocation.getMethodName(), paramTypes);
        methodCache.put(cacheKey, method);
        return method;
    }

    /**
     * 将参数数组中的值转换为方法签名声明的类型。
     * 主要解决 Gson 将所有数字解析为 Double 的问题。
     */
    private Object[] convertArgs(Object[] rawArgs, Class<?>[] targetTypes) {
        if (rawArgs == null || rawArgs.length == 0) {
            return rawArgs;
        }
        Object[] converted = new Object[rawArgs.length];
        for (int i = 0; i < rawArgs.length; i++) {
            converted[i] = convertSingleArg(rawArgs[i], targetTypes[i]);
        }
        return converted;
    }

    @SuppressWarnings({"rawtypes", "unchecked"})
    private Object convertSingleArg(Object raw, Class<?> targetType) {
        if (raw == null) return null;
        if (targetType.isInstance(raw)) return raw;

        // Gson 把 JSON 数字解析为 Double，需要转为目标类型
        if (raw instanceof Number num) {
            if (targetType == int.class || targetType == Integer.class) return num.intValue();
            if (targetType == long.class || targetType == Long.class) return num.longValue();
            if (targetType == double.class || targetType == Double.class) return num.doubleValue();
            if (targetType == float.class || targetType == Float.class) return num.floatValue();
            if (targetType == short.class || targetType == Short.class) return num.shortValue();
            if (targetType == byte.class || targetType == Byte.class) return num.byteValue();
        }

        // String → 枚举
        if (targetType.isEnum() && raw instanceof String s) {
            return Enum.valueOf((Class<? extends Enum>) targetType, s);
        }

        // 兜底：用 Gson 的转换
        return GSON.fromJson(GSON.toJson(raw), targetType);
    }

    private String buildCacheKey(RpcInvocation inv) {
        return inv.getServiceName() + "#" + inv.getMethodName()
                + "#" + String.join(",", inv.getParameterTypes());
    }

    /**
     * 将类型名称转为 Class 对象，处理基本类型。
     */
    private Class<?> toClass(String typeName) throws ClassNotFoundException {
        return switch (typeName) {
            case "int"     -> int.class;
            case "long"    -> long.class;
            case "double"  -> double.class;
            case "float"   -> float.class;
            case "boolean" -> boolean.class;
            case "byte"    -> byte.class;
            case "short"   -> short.class;
            case "char"    -> char.class;
            case "void"    -> void.class;
            default        -> Class.forName(typeName);
        };
    }
}
```

**关键设计决策①：Method 缓存**

反射调用 `getMethod()` 本身不慢，但用 `serviceClass.getMethod(name, paramTypes)` 每次都要遍历类的所有方法去做参数匹配。缓存 Method 对象可以跳过这一步，在高频调用场景下有明显收益。key 是 `serviceName#methodName#paramType1,paramType2`，唯一确定一个方法。

**关键设计决策②：Gson 数字类型转换**

```
JSON 没有 int / long / double 的区分，Gson 默认把所有数字解析为 Double。
如果你的方法是 processImage(String path, int quality)，
  body = {"args": ["img.jpg", 90]}
  → Gson 把 90 解析为 Double(90.0)
  → method.invoke(service, "img.jpg", Double(90.0))
  → IllegalArgumentException: argument type mismatch
     (期望 int，实际是 Double)

所以需要 convertArgs() 做类型转换：检查目标类型，把 Double 拆箱成 int/long 等。
```

**关键设计决策③：枚举参数支持**

如果接口方法有枚举参数（如 `TaskType type`），Worker 收到的是字符串 `"INFERENCE"`，需要转回枚举值。`Enum.valueOf()` 完成这个映射。

**关键设计决策④：异常怎么处理？**

Worker 端如果执行方法时抛了异常，`dispatch()` 会把这个异常抛出去。我们在 `ClientHandler` 里 catch 住它，把异常信息塞进 TASK_RESPONSE 的 body，这样 Client 的代理能拿到一个错误响应。目前阶段简单处理——后续课可以做专门的异常编码。

### 5.5 ClientHandler 改造

位置：`heteromesh-worker/src/main/java/com/heteromesh/worker/ClientHandler.java`

**为什么要改？**
- 原来 `handleTaskRequest()` 是死代码——拼一个 `"[nodeId] 已处理: " + body` 就返回了
- 现在要变成真正的 RPC 分发：解析 RpcInvocation → 查服务 → 反射调用 → 返回结果
- **和原来的区别**：原来的 echo 逻辑被替换为 `RpcDispatcher.dispatch()`

```java
// ClientHandler.java 改动：

// ==================== 改动前 ====================
public class ClientHandler extends SimpleChannelInboundHandler<Message> {
    private final RpcClient rpcClient;
    private final String nodeId;

    // ...

    private void handleTaskRequest(ChannelHandlerContext ctx, Message msg) {
        log.info("收到转发任务: requestId = {}, body = {}", msg.getRequestId(), msg.getBody());
        String result = "[" + this.nodeId + "] 已处理: " + msg.getBody();
        Message response = Message.createTaskResponse(msg.getRequestId(), result);
        ctx.writeAndFlush(response);
    }
}

// ==================== 改动后 ====================
public class ClientHandler extends SimpleChannelInboundHandler<Message> {
    private final RpcClient rpcClient;
    private final String nodeId;
    private final RpcDispatcher dispatcher;  // ← 新增字段

    // 构造函数加 dispatcher 参数
    public ClientHandler(RpcClient client, String nodeId, RpcDispatcher dispatcher) {
        this.rpcClient = client;
        this.nodeId = nodeId;
        this.dispatcher = dispatcher;
    }

    // ...

    private void handleTaskRequest(ChannelHandlerContext ctx, Message msg) {
        log.info("收到 RPC 调用: requestId={}", msg.getRequestId());
        try {
            // ① 反射分发：找到服务 → 调用方法 → 拿到返回值
            Object result = dispatcher.dispatch(msg.getBody());

            // ② 将返回值序列化后返回
            String resultJson = result != null ? new Gson().toJson(result) : "";
            Message response = Message.createTaskResponse(msg.getRequestId(), resultJson);
            ctx.writeAndFlush(response);

        } catch (Exception e) {
            log.error("RPC 调用失败: requestId={}", msg.getRequestId(), e);
            // ③ 异常信息也返回给调用方
            String errorBody = "{\"error\":\"" + e.getMessage() + "\"}";
            Message response = Message.createTaskResponse(msg.getRequestId(), errorBody);
            ctx.writeAndFlush(response);
        }
    }
}
```

**改完后 `channelActive` 里的 `rpcClient.call("你好")` 那行可以删掉了**——因为注册完没必要再发一个测试 echo。当然保留也无所谓，Worker 既是服务提供者（处理别人发来的 TASK_REQUEST），也可以作为消费者（发请求给别的 Worker）。这节课先关注「提供者」这一半。

## 八、复习问题

1. JDK 动态代理的核心原理是什么？`Proxy.newProxyInstance()` 的三个参数分别是什么？
2. `RpcInvocation` 为什么需要 `parameterTypes` 字段？只有 `methodName` + `args` 不行吗？
3. 代理的 `invoke()` 方法里，为什么要判断 `method.getDeclaringClass() == Object.class`？
4. `RpcDispatcher` 里为什么要缓存 Method 对象？用什么做 key？
5. Gson 把 JSON 里的数字解析成了什么类型？这会导致什么问题？怎么解决？
6. 描述一次完整的 RPC 调用经过的所有模块：Client 代理 → ... → Worker 反射调用 → ... → Client 拿到结果
7. Controller 需要改代码吗？为什么？
8. `RpcServiceRegistry` 为什么用 `ConcurrentHashMap` 而不是普通 `HashMap`？
9. Worker 端执行方法时抛了异常，Client 端会怎样？
10. 如果要在代理里支持异步调用（接口方法返回 `CompletableFuture<T>`），怎么改？

### 参考答案

**1. JDK 动态代理原理：**

在运行时（通过字节码生成）动态创建一个实现了指定接口的代理类。`Proxy.newProxyInstance(classLoader, interfaces, handler)` 的三个参数：① 类加载器（定义代理类在哪个 ClassLoader 里）；② 要实现的接口数组；③ InvocationHandler（所有方法调用都会转发到这里）。运行时动态生成字节码，不需要写 `.java` 文件。

**2. parameterTypes 为什么必要？**

Java 支持方法重载：一个接口里可以有多个同名方法，仅参数类型不同。如果没有 parameterTypes，Worker 端拿到 `methodName="process"` + `args=["img.jpg"]` 时无法确定该调 `process(String)` 还是 `process(byte[])`。有了 parameterTypes，用 `getMethod(name, paramTypes)` 就能精确匹配。**这和 Java 编译器的重载决议是一个道理**——编译时也是靠参数类型确定调用哪个方法。

**3. 为什么要判断 `Object.class`？**

`toString()`、`equals()`、`hashCode()` 这三个方法定义在 Object 里，代理对象也有它们。如果把它们也当成 RPC 调用发到远程，远程没有这个代理对象的对应物，会出错。而且 `toString()` 在日志里无处不在，如果走远程会导致性能问题甚至死循环。

**4. Method 缓存：**

`getMethod()` 每次要遍历类的所有方法做参数匹配，在高频调用下浪费 CPU。缓存 key = `"serviceName#methodName#paramType1,paramType2,..."`，唯一确定一个方法。这个缓存不需要失效——同一个 serviceName 下同名同参数的方法在运行时不会变。

**5. Gson 数字类型问题：**

Gson 默认把 JSON 里的所有数字解析为 `Double`。如果接口参数声明是 `int`，`method.invoke()` 传 `Double(90.0)` 会报 `IllegalArgumentException: argument type mismatch`。解决办法：`RpcDispatcher.convertArgs()` 检查目标参数类型，如果是 `int.class` 就拆箱 `num.intValue()`，如果是 `long.class` 就 `num.longValue()`，以此类推。

**6. 完整 RPC 调用链路：**

```
Client: service.processImage("img.jpg")
  → RpcProxy.invoke()
  → 构造 RpcInvocation {serviceName, methodName, parameterTypes, args}
  → Gson.toJson(invocation)
  → rpcClient.call(body)  ← 发送 TASK_REQUEST
  → [Netty Channel]
  
Controller: ServerHandler.handleTaskRequest()
  → loadBalancer.select(requestId)  ← 选 Worker
  → 转发 TASK_REQUEST
  → [Netty Channel]
  
Worker: ClientHandler.handleTaskRequest()
  → RpcDispatcher.dispatch(body)
  → Gson.fromJson(body, RpcInvocation.class)
  → registry.lookup(invocation.serviceName)  ← 找到实现对象
  → getMethod(serviceClass, invocation)       ← 找到 Method
  → convertArgs(invocation.args, paramTypes)  ← 转换参数类型
  → method.invoke(service, convertedArgs)     ← 反射执行！
  → Gson.toJson(result)
  → ctx.writeAndFlush(TASK_RESPONSE)
  
  [原路返回 → Controller 转发 → Client]
  
Client: RpcClient.onResponse(msg)
  → future.complete(msg)
  → RpcProxy 拿到 response.body
  → Gson.fromJson(body, method.getReturnType())
  → return result  ← service.processImage() 返回 "图片处理完成"
```

**7. Controller 不需要改：**

Controller 的 ServerHandler 只读 `msg.getType()` 做路由转发，不读 `msg.getBody()`。body 从 `"你好"` 变成了 `RpcInvocation JSON`，对 Controller 来说是透明的。这就是分层设计的价值——传输层（Controller）不关心应用层（RPC）的数据格式。

**8. ConcurrentHashMap vs HashMap：**

虽然当前是「启动时注册、运行时不变」，但 ConcurrentHashMap 保证了跨线程的 happens-before 语义——注册线程 put 之后，处理 RPC 的 Netty worker 线程能立刻看到。HashMap 在多线程下不能保证可见性，理论上可能出现注册了但查不到的情况。

**9. Worker 端异常 → Client 端：**

`ClientHandler.handleTaskRequest()` 的 catch 块会把异常信息放到 TASK_RESPONSE 的 body 里返回（`{"error":"..."}` 格式）。Client 端 `future.get()` 能正常拿到 Message，但 body 里是错误信息而不是预期的返回值。当前阶段 Client 端不会自动识别并抛异常——`Gson.fromJson(errorBody, returnType)` 会失败。后续课会做专门的异常编码（RpcException），让 Client 端自动识别并抛出和服务器端一致的异常。

**10. 异步调用支持：**

```java
// 代理中判断返回值类型
if (method.getReturnType() == CompletableFuture.class) {
    return future.thenApply(msg -> {
        // 从 Message body 反序列化出实际类型
        // 需要知道泛型参数（CompletableFuture<String> 里的 String）
        // 这需要获取方法的泛型返回类型（method.getGenericReturnType()）
        // 用 ParameterizedType 提取实际类型参数
        return GSON.fromJson(msg.getBody(), actualTypeArgument);
    });
}
```

## 九、面试怎么聊

> "通信层做完之后，我做了 RPC 框架最关键的一步：动态代理 + 服务发布/引用。Client 端用 JDK 动态代理，`Proxy.newProxyInstance()` 生成代理对象，InvocationHandler 拦截所有方法调用，把「方法名 + 参数类型 + 参数值」打包成 RpcInvocation，序列化后通过 Netty 发出去，然后等响应、解包、返回。对调用方来说，`service.processImage(img)` 就是一行代码，完全感知不到网络的存在——这才是 RPC。"

> "RpcInvocation 是一个自描述的方法调用结构：serviceName、methodName、parameterTypes、args。为什么要带 parameterTypes？因为 Java 有方法重载，如果不区分 `process(String)` 和 `process(byte[])`，Worker 端没法知道该调哪个。这和编译器的重载决议原理一样。"

> "Worker 端收到调用后，通过 RpcDispatcher 做反射分发：从本地 ServiceRegistry 找到实现对象，用缓存的 Method 反射调用，拿到返回值后序列化返回。之所以缓存 Method，是因为 `getMethod()` 每次要遍历类的所有方法——高频调用场景下这是没必要的开销。"

> "有意思的细节是 Gson 的数字类型问题——Gson 默认把 JSON 数字解析成 Double，如果你的接口参数是 int，反射调用会报类型不匹配。我做了 convertArgs() 来根据目标参数类型转换：int→intValue，long→longValue，等等。"

> "Controller 一行代码都不用改——它只转发 TASK_REQUEST/TASK_RESPONSE，body 里是裸字符串还是 RpcInvocation JSON 对它来说是透明的。这验证了我们分层架构的合理性：传输层不关心应用层协议。"
