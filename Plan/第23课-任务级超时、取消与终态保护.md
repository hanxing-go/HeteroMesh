# 第23课：任务级超时、取消与终态保护

---

## 一、本课目标

前面第 21 课和第 22 课，我们已经把任务结果写回和任务查询服务补上了。

现在系统已经能做到：

```text
Client 提交任务
Controller 创建任务
Controller 选择 Worker
Worker 执行任务
Worker 返回 TASK_RESULT
Controller 写回 TaskStore
TaskQueryService 查询任务结果
```

但是这里还有三个真实系统一定会遇到的问题：

```text
1. Worker 一直不返回结果怎么办？
2. 用户想取消一个还没完成的任务怎么办？
3. 任务已经 TIMEOUT / CANCELED 了，Worker 后来又返回 SUCCEEDED 怎么办？
```

本课要做的是任务级超时、取消和终态保护。

完成后，系统应该具备：

```text
任务超过 timeoutMs 后进入 TIMEOUT
未完成任务可以被取消并进入 CANCELED
SUCCEEDED / FAILED / TIMEOUT / CANCELED 这些终态不能被后到结果覆盖
```

---

## 二、先分清 RPC 超时和任务超时

这是本课最重要的概念。

RPC 超时关注的是：

```text
这一次远程调用，我等响应等了多久？
```

比如第 9 课里的 `RpcFuture.get(timeoutMs)`，如果 Client 等不到响应，就返回 `RpcStatus.TIMEOUT`。

任务超时关注的是：

```text
这个业务任务，从提交到完成，是否超过了任务允许的最长执行时间？
```

比如图片推理任务设置了：

```java
timeoutMs = 30_000;
```

那 Controller 应该在任务提交后注册一个超时检查。超过 30 秒还没有进入终态，就把任务标记为：

```java
TaskStatus.TIMEOUT
```

二者区别：

| 类型 | 关注对象 | 发生位置 | 结果 |
|------|----------|----------|------|
| RPC 超时 | 一次调用等待响应 | Client / RpcFuture | `RpcStatus.TIMEOUT` |
| 任务超时 | 一个任务生命周期 | Controller / TaskStore | `TaskStatus.TIMEOUT` |

面试时可以这样讲：

```text
RPC 超时是通信层语义，解决“这次调用我还等不等”。
任务超时是业务生命周期语义，解决“这个任务是否还应该被系统承认”。
```

## 三、本课边界

本课先不做这些：

```text
不做 HTTP API
不做真正通知 Worker 中断执行
不做任务级重试
不做持久化数据库
```

我们先把 Controller 侧状态保护做好。

也就是说，即使 Worker 还在执行，Controller 也可以先把任务标记为 `TIMEOUT` 或 `CANCELED`。

如果 Worker 后面才返回结果，Controller 不应该再覆盖这个终态。

## 五、第一步：给 TaskStatus 增加终态判断

打开：

```text
heteromesh-common/src/main/java/com/heteromesh/task/TaskStatus.java
```

现在已经有这些状态：

```java
SUBMITTED,
DISPATCHING,
RUNNING,
SUCCEEDED,
FAILED,
TIMEOUT,
CANCELED
```

本课要加一个方法：

```java
public boolean isTerminal() {
    // TODO:
    // SUCCEEDED / FAILED / TIMEOUT / CANCELED 返回 true
    // 其他状态返回 false
}
```

为什么要放在 `TaskStatus` 里？

因为“哪些状态是终态”是状态枚举自己的语义，不应该散落在各个类里写：

```java
status == SUCCEEDED || status == FAILED || ...
```

后续代码只需要写：

```java
if (task.getStatus().isTerminal()) {
    ...
}
```

## 六、第二步：扩展 TaskStore 接口

打开：

```text
heteromesh-common/src/main/java/com/heteromesh/task/TaskStore.java
```

现在已经有：

```java
void complete(String taskId, TaskResult result);
```

本课建议新增两个方法：

```java
void timeout(String taskId, String reason);

void cancel(String taskId, String reason);
```

语义分别是：

```text
timeout: Controller 判定任务超时，任务进入 TIMEOUT
cancel: 用户或上层系统取消任务，任务进入 CANCELED
```

注意：这里不要直接让外部调用 `updateStatus(taskId, TIMEOUT)`。

原因是 `timeout` / `cancel` 不只是改状态，还应该写入一个 `TaskResult`，方便后续查询详情时能看到：

```text
status = TIMEOUT
errorMessage = "Task timed out after 30000 ms"
finishedAt = ...
workerId = assignedWorkerId
```

## 七、第三步：实现 InMemoryTaskStore 的终态保护

打开：

```text
heteromesh-common/src/main/java/com/heteromesh/task/InMemoryTaskStore.java
```

本课的核心保护规则是：

```text
只要任务已经是终态，就不能再被 complete / timeout / cancel 修改。
```

可以先写一个私有方法：

```java
private void ensureNotTerminal(TaskMetadata task) {
    // TODO:
    // 如果 task.getStatus().isTerminal()
    // 就抛 IllegalStateException
}
```

然后在这些入口里调用：

```java
complete(...)
timeout(...)
cancel(...)
```

### 7.1 改 complete

当前 `complete` 大概是：

```java
public void complete(String taskId, TaskResult result) {
    TaskMetadata task = requireTask(taskId);
    stateMachine.transit(task, result.getStatus());
    task.setResult(result);
    task.markUpdated();
}
```

你要加两层保护：

```java
public void complete(String taskId, TaskResult result) {
    TaskMetadata task = requireTask(taskId);

    // TODO 1: 确认 task 还不是终态

    // TODO 2: 确认 result.getStatus() 是终态
    // Worker 返回 RUNNING / DISPATCHING 这种结果没有意义，应该拒绝

    // TODO 3: 走状态机

    // TODO 4: 写 result
}
```

为什么要检查 `result.getStatus().isTerminal()`？

因为 `complete` 的语义是“写入最终结果”。最终结果只能是：

```text
SUCCEEDED / FAILED / TIMEOUT / CANCELED
```

不能是：

```text
RUNNING / DISPATCHING / SUBMITTED
```

### 7.2 实现 timeout / cancel

你可以提取一个私有方法：

```java
private void finishWithoutWorkerResult(String taskId,
                                       TaskStatus status,
                                       String reason) {
    // TODO 1: requireTask
    // TODO 2: ensureNotTerminal
    // TODO 3: 构造 TaskResult
    // TODO 4: stateMachine.transit(task, status)
    // TODO 5: task.setResult(result)
    // TODO 6: markUpdated
}
```

这里的 `TaskResult` 可以这样理解：

```text
虽然不是 Worker 返回的结果，
但 Controller 也要为 TIMEOUT / CANCELED 写入一个系统生成的结果。
```

字段建议：

```java
taskId         = taskId
status         = TIMEOUT 或 CANCELED
output         = null
errorMessage   = reason
startedAt      = now
finishedAt     = now
workerId       = task.getAssignedWorkerId()
```

然后：

```java
public void timeout(String taskId, String reason) {
    finishWithoutWorkerResult(taskId, TaskStatus.TIMEOUT, reason);
}

public void cancel(String taskId, String reason) {
    finishWithoutWorkerResult(taskId, TaskStatus.CANCELED, reason);
}
```

## 八、第四步：设计 TaskTimeoutManager

新增：

```text
heteromesh-controller/src/main/java/com/heteromesh/controller/task/TaskTimeoutManager.java
```

它的职责是：

```text
任务调度成功后，按照 request.timeoutMs 注册一个延迟任务。
延迟任务触发时，如果任务还没结束，就调用 taskStore.timeout(...)
```

建议结构：

```java
public class TaskTimeoutManager implements AutoCloseable {
    private final TaskStore taskStore;
    private final ScheduledExecutorService scheduler;
    private final Map<String, ScheduledFuture<?>> timeoutTasks = new ConcurrentHashMap<>();

    public void registerTimeout(TaskMetadata task) {
        // TODO:
        // 1. 读取 task.getRequest().getTimeoutMs()
        // 2. timeoutMs <= 0 时直接返回
        // 3. 如果同一个 taskId 已经注册过，先取消旧的
        // 4. scheduler.schedule(...)
        // 5. 到点后调用 taskStore.timeout(...)
        // 6. finally 里从 timeoutTasks 移除
    }

    public boolean cancelTimeout(String taskId) {
        // TODO:
        // 从 timeoutTasks 删除并 cancel
    }

    @Override
    public void close() {
        // TODO:
        // 取消所有未触发的 timeout 任务
        // 关闭 scheduler
    }
}
```

这里有一个设计点：

```java
taskStore.timeout(...)
```

可能会抛 `IllegalStateException`。

比如任务已经先一步 `SUCCEEDED` 了，超时定时器后触发。这时候应该忽略，因为终态保护已经生效。

可以在定时任务里：

```java
try {
    taskStore.timeout(...);
} catch (IllegalStateException ignored) {
    // 任务已经完成，超时检查安全忽略
}
```

## 九、第五步：接入 TaskScheduler

打开：

```text
heteromesh-controller/src/main/java/com/heteromesh/controller/scheduler/TaskScheduler.java
```

现在 `schedule` 成功后会：

```java
taskStore.assignWorker(taskId, worker.getNodeId());
taskStore.recordAttempt(taskId, worker.getNodeId());
return ScheduleResult.success(task, worker);
```

你要让它在调度成功后注册超时：

```java
taskStore.assignWorker(taskId, worker.getNodeId());
taskStore.recordAttempt(taskId, worker.getNodeId());

// TODO:
// timeoutManager.registerTimeout(task)

return ScheduleResult.success(task, worker);
```

构造器也要改，让 `TaskScheduler` 持有一个 `TaskTimeoutManager`。

注意：为了不把旧测试全部改爆，你可以保留旧构造器：

```java
public TaskScheduler(TaskStore taskStore,
                     ServiceRegistry serviceRegistry,
                     LoadBalancer loadBalancer) {
    this(taskStore, serviceRegistry, loadBalancer, null);
}
```

然后新构造器：

```java
public TaskScheduler(TaskStore taskStore,
                     ServiceRegistry serviceRegistry,
                     LoadBalancer loadBalancer,
                     TaskTimeoutManager timeoutManager) {
    ...
}
```

如果 `timeoutManager == null`，就不注册超时。这样旧测试仍然能跑。

## 十一、第七步：处理后到 TASK_RESULT

打开：

```text
heteromesh-controller/src/main/java/com/heteromesh/controller/ServerHandler.java
```

当前 `handleTaskResult` 会：

```java
TaskResult result = TaskPayloadCodec.decodeResult(message.getBody());
taskStore.complete(result.getTaskId(), result);
```

现在 `complete` 加了终态保护后，如果任务已经 `TIMEOUT` 或 `CANCELED`，这里会抛 `IllegalStateException`。

你要做的是：

```java
try {
    taskStore.complete(result.getTaskId(), result);
} catch (IllegalStateException e) {
    // TODO:
    // 说明这是后到结果，不能覆盖终态
    // 记录日志即可
}
```

这里不要再强行写回结果。

也就是说：

```text
TIMEOUT 任务后到 SUCCEEDED
最终状态仍然是 TIMEOUT
```

这就是终态保护。

## 十三、常见错误

### 错误 1：直接用 updateStatus(taskId, TIMEOUT)

这样只会改状态，不会写入 `TaskResult`。

后续 `TaskQueryService.getTask(...)` 查详情时，就看不到失败原因和结束时间。

### 错误 2：忘记终态保护

如果没有终态保护，就会出现：

```text
任务已经 TIMEOUT
Worker 后来返回 SUCCEEDED
任务又变成 SUCCEEDED
```

这会让 Dashboard、日志、用户感知全部混乱。

### 错误 3：timeout/cancel 不走 TaskStateMachine

不要直接：

```java
task.setStatus(TaskStatus.TIMEOUT);
```

应该继续走：

```java
stateMachine.transit(task, TaskStatus.TIMEOUT);
```

这样状态规则仍然集中在状态机里。

### 错误 4：TaskTimeoutManager 触发后不清理 Map

定时任务触发后要把 `taskId` 从 `timeoutTasks` 移除。

否则任务越多，Map 越大。

### 错误 5：把取消理解成真的杀掉 Worker 线程

本课的取消只是 Controller 侧任务生命周期取消。

真正通知 Worker 停止执行，是后续更复杂的能力，需要：

```text
取消消息
Worker 执行器可中断
任务执行上下文
幂等取消
```

本课先不做。

## 十四、完成标准

本课完成后，你应该能做到：

```text
1. task.timeoutMs 到期后，任务进入 TIMEOUT
2. 调用 taskStore.cancel 后，任务进入 CANCELED
3. TIMEOUT / CANCELED 后，Worker 后到的 SUCCEEDED 不会覆盖原状态
4. TaskQueryService 能查到 TIMEOUT / CANCELED 的 result 和 errorMessage
5. 你能讲清楚 RPC 超时和任务超时的区别
```

## 十五、面试讲法

可以这样组织：

```text
我们把任务状态设计成一个状态机，SUCCEEDED、FAILED、TIMEOUT、CANCELED 都是终态。
第 23 课开始，TaskStore 不只是保存结果，还负责保护终态。
Controller 调度成功后会注册任务级 timeout，到期仍未完成就把任务标记为 TIMEOUT。
如果用户取消任务，则标记为 CANCELED。
后续 Worker 即使返回成功结果，也不能覆盖已有终态。
这解决的是任务生命周期一致性问题，不是普通 RPC 等响应超时问题。
```
