## 一、这节课解决什么问题？

### 1.1 当前系统的问题

现在的链路更像这样：

```text
Client -> Controller -> Worker -> Controller -> Client
```

Controller 只是中转消息。它并不知道：

- 这个请求对应哪个任务
- 任务现在是刚提交、已派发、正在执行，还是已经完成
- 任务失败了几次
- 任务分配给过哪些 Worker
- 任务什么时候创建、什么时候结束
- 用户如何查询任务状态

这会导致面试官一追问就露出短板：

> 你说这是任务调度系统，那任务在哪里？
> 任务生命周期怎么管理？
> Worker 挂了以后任务状态怎么变化？
> 怎么查询某个任务的执行结果？

所以本课要先补最基础、最重要的一层：**任务模型与状态机**。

### 1.2 本课完成后的效果

你会新增一组任务领域类：

```text
TaskRequest       用户提交的任务请求
TaskResult        Worker 执行后的任务结果
TaskStatus        任务状态枚举
TaskMetadata      Controller 维护的任务元数据
TaskStateMachine  任务状态流转校验器
```

以后 Controller 收到请求后，不再只是转发，而是：

```text
1. 创建 TaskMetadata
2. 状态 SUBMITTED
3. 选择 Worker
4. 状态 DISPATCHING
5. Worker 接收任务
6. 状态 RUNNING
7. Worker 返回结果
8. 状态 SUCCEEDED / FAILED / TIMEOUT
```

## 二、参考主流项目怎么设计

### 2.1 XXL-JOB：任务有生命周期

XXL-JOB 不是把请求直接扔给执行器就完事，而是维护调度日志和执行状态：

- 任务被触发
- 任务被路由到执行器
- 执行器回调结果
- 调度中心记录成功/失败

HeteroMesh 后面也要做类似事情。

### 2.2 Kubernetes Job：状态是系统可观测性的基础

Kubernetes 的 Job/Pod 都有状态：

- Pending
- Running
- Succeeded
- Failed

状态不是装饰品，而是调度器做决策、用户查询、系统恢复的基础。

### 2.3 Apache Flink / Spark：任务失败和重试必须可追踪

分布式计算框架不会只说“失败了”，而会记录：

- 哪个 task attempt 失败
- 失败在哪个节点
- 是否还能重试
- 最终是否完成

HeteroMesh 当前已有重试和熔断，但缺少任务层面的状态记录。本课就是补这块地基。

## 三、任务状态设计

### 3.1 推荐状态

新建枚举：

位置：

`heteromesh-common/src/main/java/com/heteromesh/task/TaskStatus.java`

```java
package com.heteromesh.task;

/**
 * 任务状态。
 *
 * 注意：状态不是随便跳的，必须按 TaskStateMachine 允许的路径流转。
 */
public enum TaskStatus {
    SUBMITTED,      // 已提交到 Controller，但还没选择 Worker
    DISPATCHING,    // Controller 正在选择 Worker / 正在转发
    RUNNING,        // Worker 已接收并开始执行
    SUCCEEDED,      // 执行成功
    FAILED,         // 执行失败，且不再重试
    TIMEOUT,        // 超时
    CANCELED        // 被用户取消，后续 HTTP API 会用到
}
```

### 3.2 为什么不用字符串？

```java
// 不推荐
private String status;

// 推荐
private TaskStatus status;
```

原因：

- 字符串容易拼错
- 枚举天然限制合法取值
- switch 更清楚
- 面试时能讲状态机

## 四、任务请求模型

### 4.1 TaskRequest

位置：

`heteromesh-common/src/main/java/com/heteromesh/task/TaskRequest.java`

建议字段：

```java
package com.heteromesh.task;

import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

import java.util.Map;

/**
 * 用户提交给 Controller 的任务请求。
 *
 * 当前阶段先不接真实 GPU 推理，payload 可以是一段字符串或 JSON。
 * resourceRequirements 用来为后续异构调度做准备。
 */
@Data
@NoArgsConstructor
@AllArgsConstructor
public class TaskRequest {
    private String taskId;
    private String taskType;
    private String payload;
    private Map<String, String> resourceRequirements;
    private long timeoutMs;
}
```

字段解释：

| 字段 | 说明 |
|------|------|
| taskId | 任务唯一 ID，可以由客户端传，也可以由 Controller 生成 |
| taskType | 任务类型，比如 `TEXT_GENERATION`、`IMAGE_INFERENCE` |
| payload | 任务输入 |
| resourceRequirements | 资源需求，比如 GPU 型号、显存下限 |
| timeoutMs | 任务超时时间 |

### 4.2 为什么保留 resourceRequirements？

因为 HeteroMesh 的目标是异构 GPU 调度。后面可以这样表达任务需求：

```java
Map.of(
    "gpuType", "RTX 4090",
    "minVramMb", "12000"
)
```

这样调度器就可以优先选择满足条件的 Worker。

## 五、任务结果模型

### 5.1 TaskResult

位置：

`heteromesh-common/src/main/java/com/heteromesh/task/TaskResult.java`

```java
package com.heteromesh.task;

import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

/**
 * Worker 执行任务后的结果。
 */
@Data
@NoArgsConstructor
@AllArgsConstructor
public class TaskResult {
    private String taskId;
    private TaskStatus status;
    private String output;
    private String errorMessage;
    private long startedAt;
    private long finishedAt;
    private String workerId;
}
```

设计原则：

- 成功时：`status = SUCCEEDED`，`output` 有值
- 失败时：`status = FAILED`，`errorMessage` 有值
- `startedAt` / `finishedAt` 用于统计耗时
- `workerId` 用于追踪任务在哪个 Worker 上执行

## 六、Controller 侧任务元数据

### 6.1 TaskMetadata

位置：

`heteromesh-common/src/main/java/com/heteromesh/task/TaskMetadata.java`

```java
package com.heteromesh.task;

import lombok.Data;

import java.util.ArrayList;
import java.util.List;

/**
 * Controller 维护的任务元数据。
 *
 * TaskRequest 是用户输入，TaskMetadata 是系统内部对任务生命周期的记录。
 */
@Data
public class TaskMetadata {
    private final String taskId;
    private final TaskRequest request;

    private TaskStatus status = TaskStatus.SUBMITTED;
    private String assignedWorkerId;
    private int retryCount = 0;
    private long createdAt = System.currentTimeMillis();
    private long updatedAt = createdAt;
    private TaskResult result;

    private final List<String> attemptedWorkers = new ArrayList<>();

    public TaskMetadata(String taskId, TaskRequest request) {
        this.taskId = taskId;
        this.request = request;
    }

    public void markUpdated() {
        this.updatedAt = System.currentTimeMillis();
    }
}
```

### 6.2 为什么 TaskRequest 和 TaskMetadata 分开？

这是很重要的设计点。

```text
TaskRequest:
  用户提交了什么

TaskMetadata:
  系统怎么调度、执行、记录这个任务
```

不要把所有字段都塞进一个类。否则后面会变成一个“上帝对象”。

面试时可以这样说：

> 我把用户输入和系统运行时元数据拆开。TaskRequest 表示任务本身，TaskMetadata 表示 Controller 对任务生命周期的追踪，包括状态、分配节点、重试次数、尝试过的 Worker 和结果。

## 七、状态机设计

### 7.1 为什么需要状态机？

如果没有状态机，代码里可能出现这种非法流转：

```text
SUBMITTED -> SUCCEEDED
FAILED -> RUNNING
TIMEOUT -> DISPATCHING
```

这些状态跳转在业务上是不合理的。

所以我们要写一个小的状态机类，专门判断：

```text
from 状态 能不能转到 to 状态
```

### 7.2 TaskStateMachine

位置：

`heteromesh-common/src/main/java/com/heteromesh/task/TaskStateMachine.java`

参考代码：

```java
package com.heteromesh.task;

import java.util.EnumMap;
import java.util.EnumSet;
import java.util.Map;
import java.util.Set;

/**
 * 任务状态机。
 *
 * 职责：
 * 1. 定义哪些状态可以流转到哪些状态
 * 2. 拒绝非法状态跳转
 */
public class TaskStateMachine {
    private static final Map<TaskStatus, Set<TaskStatus>> ALLOWED_TRANSITIONS =
            new EnumMap<>(TaskStatus.class);

    static {
        ALLOWED_TRANSITIONS.put(TaskStatus.SUBMITTED,
                EnumSet.of(TaskStatus.DISPATCHING, TaskStatus.CANCELED));

        ALLOWED_TRANSITIONS.put(TaskStatus.DISPATCHING,
                EnumSet.of(TaskStatus.RUNNING, TaskStatus.FAILED, TaskStatus.TIMEOUT, TaskStatus.CANCELED));

        ALLOWED_TRANSITIONS.put(TaskStatus.RUNNING,
                EnumSet.of(TaskStatus.SUCCEEDED, TaskStatus.FAILED, TaskStatus.TIMEOUT, TaskStatus.CANCELED));

        ALLOWED_TRANSITIONS.put(TaskStatus.SUCCEEDED, EnumSet.noneOf(TaskStatus.class));
        ALLOWED_TRANSITIONS.put(TaskStatus.FAILED, EnumSet.noneOf(TaskStatus.class));
        ALLOWED_TRANSITIONS.put(TaskStatus.TIMEOUT, EnumSet.noneOf(TaskStatus.class));
        ALLOWED_TRANSITIONS.put(TaskStatus.CANCELED, EnumSet.noneOf(TaskStatus.class));
    }

    public boolean canTransit(TaskStatus from, TaskStatus to) {
        // TODO: 从 ALLOWED_TRANSITIONS 里取出 from 对应的集合，判断是否包含 to
        return false;
    }

    public void transit(TaskMetadata task, TaskStatus to) {
        // TODO:
        // 1. 读取 task 当前状态 from
        // 2. 如果不能从 from 转到 to，抛 IllegalStateException
        // 3. 设置 task.status = to
        // 4. 调用 task.markUpdated()
    }
}
```

### 7.3 你要手敲的核心逻辑

`canTransit` 参考：

```java
public boolean canTransit(TaskStatus from, TaskStatus to) {
    Set<TaskStatus> allowed = ALLOWED_TRANSITIONS.get(from);
    return allowed != null && allowed.contains(to);
}
```

`transit` 参考：

```java
public void transit(TaskMetadata task, TaskStatus to) {
    TaskStatus from = task.getStatus();
    if (!canTransit(from, to)) {
        throw new IllegalStateException("Invalid task state transition: " + from + " -> " + to);
    }
    task.setStatus(to);
    task.markUpdated();
}
```

这段很短，但意义很大：它让状态流转有了统一入口。

## 十、面试怎么讲

可以这样讲：

> HeteroMesh 早期只是把 RPC 请求从 Controller 转发给 Worker，后来我补了任务模型，把请求抽象成 TaskRequest，把 Controller 内部运行时信息抽象成 TaskMetadata，并用 TaskStatus 和 TaskStateMachine 约束状态流转。这样后续才能支持任务查询、失败重试、超时处理、Worker 故障转移和可观测性。

如果面试官问：

> 为什么 TaskRequest 和 TaskMetadata 不合成一个类？

可以回答：

> TaskRequest 是用户输入，TaskMetadata 是系统运行时追踪信息。分开后边界更清楚，也方便后续 HTTP API 暴露请求字段，而不暴露内部调度状态。

如果面试官问：

> 状态机是不是过度设计？

可以回答：

> 如果只有一两个状态，确实可以简单 if 判断。但任务调度系统里会有提交、派发、运行、成功、失败、超时、取消等状态，而且状态流转有约束。集中到 TaskStateMachine 可以避免状态跳转散落在各个 Handler 里，后续维护和测试都更清楚。

## 十二、你开始前先想三个问题

1. 为什么任务调度系统不能只靠 `RpcRequest` / `RpcResponse`？
2. 为什么 `SUCCEEDED`、`FAILED`、`TIMEOUT` 应该设计成终态？
